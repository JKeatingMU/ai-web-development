The Fullstack Architecture

In development you run two servers. In production you run one — Express serves both the API and the built React files from the same origin, eliminating CORS entirely for your own frontend.

Development CORS or a Vite proxy bridges the port gap between your two dev servers. You learned this in C3.
Production — one server: Express serves client/dist/ on all non-API routes. Same origin = no CORS needed for your own app.
Third-party consumers (mobile apps, other frontends) still need CORS headers even in production. Keep your CORS config — just tighten the allowed origins.

The API Contract

An API contract is an agreement between frontend and backend about request and response shapes. When both sides are built by AI, mismatches are the most common integration bug.

Naming conventions diverge: databases use snake_case, JavaScript uses camelCase. AI sometimes transforms field names, sometimes doesn't. Always check column names against interface field names.

Shared TypeScript Types

The ideal solution is a single source of truth for your data types — defined once and used by both frontend and backend. AI can generate this; the challenge is keeping it in sync.

shared/types.ts (shared between client + server)
// Single file imported by both client and server // Place in a shared/ directory at the project root export interface Book { id: number; title: string; author: string; status: BookStatus; created_at: string; // ISO 8601 from DB } export type BookStatus = | 'want-to-read' | 'reading' | 'finished'; export interface CreateBookBody { title: string; author: string; status: BookStatus; } export interface ApiError { error: string; // always this key — never 'message' } // In client — import from shared types import type { Book, CreateBookBody } from '../../shared/types'; // In server (if using TypeScript) — same import import type { Book, CreateBookBody } from '../shared/types';
Single source of truth: change the interface once and both frontend and backend immediately get a type error if they're out of sync. TypeScript catches contract violations at compile time.
Pragmatic alternative: if your backend is plain JavaScript (no TypeScript), duplicate the types in the frontend and treat curl output as the ground truth. Less elegant but common in mixed-language projects.
AI prompt tip: paste your schema.sql and ask AI to generate matching TypeScript interfaces. The column names, nullability, and types from SQL map directly to interface fields.
created_at: string — database timestamps come back as ISO 8601 strings over JSON, not JavaScript Date objects. Use new Date(book.created_at) when you need to format them.

Consistent Error Responses

Your frontend's error handling is only as good as your backend's error responses. AI sometimes generates inconsistent error shapes — standardise them once and your api.ts can handle everything uniformly.

server/middleware/errorHandler.js
// Centralised error middleware — always last in Express export function errorHandler(err, req, res, next) { // Log the full error server-side (not sent to client) console.error(err); // Known error types if (err.type === 'validation') { return res.status(422).json({ error: err.message }); } if (err.code === '23505') { // PG unique violation return res.status(409).json({ error: 'Already exists' }); } // Default — never expose internal details res.status(500).json({ error: 'Internal server error' }); } // Register after all routes in server/index.js app.use(errorHandler); // ───────────────────────────────────────────── // api.ts — reads the standard error key if (!res.ok) { const body = await res.json().catch(() => ({})); throw new Error(body.error ?? `HTTP ${res.status}`); }
One error key everywhere: use { error: "..." } consistently. If your backend sometimes returns { error } and sometimes { message }, your frontend catch blocks need to handle both — messy and fragile.
Never send stack traces to the client. err.stack or err.message from an uncaught exception may expose file paths, library versions, or database structure. Log server-side only.
The four error statuses you'll use most: 400 (bad request / validation), 401 (unauthenticated), 403 (authenticated but unauthorised), 404 (not found), 409 (conflict), 422 (unprocessable), 500 (server error).

Environment-Based CORS

Development allows localhost:5173. Production allows your deployed domain. Hardcoding one or the other breaks the other environment. The fix is one environment variable.

server/index.js
import cors from 'cors'; import 'dotenv/config'; // In production this is your Railway domain. // In development it is http://localhost:5173. // Never hardcode either. const allowedOrigin = process.env.CLIENT_ORIGIN ?? 'http://localhost:5173'; app.use(cors({ origin: allowedOrigin, methods: ['GET', 'POST', 'PATCH', 'DELETE'], allowedHeaders: ['Content-Type', 'Authorization'], credentials: true, })); // .env (development) CLIENT_ORIGIN=http://localhost:5173 // Railway dashboard (production) CLIENT_ORIGIN=https://myapp.up.railway.app
Never use origin: '*' in production — it allows any website to make authenticated requests to your API using the visitor's credentials. This is a serious security misconfiguration.
When Express serves React directly (same origin), your own frontend doesn't need CORS. But you still want CORS configured for API consumers — mobile apps, other frontends, curl tests from other origins.
credentials: true is required if you ever use cookies. With JWT in localStorage it is optional, but harmless to include and easier than adding it later.
The ?? fallback means the server works in development without setting CLIENT_ORIGIN in .env — it just uses localhost:5173 automatically.

The /api Prefix Convention

When Express serves both API routes and static React files, you need a way to distinguish them. The /api prefix on every API route is the standard solution.

server/index.js — route order matters
// ① API routes — registered first, prefixed /api app.use('/api/books', booksRouter); app.use('/api/auth', authRouter); app.get('/api/health', (req, res) => res.json({ ok: true })); // ② Serve built React files from client/dist import { fileURLToPath } from 'url'; import { join, dirname } from 'path'; const __dirname = dirname(fileURLToPath(import.meta.url)); const clientDist = join(__dirname, '../client/dist'); app.use(express.static(clientDist)); // ③ Catch-all — send index.html for any non-API path // This supports React Router's client-side routing app.get('*', (req, res) => { res.sendFile(join(clientDist, 'index.html')); });
Order is critical. The catch-all GET * must come last — after all API routes and after express.static. If it's first, every API request returns index.html instead of JSON.
The catch-all serves index.html for routes like /books and /books/42. The browser loads React, React Router reads the URL, and renders the correct page — no 404 on refresh.
__dirname in ES modules: import.meta.url replaces the CommonJS __dirname. AI sometimes generates the CommonJS version — check if your server uses "type": "module" in package.json.
Dev vs prod: in development the Vite dev server handles index.html — the static serving and catch-all only activate in production (after npm run build).

Scaffold Prompt — Fullstack Wiring

Give AI both halves at once. Paste the server entry point and ask for the changes needed to serve the React build alongside the existing API.

✎ Scaffold prompt — paste into your AI assistant
I have an Express API (ES modules, "type": "module") and a React + Vite frontend in client/. Modify my server/index.js to also serve the React production build. Requirements:
  • Serve static files from client/dist using express.static
  • Add a catch-all GET * route that sends client/dist/index.html — placed after all API routes
  • Use ES module path resolution (import.meta.url, not __dirname) to construct the path to client/dist
  • CORS: read the allowed origin from process.env.CLIENT_ORIGIN, falling back to http://localhost:5173

Reading the Generated Wiring

Five things to verify before testing the integrated app.

  • 1Route order: API routes must be registered before express.static and the catch-all. Search the generated file top to bottom — if the catch-all appears before any /api route, move it.
  • 2ES module path resolution: look for import.meta.url. If you see __dirname and your project uses "type": "module", the path will fail at runtime with "ReferenceError: __dirname is not defined".
  • 3CORS origin source: confirm cors({ origin: process.env.CLIENT_ORIGIN ?? 'http://localhost:5173' }). If the origin is hardcoded as a string, it breaks in the other environment.
  • 4Shared types — field names: compare the interface field names in shared/types.ts against your actual database column names from schema.sql. AI may camelCase them; your DB uses snake_case.
  • 5Error key consistency: search the generated route handlers for res.json({ message:. Every error response should use error:, not message:, to match what api.ts reads.

Testing the Integration Locally

Before deploying, build the React app and confirm Express serves it correctly on port 3001.

terminal
# Build the React app $ cd client && npm run build # → creates client/dist/ # Start Express (serves API + built React) $ cd .. && node server/index.js # Test API still works $ curl http://localhost:3001/api/health # → {"ok":true} # Test React app is served $ curl -s http://localhost:3001/ | head -5 # → <!DOCTYPE html>... # Test React Router catch-all $ curl -s http://localhost:3001/books | head -3 # → <!DOCTYPE html> (not 404) # Open in browser $ open http://localhost:3001
Build before testing. express.static serves files from client/dist — that directory doesn't exist until you run npm run build. Forgetting this produces a silent blank page.
If /books returns JSON instead of HTML, your catch-all is matching the API routes. Confirm that /api/books returns JSON and /books returns HTML.
Check the Network tab in browser DevTools as you navigate. All API calls should go to /api/... (same origin, no CORS headers needed). If you see requests to localhost:5173, you're still running the Vite dev server.
After a successful local test, commit the changes — including any .env.example updates for the new CLIENT_ORIGIN variable — before deploying.

Prompt Reflection

Integration bugs are different from component bugs — they cross boundaries between separately generated pieces of code. Reflect on that here.

The context gap:
Your backend prompt and your frontend prompt were written at different times. What information would have been useful to share between them? How would you structure a single prompt that generates a consistent contract for both sides?
Finding the mismatch:
Before testing the integrated app, you read both sides of the contract. Which field name or response shape mismatch did you find? Was it a naming convention issue, a wrapper object, or something else?
Route order bug:
The catch-all route position is a silent bug — the app still starts, but API calls return HTML. What would you see in the browser Network tab that would help you diagnose this without reading the source code?
Shared types value:
The shared/types.ts file catches field name mismatches at compile time. Give a concrete example of a mismatch it would have caught — and a mismatch it would not catch (a runtime bug TypeScript can't see).
