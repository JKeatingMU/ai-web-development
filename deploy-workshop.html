What npm run build Does

Vite transforms your React source — TypeScript, JSX, imports, env vars — into a handful of optimised static files that any web server can serve.

terminal
$ cd client && npm run build vite v5.x building for production... ✓ 42 modules transformed. dist/index.html 0.46 kB dist/assets/index-Bk9mTfgD.js 148.32 kB │ gzip: 48.21 kB dist/assets/index-DiwrgTda.css 2.14 kB │ gzip: 0.62 kB ✓ built in 1.24s # client/dist/ is now ready to be served
client/dist/ structure
client/dist/ ├── index.html ← entry point for all routes └── assets/ ├── index-Bk9m.js ← all JS bundled + minified └── index-Diwg.css ← all CSS bundled + minified
VITE_ variables are baked in at build time. import.meta.env.VITE_API_URL becomes a literal string in the bundle. If your API URL changes after building, you must rebuild.
In production, VITE_API_URL should be empty or omitted — Express serves the API from the same origin, so all /api/... paths resolve without a hostname prefix. Check api.ts: const BASE = import.meta.env.VITE_API_URL ?? ''.
The hashed filenames (e.g. index-Bk9m.js) change on every build — Vite adds a content hash so browsers don't serve stale cached files after a deploy. This is automatic.
Do not commit client/dist/ to Git. Railway builds it from source. Add client/dist to .gitignore. Committing it bloats the repo and causes confusion about which version is deployed.

Pre-Deploy Checklist

Fix these before pushing to Railway. Most deployment failures trace back to one item on this list.

  • 1.gitignore covers secrets: confirm .env is listed. Run git status and verify no .env file appears in the staged or untracked list. A leaked JWT_SECRET or DATABASE_URL is a serious incident.
  • 2.env.example is up to date: every environment variable your server reads must appear in .env.example with a placeholder value. This is your deployment reference — Railway config comes from here.
  • 3package.json start script: Railway runs npm start. Confirm "start": "node server/index.js" exists in the root or server package.json. Missing this produces "no start script found" deploy errors.
  • 4Port is dynamic: const PORT = process.env.PORT || 3001. Railway assigns a random port via the PORT env var. Hardcoding 3001 causes the health check to fail on Railway.
  • 5Build command set: Railway needs to build the React app. Either add a root-level build script ("build": "cd client && npm install && npm run build") or configure it in the Railway dashboard settings.
  • 6No hardcoded localhost URLs: search the codebase for localhost:3001 and localhost:5173 in non-test files. Any that appear in server code or shared types will break in production.

Railway Setup — Step by Step

  • 1Create project: railway.app → New Project → Deploy from GitHub repo. Select your repository. Railway detects Node.js automatically.
  • 2Add PostgreSQL: in the project dashboard → + New → Database → PostgreSQL. Railway provisions a managed database and sets DATABASE_URL in your service's environment automatically.
  • 3Set environment variables: Service → Variables tab. Add all variables from your .env.example: JWT_SECRET, NODE_ENV=production, CLIENT_ORIGIN (your Railway domain — set this after the first deploy).
  • 4Set build + start commands: Settings → Build Command: cd client && npm install && npm run build. Start Command: node server/index.js (or npm start).
  • 5Deploy: push to your main branch — Railway builds and deploys automatically. Watch the build logs for errors.
  • 6Run schema.sql: after the first deploy, connect to the Railway PostgreSQL instance and run your schema. See the next slide for how.
  • 7Set CLIENT_ORIGIN: copy your Railway domain (e.g. https://myapp.up.railway.app) and add it as CLIENT_ORIGIN in Variables. Redeploy.

Running Your Schema on Railway PostgreSQL

Railway's managed database doesn't have your tables yet. Run schema.sql once after the first deploy using either the Railway shell or a local connection via the Railway CLI.

Option A — Railway CLI (recommended)
# Install Railway CLI $ npm install -g @railway/cli # Authenticate $ railway login # Link to your project $ railway link # Run schema against Railway DB # (uses DATABASE_URL from Railway env) $ railway run psql $DATABASE_URL < schema.sql # Verify tables were created $ railway run psql $DATABASE_URL -c "\dt" List of relations Schema │ Name │ Type │ Owner ────────┼──────────┼───────┼─────── public │ books │ table │ ... public │ users │ table │ ...
Option B — Railway dashboard → PostgreSQL → Query
# Paste schema.sql contents into the # Railway dashboard query editor and run
Run once — not on every deploy. schema.sql typically contains CREATE TABLE statements. Running it twice on a database with data will fail or drop data if you used DROP TABLE IF EXISTS. For subsequent changes, use ALTER TABLE migrations.
Use IF NOT EXISTS: write CREATE TABLE IF NOT EXISTS in your schema so re-running is safe in development. Railway's DB is fresh on first deploy so this is mostly a safety net for local resets.
DATABASE_URL format: Railway provides a full PostgreSQL connection string. Your pg Pool picks it up automatically: new Pool({ connectionString: process.env.DATABASE_URL }). No other DB config needed.
After running the schema, test the health endpoint: curl https://your-app.up.railway.app/api/health. If it returns { "ok": true }, the server is up and connected to the database.

Environment Variables in Production

Every secret that lives in your local .env must be set in Railway's dashboard. Never commit secrets to Git.

VariableValue in RailwayNotes
DATABASE_URL Set automatically by Railway PostgreSQL plugin Do not set manually — Railway manages this
JWT_SECRET A long random string (32+ chars) Generate with node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
NODE_ENV production Some packages behave differently in production (logging, error detail)
CLIENT_ORIGIN https://myapp.up.railway.app Set after first deploy when you know the domain
PORT Do not set — Railway provides it Your code reads process.env.PORT || 3001
JWT_SECRET in production must be different from development. If the same secret is used in both environments, a token signed in development is valid in production — a security hole.
After setting variables, redeploy. Railway does not restart your service when env vars change — you must trigger a redeploy manually or push a new commit.

Testing the Live Deployment

Test in layers — API first, then auth, then the full frontend flow. Diagnose from the bottom up.

terminal — replace with your domain
# 1. Health check — server + DB connected $ curl https://myapp.up.railway.app/api/health {"ok":true} # 2. Register a user $ curl -s -X POST \ https://myapp.up.railway.app/auth/register \ -H "Content-Type: application/json" \ -d '{"email":"test@example.com","password":"secret123"}' | jq . {"message":"Created"} # 3. Login — capture the token $ TOKEN=$(curl -s -X POST \ https://myapp.up.railway.app/auth/login \ -H "Content-Type: application/json" \ -d '{"email":"test@example.com","password":"secret123"}' \ | jq -r .token) # 4. Authenticated request $ curl -s \ https://myapp.up.railway.app/api/books \ -H "Authorization: Bearer $TOKEN" | jq . [] # 5. Add a book $ curl -s -X POST \ https://myapp.up.railway.app/api/books \ -H "Authorization: Bearer $TOKEN" \ -H "Content-Type: application/json" \ -d '{"title":"The Pragmatic Programmer","author":"Hunt & Thomas","status":"reading"}' | jq . {"id":1,"title":"The Pragmatic Programmer",...}
Test with curl before the browser. curl removes browser-layer issues (CORS, caching, React Router) — if curl works, the API is correct and any remaining issues are frontend.
If the health check fails: check Railway build logs. The most common causes are a missing start script, a hardcoded port, or a missing dependency that was accidentally in devDependencies.
If login returns 500: JWT_SECRET is probably not set in Railway. Verify in Variables → confirm the key is spelled exactly as process.env.JWT_SECRET reads it in your code.
If the React app loads but API calls fail: open DevTools → Network → look at a failing API request. Check the URL it is calling — if it still says localhost:3001, VITE_API_URL is set in Railway and overriding the empty default.

Common Deploy Failures

SymptomCauseFix
Build fails: "Cannot find module 'express'" express is in devDependencies instead of dependencies Move to dependencies: npm install express --save
Build fails: "No start script found" Railway looks for "start" in package.json and finds nothing Add "start": "node server/index.js" to root package.json
App deploys but returns 502 on every request Server crashes on startup — usually a missing env var or a bad DB connection Check Railway deploy logs; confirm DATABASE_URL and JWT_SECRET are set
Health check passes, API returns 500 Schema not run — tables don't exist yet Run schema.sql against Railway DB via CLI or dashboard query editor
React app loads, all API calls return CORS error CLIENT_ORIGIN not set or set to wrong value Set CLIENT_ORIGIN=https://your-app.up.railway.app and redeploy
API calls go to localhost:3001 from production VITE_API_URL is set in Railway environment to localhost Remove VITE_API_URL from Railway — it should only be set in local .env during development

Build-time vs runtime config:
