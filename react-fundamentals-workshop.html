What is React — and Why Does It Exist?

Traditional HTML + JavaScript updates the page by directly manipulating DOM elements. This works but gets messy fast. React introduces a better mental model: describe what the UI should look like, and let the library figure out what to change.

Components — the UI is split into small, reusable pieces. A button, a card, a form are each their own component. Compose them to build a page.
State — when data changes, React automatically re-renders only the parts of the page that depend on that data. No manual DOM updates.
Declarative — you write what the UI should look like for a given state. React handles the how. This is what AI generates — declarative component trees.
React is not magic — it compiles JSX to JavaScript function calls. When you understand the output, you understand the tool. That is this deck's goal.

Setting Up — Vite + React + TypeScript

We use Vite: a fast build tool that handles JSX compilation, hot module replacement, and bundling. One command scaffolds everything.

Reading What Vite Generated

Before writing a line, understand the files Vite created. AI will reference these constantly.

file structure
my-app/ ├── index.html ← entry point for the browser ├── vite.config.ts ← build config ├── tsconfig.json ← TypeScript settings ├── package.json └── src/ ├── main.tsx ← mounts React into index.html ├── App.tsx ← root component └── App.css
main.tsx — finds the <div id="root"> in index.html and renders your React app into it. You rarely touch this file.
App.tsx — where you start. Everything you build will either live here or be imported here.
.tsx means TypeScript with JSX. Files without JSX use .ts. AI will always use the right extension — now you know why.

JSX — HTML Inside JavaScript

JSX is not HTML. It looks like it, but it compiles to JavaScript function calls. Understanding this explains most AI-generated React patterns.

JSX (what you write)
function Greeting() { return ( <div className="card"> <h1>Hello, world!</h1> <p>Welcome to React.</p> </div> ); }
className not class — class is a reserved word in JavaScript. AI always uses className. If you see class= in JSX it is a bug.
One root element — JSX must return a single parent. AI wraps multiple elements in <div> or an empty fragment <>...</>.
Expressions in { } — any JavaScript expression inside curly braces is evaluated. {2 + 2} renders 4. {name} renders the variable.

Function Components — The Building Block

A React component is just a JavaScript function that returns JSX. When AI generates a component, it is generating one of these — nothing more mysterious.

BookCard.tsx
// A component for one book function BookCard() { return ( <div className="card"> <h2>Clean Code</h2> <p>Robert C. Martin</p> </div> ); } export default BookCard; // Use it in App.tsx like an HTML tag: <BookCard />
Capital letter matters — React distinguishes HTML tags (div, p) from components (BookCard) by the first letter. AI always capitalises component names.
export default — makes the component available to import from other files. AI adds this automatically.
Self-closing — components with no children can be written <BookCard />. This is JSX syntax, not HTML.

Props — Passing Data into Components

A hardcoded component is not very useful. Props let the parent pass data down to the child, making components reusable.

BookCard.tsx — with props
// TypeScript: define the shape of props interface BookCardProps { title: string; author: string; status: string; } function BookCard({ title, author, status }: BookCardProps) { return ( <div className="card"> <h2>{title}</h2> <p>{author} · {status}</p> </div> ); } // Passing props from parent: <BookCard title="Clean Code" author="Martin" status="read" />
Destructuring in the parameter — AI almost always writes ({ title, author }) rather than (props). Both work; destructuring is cleaner.
interface — TypeScript's way of describing the shape of an object. If you pass the wrong prop type, TypeScript tells you before the browser does.
Props flow one way — parent to child only. A child cannot modify its own props. If data needs to go up, you pass a callback function as a prop.

useState — Local Component State

Props carry data in from outside. State is data that lives inside the component and can change over time. When state changes, React re-renders the component automatically.

Counter.tsx
import { useState } from 'react'; function Counter() { // [current value, setter function] const [count, setCount] = useState(0); return ( <div> <p>Count: {count}</p> <button onClick={() => setCount(count + 1)}> Add </button> </div> ); }
useState(0) — the argument is the initial value. AI will use useState('') for strings, useState([]) for arrays, useState(false) for booleans.
Never mutate state directly — count++ will not trigger a re-render. Always call the setter: setCount(count + 1). AI knows this; if you see direct mutation it is a bug.
Array destructuring — [count, setCount] is a convention. The names are yours to choose; the order matters. First = value, second = setter.

Event Handlers — Responding to User Actions

React events are the same browser events you know — click, submit, change — wrapped in React's synthetic event system. AI generates these as arrow functions or references to named handlers.

event handler patterns
// Inline arrow function (simple actions) <button onClick={() => setCount(count + 1)}> Add </button> // Named handler (complex logic) function handleDelete(id: number) { // validation, API call, state update setBooks(books.filter(b => b.id !== id)); } <button onClick={() => handleDelete(book.id)}> Delete </button> // Form submission — always prevent default! function handleSubmit(e: React.FormEvent) { e.preventDefault(); // handle the form }
onClick not onclick — React events use camelCase. onClick, onChange, onSubmit. HTML uses lowercase. AI always uses camelCase in JSX.
e.preventDefault() — without this, form submit triggers a full page reload. AI always includes it on form handlers. Understand why before removing it.
Pass a function reference, not a call: onClick={handleDelete} not onClick={handleDelete()}. The second runs immediately on render.

Rendering Lists — .map() and the key Prop

Real UIs show lists of things. React renders arrays of JSX — so you transform your data array into a JSX array using .map(). This is one of the most common patterns AI generates.

BookList.tsx
const books = [ { id: 1, title: 'Clean Code', author: 'Martin' }, { id: 2, title: 'The Pragmatic', author: 'Hunt' }, ]; function BookList() { return ( <ul> {books.map(book => ( <li key={book.id}> {book.title} — {book.author} </li> ))} </ul> ); }
key is required — React uses key to track which items changed. Use a stable unique ID from your data, never the array index. AI uses key={item.id} — verify this is a real ID, not an index.
.map() returns JSX — whatever you return inside .map() becomes a rendered element. The arrow function body is JSX, not a string.
Each .map() callback must return one root element. AI wraps multiple elements in a fragment <>...</> when needed, adding key to the fragment.

Controlled Inputs — Forms in React

In plain HTML, an input manages its own value. In React, you keep the value in state and sync it with onChange. This is called a controlled input — the standard pattern AI generates for all form fields.

AddBookForm.tsx
function AddBookForm() { const [title, setTitle] = useState(''); const [author, setAuthor] = useState(''); function handleSubmit(e: React.FormEvent) { e.preventDefault(); console.log({ title, author }); setTitle(''); // reset after submit setAuthor(''); } return ( <form onSubmit={handleSubmit}> <input value={title} onChange={e => setTitle(e.target.value)} placeholder="Title" /> <input value={author} onChange={e => setAuthor(e.target.value)} placeholder="Author" /> <button type="submit">Add Book</button> </form> ); }
value + onChange — the pair that makes an input controlled. Without onChange, the input will appear read-only. AI always generates both together.
e.target.value — the current value of the input element. e is the event, target is the DOM element, value is its current text.
Reset by calling setState('') after submit. This clears the input because React drives the displayed value from state.

Conditional Rendering — Show or Hide UI

React renders whatever you return. If a condition is false, return nothing. AI uses three patterns — learn to recognise all of them in generated code.

three patterns
// 1. && operator — render if true {isLoading && <p>Loading…</p>} // 2. Ternary — show one or the other {books.length > 0 ? <BookList books={books} /> : <p>No books yet.</p> } // 3. Early return — simplest for full blocks function Page() { if (error) return <p>Error: {error}</p>; if (isLoading) return <p>Loading…</p>; return <BookList books={books} />; }
0 && ... is a gotcha — if the left side evaluates to 0, React renders the number 0 on screen. Use arr.length > 0 && or !!arr.length && instead. AI sometimes gets this wrong.
AI almost always generates the early return pattern for loading and error states at the top of a component. This is idiomatic React.
You can return null to render nothing. A component that returns null is valid — it hides itself completely.

Prompting AI to Build the Component

A good scaffold prompt names the technology, describes the data shape, lists the features wanted, and asks for explanation of key choices.

✦ Prompt — React BookList scaffold
I'm building a React + TypeScript front end with Vite. I have an Express API at http://localhost:3001/api/books that returns an array of book objects with the shape: { id, title, author, status } where status is one of "to-read", "reading", or "read".

Please generate a BookList component that:
  • Fetches books from the API using useEffect and fetch
  • Shows a loading message while fetching and an error message if it fails
  • Renders each book as a card showing title, author, and a coloured badge for status
  • Accepts an optional onDelete prop (a callback) that shows a Delete button per card
Use a TypeScript interface for the Book type. Explain why you used useEffect here.
What makes this prompt effective: it provides the data shape (so AI generates a matching interface), lists concrete features, and asks for explanation — forcing AI to be deliberate about useEffect rather than just pattern-matching.

Reading What Was Generated — Line by Line

AI generates a working component. Your job is to understand every decision before you run it.

key patterns to find in the output
// 1. Type safety — does this match our API? interface Book { id: number; title: string; author: string; status: string; } // 2. State initialisation — three states const [books, setBooks] = useState<Book[]>([]); const [isLoading, setIsLoading] = useState(true); const [error, setError] = useState<string | null>(null); // 3. useEffect dependency array useEffect(() => { // fetch runs once — [] means "on mount only" }, []); // 4. Early returns before main render if (isLoading) return <p>Loading…</p>; if (error) return <p>{error}</p>;
Three state variables — data, loading, error. AI always generates this trio for async operations. Understand each before removing one.
Empty dependency array [] — useEffect runs once after mount. Without it, the effect runs on every render — infinite fetch loop. Ask AI to explain this if it is not in the output.
string | null — TypeScript union type. Error is either a string message or null (no error). If AI uses any, ask it to use a specific type instead.

Reflect — What Did AI Choose and Why?

AI made decisions on your behalf. The critical question is not just "does it work?" but "do you agree with these choices, and do you understand the trade-offs?"

Fetch vs Axios
AI often uses the native fetch API. Ask: "Why fetch and not axios? When would axios be better?" Understanding the choice makes you a better architect, not just a copy-paste developer.
Error handling depth
Did AI catch network errors? HTTP error status codes? Both? Ask: "What happens if the server returns 401?" If the error state does not catch it, prompt a fix and understand why it was missing.
Component granularity
Did AI generate one large component or split into BookCard + BookList? Ask: "What is the benefit of extracting BookCard into its own file?" There is no single right answer — the discussion is the learning.
The habit to build: for every non-trivial line AI generates, be able to answer — what does this do, why is it here, and what would break if I removed it? If you cannot answer, that is your next prompt.

Component Architecture — Thinking in Trees

A React app is a tree of components. Each node is a component; data flows down via props, events bubble up via callback props. AI generates this tree — you need to read it as a structure, not just code.

State lives at the lowest common ancestor. If both BookList and AddBookForm need the books array, it lives in App — and flows down as props. AI understands this; ask it to explain where it placed state and why.

Reflecting on What AI Built With You

You have now generated a React UI with AI assistance. The reflection questions below are not optional extras — they are the learning. Vibe coding without reflection is just copying.

  • 01Can you explain each useState call? For every piece of state, describe what triggers a change and what re-renders when it changes. If you cannot, that state is not yet understood.
  • 02What would happen if you removed the key prop from your .map()? Try it. Observe the console warning. Understand why React needs it for reconciliation.
  • 03What does AI do differently from what you would have written? This is the most interesting comparison. Every difference is a prompt: "Why did you use X here instead of Y?"
  • 04What is the next thing you do not know how to do? Name it specifically. That becomes your next prompt, your next search, your next step.
