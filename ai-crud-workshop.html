Technology Choices

Why Node.js + Express + PostgreSQL?

Node.js
JavaScript on the server. One language for front and back end. Huge ecosystem (npm). Excellent for I/O-heavy APIs — reading from a database, calling external APIs. Non-blocking I/O means it handles many simultaneous requests while waiting for database responses. The same V8 engine as Chrome — familiar if you already know browser JS. Not ideal for CPU-heavy computation.
Express
Minimal web framework — routes, middleware, request/response handling. Does almost nothing by default, which means you see exactly what is happening. A complete working API is a single file of ~50 lines. Middleware chains let you add logging, auth, or validation before any route handler. The most-used Node.js web framework in production worldwide.
PostgreSQL
Production-grade relational database. Free, open source, battle-tested. Runs on every cloud platform. Full SQL — joins, aggregates, constraints, transactions. Enforces data types and constraints at the database level, so bad data cannot enter even if your application has a bug. The right default choice for nearly every new project.
The alternative path: SQLite (file-based, zero setup) is great for prototyping and learning — no database server to install. But PostgreSQL is what you'll encounter in industry and research infrastructure. We use it here.
Part 1

Prompting an AI to Build This

The quality of what an AI generates depends almost entirely on the quality of what you ask for. Prompt engineering is a learnable skill.

Prompting Strategy

What Makes a Good Scaffold Prompt?

A vague prompt produces vague code. A precise prompt produces code you can actually use. The difference is specificity.

Weak prompt:
"Write me a Node.js REST API for a reading list."

What you get: generic boilerplate, likely outdated patterns, probably uses CommonJS not ES modules, no validation, no error handling, fields you didn't want, fields you needed missing.
Strong prompt includes:
  • ✓ Exact stack + versions (Node, Express, pg)
  • ✓ Module system (ES modules — type: module)
  • ✓ Every field with type and constraints
  • ✓ Every route with its exact behaviour
  • ✓ What files to produce
  • ✓ What to exclude (no auth, no ORM, etc.)
The rule of thumb:

Imagine you are handing the specification to a junior developer. Would they know exactly what to build? If not, your prompt is not specific enough.

An AI coding assistant is not a mind reader. It is a very fast, very capable developer who needs clear requirements.
Prompt 1 — Initial Scaffold

The Opening Prompt

✦ Prompt sent to Claude / ChatGPT / Gemini
I want to build a simple REST API using Node.js, Express, and PostgreSQL (pg package).
The app is a personal reading list tracker. A book has these fields:
  • title (text, required) and author (text, required)
  • genre (text, optional), status ('want-to-read' / 'reading' / 'done', default 'want-to-read')
  • rating (integer 1–5, optional), notes (text, optional), created_at (auto-set)
Please generate these files: package.json (with dependencies), db.js (pg Pool), schema.sql (CREATE TABLE with CHECK constraints), server.js (Express routes), .env.example.

Routes needed: GET /api/health · GET /api/books (with optional ?status= filter) · GET /api/books/:id · POST /api/books · PATCH /api/books/:id (partial update with COALESCE) · DELETE /api/books/:id.

Use ES modules (type: module). Keep it minimal — no auth, no ORM, no extra middleware. Use parameterised queries ($1, $2…) throughout. PATCH should return the updated row (RETURNING *).
Notice: stack, module system, schema, every route, every file, explicit patterns (COALESCE, RETURNING *), and what to exclude — all specified upfront.
Prompt 2 & 3 — Iteration

Follow-up Prompts — Iterating on What You Got

The first prompt gets you 80% of the way. Follow-up prompts refine and extend.

✦ Prompt 2 — Understanding
Can you explain the COALESCE pattern in the PATCH route?
Why use COALESCE($2, title) instead of just $2?
And why do we need RETURNING * at the end?
Always ask why. If you don't understand a pattern the AI generated, ask it to explain. This is how you learn — not just what to write, but why it works.
✦ Prompt 3 — Adding a Feature
Add a GET /api/books/stats route that returns in a single query:
  • total book count
  • count by each status value
  • average rating for 'done' books
Use COUNT(*) FILTER (WHERE ...) rather than multiple queries.
Iterative development: Start with the skeleton, verify it works, then add features one by one. Never ask for everything at once.
Part 2

Reading the Generated Code

Understanding every file and every pattern — so you own the code, not just the output.

The Generated Output

What the AI Produces — Five Files

reading-list-api/ ├── package.json ← project config + dependencies ├── .env.example ← environment variable template ├── schema.sql ← database table definition ├── db.js ← PostgreSQL connection pool └── server.js ← Express app + all routes
Separation of concerns: database config lives in db.js, schema lives in schema.sql, routes live in server.js. Each file has one job.

Key terms: A table stores rows of data with named, typed columns — like a spreadsheet with rules. A schema describes the table structure (columns, types, constraints). SQL (Structured Query Language) is the language for creating and querying databases. psql is PostgreSQL's command-line client for running SQL files.
Note: .env (your actual secrets) is never committed. .env.example (the template) is committed so other developers know what variables they need.
Install and run:
npm install → creates node_modules/
cp .env.example .env → fill in DATABASE_URL
psql $DATABASE_URL < schema.sql → create table
npm run dev → start server
http://localhost:3001/api/health ↗
File: package.json

package.json — Project Manifest

package.json
{ "name": "reading-list-api", "version": "1.0.0", "type": "module", "scripts": { "start": "node server.js", "dev": "node --watch server.js" }, "dependencies": { "dotenv": "^16.4.5", "express": "^4.18.2", "pg": "^8.11.3" } }
  • "type": "module" ES modules — enables import/export syntax. Without this, Node.js uses CommonJS (require()/module.exports). You'll see both in tutorials — always check which style a project uses before mixing them.
  • --watch Auto-restart — built into Node.js since v18. No need for nodemon. Every file save restarts the server.
  • dotenv Loads .env file into process.env. Keeps secrets out of your code.
  • pg The official PostgreSQL client for Node.js. Gives us a connection pool and parameterised queries.
ES modules vs CommonJS — the syntax difference:
// ES modules ("type":"module")
import express from 'express';
export default app;
// CommonJS (Node default)
const express = require('express');
module.exports = app;
File: schema.sql

schema.sql — The Database Table

schema.sql
CREATE TABLE IF NOT EXISTS books ( id SERIAL PRIMARY KEY, title TEXT NOT NULL, author TEXT NOT NULL, genre TEXT, status VARCHAR(15) NOT NULL DEFAULT 'want-to-read' CHECK (status IN ('want-to-read','reading','done')), rating SMALLINT CHECK (rating BETWEEN 1 AND 5), notes TEXT, created_at TIMESTAMPTZ NOT NULL DEFAULT NOW() ); CREATE INDEX IF NOT EXISTS idx_books_status ON books(status);
  • SERIAL Auto-increment integer. Database assigns the id — your app never needs to calculate one.
  • NOT NULL Database-level enforcement. Even if your app has a bug and tries to insert a null title, the database rejects it.
  • CHECK Constraint — the database will reject any row with an invalid status or a rating outside 1–5. Defence in depth.
  • DEFAULT NOW() created_at is set automatically. Your app never passes it — the database handles it.
  • INDEX Speeds up WHERE status = ... queries. Critical for filtered list endpoints on large tables.
File: db.js

db.js — The Database Connection

db.js
import 'dotenv/config'; import pg from 'pg'; const { Pool } = pg; const pool = new Pool({ connectionString: process.env.DATABASE_URL }); export const query = (text, params) => pool.query(text, params);
Connection Pool: a Pool maintains multiple open database connections and reuses them. Opening a new connection for every request is slow — a pool of 10 connections handles hundreds of concurrent requests efficiently.
The query helper: export const query = ... means every route file imports this one function. One place to change if you ever need to swap the database driver.
process.env.DATABASE_URL — the connection string is read from the environment, never hardcoded. On your laptop: from .env. In production: from Railway's environment variables.
File: server.js

server.js — Structure Overview

server.js — skeleton
import 'dotenv/config'; // load .env file import express from 'express'; // web framework import { query } from './db.js'; // our db helper const app = express(); const PORT = process.env.PORT || 3001; app.use(express.json()); // parse JSON request bodies automatically app.get('/api/health', ...); // health check app.get('/api/books', ...); // list all app.get('/api/books/stats', ...); // aggregate stats ← must come before /:id app.get('/api/books/:id', ...); // get one app.post('/api/books', ...); // create app.patch('/api/books/:id', ...);// update app.delete('/api/books/:id', ...); // delete app.listen(PORT, () => console.log(`API running on port ${PORT}`));
Route order matters: /api/books/stats must be defined before /api/books/:id. Express matches routes top-to-bottom — if /:id comes first, the string "stats" would be treated as an id, giving a database error.
File: server.js

The Routes — GET and POST

GET /api/books — list with optional filter
app.get('/api/books', async (req, res) => { const { status } = req.query; const result = status ? await query( 'SELECT * FROM books WHERE status = $1 ORDER BY created_at DESC', [status] ) : await query( 'SELECT * FROM books ORDER BY created_at DESC' ); res.json(result.rows); });
POST /api/books — create
app.post('/api/books', async (req, res) => { const { title, author, genre, status, notes } = req.body; if (!title || !author) { return res.status(400).json( { error: 'title and author required' } ); } const result = await query( `INSERT INTO books (title,author,genre,status,notes) VALUES ($1,$2,$3,$4,$5) RETURNING *`, [title, author, genre ?? null, status ?? 'want-to-read', notes ?? null] ); res.status(201).json(result.rows[0]); });
req.query — URL query string params (?status=reading). req.body — parsed JSON body from the request.
201 Created — correct status for a successful POST that creates a new resource. 200 OK is for reads and updates.
Key Pattern — PATCH route

COALESCE — The Partial Update Pattern

PATCH /api/books/:id — partial update
app.patch('/api/books/:id', async (req, res) => { const { title, author, genre, status, rating, notes } = req.body; const result = await query( `UPDATE books SET title = COALESCE($2, title), rating = COALESCE($6, rating), ... (all fields) WHERE id = $1 RETURNING *`, [req.params.id, title, author, genre, status, rating, notes] ); if (result.rows.length === 0) return res.status(404).json({ error: 'Not found' }); res.json(result.rows[0]); });
COALESCE(A, B) returns A if A is not null, otherwise B.

So COALESCE($2, title) means: "use the new value if one was provided, otherwise keep the existing value."

This is how partial updates work — the client only sends the fields it wants to change.
RETURNING * tells PostgreSQL to send back the updated row after the UPDATE. Without it you'd have to make a second SELECT query to see the result.

404 on empty result — if the id doesn't exist, result.rows is empty and we return 404 rather than silently succeeding.
Key Pattern — Security

Parameterised Queries — Why They Matter

Every query in this app uses $1, $2, ... placeholders. This is not just style — it is the difference between a secure app and one that can be destroyed.

SQL Injection — the wrong way:
// NEVER DO THIS const id = req.params.id; query(`SELECT * FROM books WHERE id = ${id}`);
If a user sends id = "1 OR 1=1" or "1; DROP TABLE books", the injected SQL runs. Your entire database can be read or destroyed.
Parameterised query — the right way:
// Always do this const id = req.params.id; query( 'SELECT * FROM books WHERE id = $1', [id] // passed separately );
The pg driver sends the query and the value separately to PostgreSQL. The value is never interpreted as SQL. Injection is impossible.
SQL injection is the #1 web application vulnerability worldwide (OWASP Top 10). Parameterised queries prevent it completely. Every single database query you ever write should use them.
Bonus Route

The Stats Route — Aggregation in SQL

One query, multiple aggregates. No post-processing in JavaScript needed — let the database do the work.

GET /api/books/stats
app.get('/api/books/stats', async (_req, res) => { const result = await query(` SELECT COUNT(*) AS total, COUNT(*) FILTER (WHERE status = 'want-to-read') AS want_to_read, COUNT(*) FILTER (WHERE status = 'reading') AS reading, COUNT(*) FILTER (WHERE status = 'done') AS done, ROUND(AVG(rating) FILTER (WHERE status = 'done'), 1) AS avg_rating FROM books `); res.json(result.rows[0]); });
FILTER (WHERE ...) — PostgreSQL extension to SQL that applies a condition to an aggregate. Counts only the rows matching the filter, without needing a GROUP BY or a subquery. One round-trip to the database, one result object.

Deployment — Live in 10 Minutes

From a working local API to a public URL. Railway makes this as frictionless as it gets.

Deployment — Railway

Deploying to Railway — Step by Step

  • 1 Push to GitHub — git init, git add ., git commit -m "initial", push to a new repo. Railway deploys from git.
  • 2 Create a Railway project — railway.app → New Project → Deploy from GitHub repo. Select your repository.
  • 3 Add a PostgreSQL plugin — in Railway, click + Add Plugin → PostgreSQL. Railway creates a database and sets DATABASE_URL automatically.
  • 4 Run the schema — in Railway's PostgreSQL panel, open the query console and run the contents of schema.sql.
  • 5 Set the start command — Railway auto-detects Node.js and runs npm start. Your package.json already defines this.
  • 6 Generate a public domain — in Railway, Settings → Domains → Generate Domain. Your API is now live at https://your-app.railway.app.
Why Railway?
Free tier for small projects. No Docker required. Automatic deploys on every git push. Built-in PostgreSQL plugin. Environment variables injected automatically.
What Railway injects automatically:
DATABASE_URL — full PostgreSQL connection string
PORT — the port your app must listen on

This is why process.env.PORT || 3001 is important — on Railway the port is assigned by the platform, not fixed at 3001.
After deploy — test immediately:
curl -s https://your-app.railway.app/api/health | jq .
http://localhost:3001/api/health ↗
Deployment — Environment Variables

The .env Pattern — Local vs Production

Development (your laptop) Production (Railway) .env file on disk Environment variables (never committed to git) set in Railway dashboard DATABASE_URL=postgresql://... DATABASE_URL= ← injected by PostgreSQL plugin PORT=3001 PORT= ← injected by Railway platform process.env.DATABASE_URL process.env.DATABASE_URL ↑ ↑ Same code reads from process.env in both environments. The source of the value changes — the code does not.
The .gitignore rule:
Always add .env to .gitignore. Committing .env to GitHub exposes your database credentials publicly — a serious security incident.
The .env.example rule:
Always commit .env.example — a template showing which variables are needed, with placeholder values. This tells the next developer (or your future self) what to fill in.

The Bigger Picture

What AI Does Well — and Where It Falls Short

AI is excellent at:
  • ✓ Boilerplate and scaffold — the skeleton you'd write the same way every time
  • ✓ Known patterns — parameterised queries, COALESCE, RETURNING *, connection pools
  • ✓ Explaining code it generated — often clearer than documentation
  • ✓ Translating requirements into SQL
  • ✓ Adding features incrementally when the structure is already clear
AI struggles with:
  • ! Your specific business logic — it doesn't know what your app is for
  • ! Edge cases in your data — only you know what weird inputs are possible
  • ! Security decisions — it generates technically correct but sometimes naive auth
  • ! Performance at scale — a pattern that works for 100 rows can destroy a database at 10 million
  • ! Knowing when it's wrong — it will confidently generate incorrect code
Summary

Key Takeaways

  • 1 Specificity in prompts is everything. Stack, module system, every field, every route, what to exclude — spell it all out. Vague prompts produce vague code.
  • 2 Read every line the AI generates. Ask it to explain patterns you don't recognise. You are responsible for the code you deploy — "AI wrote it" is not a defence when it breaks.
  • 3 Always use parameterised queries. $1, $2, ... — no exceptions. SQL injection is still the most common critical web vulnerability.
  • 4 Test every route before deploying. Health → POST → GET → PATCH → DELETE → validate 400/404 cases. curl is your fastest feedback loop.
  • 5 Secrets stay out of git. .env in .gitignore. .env.example committed. process.env everywhere. This pattern is non-negotiable in production.
  • 6 The database enforces your invariants. NOT NULL, CHECK, DEFAULT — database constraints are the last line of defence. Always add them.
