Client and Server

Every web interaction is a conversation between two computers: a client that asks for something and a server that responds.

Client — anything that sends requests. A browser, curl on the terminal, a mobile app, another server.
Server — a program that listens for requests and sends responses. Express is our server framework.
Protocol — HTTP is the agreed language both sides speak. You never write raw HTTP — Express and the browser handle it.

HTTP — The Language of the Web

HTTP (HyperText Transfer Protocol) is the rulebook that defines how clients and servers communicate. It specifies the format of requests and responses, what methods mean, and what status codes to use.

HTTP is stateless — each request is completely independent. The server has no memory of previous requests. This is why JWTs exist: each request must carry its own proof of identity.
HTTP/1.1 (text-based) is what you see in curl output. HTTP/2 and HTTP/3 are faster binary versions, but the semantics — methods, headers, status codes — are identical.
raw HTTP request (simplified)
GET /api/books HTTP/1.1 Host: localhost:3001 Authorization: Bearer eyJhbG... Content-Type: application/json

HTTP Methods — What You're Asking For

The method tells the server what operation to perform. These four cover 95% of web APIs.

MethodMeaningHas Request Body?Typical Success Code
GETRead data — fetch a resource or listNo200 OK
POSTCreate — add a new resourceYes (JSON)201 Created
PATCHUpdate — modify part of a resourceYes (JSON)200 OK
DELETERemove — delete a resourceNo200 OK or 204 No Content
PUT replaces the entire resource (rarely used in practice). PATCH is preferred for partial updates — only send the fields you want to change. The AI-generated API in this course uses PATCH with COALESCE.
Safe methods (GET) should never change data. Idempotent methods (GET, PUT, DELETE) can be called multiple times with the same result. POST is neither — sending it twice creates two records.

HTTP Status Codes — The Server's Reply

Every HTTP response includes a 3-digit status code. The first digit tells you the category.

CodeMeaningWhen you see it
200 OKSuccessSuccessful GET, PATCH, DELETE
201 CreatedResource createdSuccessful POST
400 Bad RequestClient sent bad dataMissing required field, invalid format
401 UnauthorizedAuth failedNo token, wrong password, expired token
403 ForbiddenNot allowedValid token but insufficient permissions
404 Not FoundResource missingWrong id, typo in route
409 ConflictDuplicateEmail already registered
500 Internal Server ErrorServer crashedBug in your code — check the logs
2xx — Success. The request worked. 200 for reads/updates, 201 for creates.
4xx — Client error. You sent something wrong. Fix the request, not the server.
5xx — Server error. The server crashed. Check your terminal logs — there will be a stack trace.

Anatomy of a URL

https://api.example.com:3001/api/books?status=reading&limit=10
Protocol (https) — http or https. Always use https in production. Encrypts data in transit.
Host (api.example.com) — the server's address. In development: localhost:3001. After Railway deploy: your Railway domain.
Path (/api/books) — the route on the server. Express matches this to a route handler: app.get('/api/books', ...).
Query string (?status=reading&limit=10) — optional key-value pairs after ?, separated by &. Read in Express with req.query.status.

What a Request Looks Like

curl — POST /api/books
$ curl -s -X POST http://localhost:3001/api/books \ -H "Authorization: Bearer $TOKEN" \ -H "Content-Type: application/json" \ -d '{"title":"Clean Code","author":"Martin"}'
  • MethodPOST — what operation to perform
  • URL/api/books — which resource
  • Header: AuthorizationBearer token — proves who you are
  • Header: Content-Typeapplication/json — tells server the body is JSON
  • Bodythe JSON data being sent — Express reads this as req.body

JSON — The Language of APIs

JSON — object and array
// JSON object { "id": 1, "title": "Clean Code", "rating": 5, "done": true, "tags": ["cs", "refactoring"], "notes": null } // JSON array [ { "id": 1, "title": "Clean Code" }, { "id": 2, "title": "The Pragmatic Programmer" } ]
  • Stringsalways double quotes — "title" not 'title'
  • Numbersno quotes — 5 not "5"
  • Booleanslowercase — true, false
  • Nulllowercase null — means "no value"
  • No trailing commas{"a":1,"b":2} not {"a":1,"b":2,}
  • No commentsJSON cannot contain // or /* */
JSON is not JavaScript — it's a text format that looks like JS object syntax. JSON.parse(text) converts text → JS object. JSON.stringify(obj) converts JS object → text. Express calls these automatically.

REST — A Style, Not a Protocol

REST (REpresentational State Transfer) is a set of conventions for how to structure HTTP APIs. An API that follows them is called RESTful.

  • Resources are nounsURLs identify things, not actions. /books not /getBooks or /fetchAllBooks.
  • Methods have meaningGET reads, POST creates, PATCH updates, DELETE removes. Use the right method.
  • StatelessEach request contains everything the server needs. No sessions stored on the server — hence JWT.
  • Standard responsesJSON data + appropriate status codes. 201 for creates, 404 when missing.
Why this matters: When AI generates an API, it follows REST conventions. Understanding REST lets you spot when the AI broke them — e.g., a DELETE route that also creates a record, or a GET route that modifies data.
Not every API is RESTful. GraphQL, gRPC, and WebSockets are different styles. REST is by far the most common and the default that AI generates.

RESTful Routes — The Pattern

REST APIs follow a predictable URL structure. Once you know the pattern, you can guess any API's routes.

MethodURLActionExpress handler
GET/api/booksList all books (with optional filter)app.get('/api/books', ...)
GET/api/books/:idGet one book by idapp.get('/api/books/:id', ...)
POST/api/booksCreate a new bookapp.post('/api/books', ...)
PATCH/api/books/:idUpdate fields of one bookapp.patch('/api/books/:id', ...)
DELETE/api/books/:idDelete one bookapp.delete('/api/books/:id', ...)
/api/books/:id — the :id is a route parameter. Express puts it in req.params.id. The /api/ prefix is a convention that distinguishes API routes from HTML page routes.
Nested resources follow the same pattern: GET /api/books/:id/sessions lists sessions for one book. POST /api/books/:id/sessions creates a new session for that book.

DNS — Domain Names to IP Addresses

localhost always resolves to 127.0.0.1 — your own machine. No DNS lookup needed. This is why http://localhost:3001 works without internet.
Railway assigns a domain like your-app.railway.app. DNS resolves this to Railway's servers, which forward requests to your Express process.
You don't need to configure DNS for this course. Railway handles it automatically when you deploy.

How Express Fits In

  • 1Browser or curl sends an HTTP request — method, URL, headers, optional body
  • 2Express receives it — the app.listen(PORT) call opens a socket waiting for connections
  • 3Middleware runs — express.json() parses the body, authenticate checks the JWT, etc.
  • 4Route handler matches — Express finds the first app.get/post/patch/delete whose path matches the URL
  • 5Your code runs — query the database, apply business logic
  • 6res.json(data) sends the response — Express formats it as HTTP with the right headers and status code
  • 7Client receives the response — browser renders it, curl prints it, your code processes it
Try it: run node server.js in your project folder, then open a new terminal and run curl http://localhost:3001/api/health. You should see a JSON response.

What AI Assumes You Know

When you give an AI a prompt like "Build me a REST API for a reading list", it immediately makes decisions based on this deck's content: which HTTP methods to use for which routes, which status codes to return, how to structure JSON, how to name URLs using REST conventions, and what headers to include. Understanding these concepts lets you verify those decisions — not just accept them.
Questions to ask about AI-generated routes: Does GET /books/:id return 404 when the id doesn't exist? Does POST return 201, not 200? Does PATCH only update the fields I sent? Does DELETE return a meaningful response?
Questions to ask about AI-generated JSON: Are error responses consistent — always { "error": "..." }? Do list endpoints return arrays, not objects? Are field names consistent across routes — id everywhere, not sometimes bookId?
A developer who understands HTTP can spot a bug in AI-generated code before testing it. A developer who just copies and pastes will only find out when something breaks in production.

Key Terms

HTTP
The protocol defining how clients and servers communicate
Client
Anything that sends requests (browser, curl, mobile app)
Server
A program that listens for and responds to HTTP requests
Request
A message from client to server: method + URL + headers + body
Response
A message from server to client: status code + headers + body
Method
GET / POST / PATCH / DELETE — the operation being performed
Status Code
3-digit number indicating success (2xx), client error (4xx), server error (5xx)
URL
Protocol + host + port + path + query string
Route
A path pattern that Express matches: /api/books/:id
JSON
Text format for structured data. All API bodies in this course are JSON.
REST
Convention: resources as nouns, HTTP methods have meaning, stateless, JSON
DNS
Translates domain names to IP addresses. localhost = 127.0.0.1.
