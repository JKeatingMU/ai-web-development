Concepts First

Authentication vs Authorisation

These two words are often confused. They solve different problems and live in different parts of your code.

Authentication
"Who are you?"

Verifying identity. The user proves they are who they claim to be — typically with a password, a token, or a biometric.

Examples: logging in with email + password, OAuth with Google, a hardware security key.

In our app: POST /auth/login — verify password, issue a JWT.

Authorisation
"What are you allowed to do?"

Determining what an authenticated identity is permitted to access or modify. You can be logged in but not permitted to do everything.

Examples: admin vs regular user, read-only vs read-write, your books vs other users' books.

In our app: future work — for now, any authenticated user can do everything.

This workshop covers authentication only. Authorisation (roles, permissions, ownership) is the natural next step once auth is working.

Part 1

Understanding JWT

Before writing a line of code — understand exactly what a JWT is, what it contains, and why it can be trusted.

JWT Anatomy

A JWT is Three Base64 Strings Joined by Dots

Every JWT looks like this — three sections, each separately encoded, joined by .

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOjEsImVtYWlsIjoidXNlckBleGFtcGxlLmNvbSIsImlhdCI6MTcwOTU1MjAwMCwiZXhwIjoxNzA5NjM4NDAwfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c
Header
Algorithm + token type.

Decodes to:
{"alg":"HS256","typ":"JWT"}
Payload
The claims — who you are, when the token expires.

Decodes to:
{"sub":1,"email":"user@example.com","exp":...}
Signature
HMAC of header + payload, signed with the server's JWT_SECRET.

Cannot be faked without the secret.
JWT — The Payload

What Goes Inside — Claims

The payload is a JSON object of claims — statements about the user and the token itself. Standard claim names are short for compactness.

JWT payload (decoded)
{ "sub": 1, // subject — the user's id in your database "email": "user@example.com", // custom claim we added "iat": 1709552000, // issued at — Unix timestamp "exp": 1709638400 // expires at — 24 hours after iat }
⚠ The payload is NOT encrypted
It is only Base64-encoded — anyone can decode it and read it. Never put passwords, credit card numbers, or secrets in a JWT payload. Only put data that is safe to be public: user id, email, role.
The signature IS tamper-proof
If anyone modifies the payload (e.g., changes sub: 1 to sub: 99), the signature no longer matches. jwt.verify() throws an error and the request is rejected.
JWT — The Full Flow

How JWT Authentication Works End-to-End

Registration (once) POST /auth/register { email, password } → Server hashes password with bcrypt → stores in users table → Returns { id, email, created_at } ← no token yet Login POST /auth/login { email, password } → Server fetches user from DB, runs bcrypt.compare() → If valid: jwt.sign({ sub: id, email }, JWT_SECRET, { expiresIn: '24h' }) → Returns { token: "eyJ..." } ← client stores this token Every protected request GET /api/books Authorization: Bearer eyJ... → Middleware calls jwt.verify(token, JWT_SECRET) → If valid: attaches payload to req.user, calls next() → Route handler runs ← response returned The server never stores the token. No DB lookup on every request. The secret is the only thing that must be kept safe.

Two new packages:
  • bcrypt — hashes passwords before storing
  • One-way: verify a password against a hash, but cannot reverse
  • jsonwebtoken — signs and verifies JWTs using your secret
The middleware pattern:
  • Runs between receiving a request and the route handler
  • Verifies the JWT and attaches the user to req.user
  • Calls next() to proceed, or returns 401 to reject
File: schema.sql

The Users Table

schema.sql — users table
CREATE TABLE IF NOT EXISTS users ( id SERIAL PRIMARY KEY, email TEXT UNIQUE NOT NULL, password_hash TEXT NOT NULL, created_at TIMESTAMPTZ NOT NULL DEFAULT NOW() );
  • UNIQUE Unique constraint on email — the database rejects duplicate registrations with error code 23505. Our register route catches this and returns 409 Conflict.
  • password_hash Never store passwords. We store only the bcrypt hash. Even if the database is compromised, an attacker cannot recover the original passwords.
  • NOT password The column is deliberately named password_hash to make it obvious in code reviews that this is a hash, not a plaintext password.
Run the migration: psql $DATABASE_URL -c "CREATE TABLE IF NOT EXISTS users (id SERIAL PRIMARY KEY, email TEXT UNIQUE NOT NULL, password_hash TEXT NOT NULL, created_at TIMESTAMPTZ NOT NULL DEFAULT NOW());"
Concept: bcrypt

bcrypt — Why We Hash Passwords

How bcrypt works
import bcrypt from 'bcrypt'; // On registration — hash once, store forever const hash = await bcrypt.hash('my-password', 12); // → "$2b$12$X9fKh3mN..." (60 characters) // On login — compare, never reverse const valid = await bcrypt.compare('my-password', hash); // → true (correct password) const valid2 = await bcrypt.compare('wrong', hash); // → false (wrong password)
The salt rounds (12):
bcrypt deliberately runs slowly — 2¹² = 4096 iterations. This means an attacker brute-forcing millions of password guesses per second is slowed to a few hundred per second. Higher rounds = more security, but slower login.
Salted by default:
bcrypt automatically generates a random salt and embeds it in the hash. Two users with the same password will have different hashes. You never handle the salt explicitly.
bcrypt is one-way. You cannot recover a password from a hash. If a user forgets their password, you must let them reset it — you cannot "look it up".
File: auth.js

The Register Route

auth.js — POST /auth/register
router.post('/register', async (req, res) => { const { email, password } = req.body; // Validate inputs if (!email || !password) return res.status(400).json({ error: 'email and password required' }); if (password.length < 8) return res.status(400).json({ error: 'password must be ≥ 8 characters' }); // Hash the password — never store the plaintext const hash = await bcrypt.hash(password, SALT_ROUNDS); try { const result = await query( `INSERT INTO users (email, password_hash) VALUES ($1, $2) RETURNING id, email, created_at`, [email, hash] ); res.status(201).json(result.rows[0]); } catch (err) { // PostgreSQL unique constraint violation = duplicate email if (err.code === '23505') return res.status(409).json({ error: 'email already registered' }); throw err; } });
  • 400 Bad Request for missing fields or weak password — client error, client should fix it
  • 409 Conflict for duplicate email — the resource already exists
  • err.code 23505 PostgreSQL's error code for UNIQUE constraint violation — we catch it to return a helpful message instead of a 500
  • RETURNING Returns id, email, created_at — but never password_hash
File: auth.js

The Login Route

auth.js — POST /auth/login
router.post('/login', async (req, res) => { const { email, password } = req.body; // Fetch user by email const result = await query( 'SELECT * FROM users WHERE email = $1', [email] ); if (result.rows.length === 0) return res.status(401).json({ error: 'Invalid credentials' }); // Verify password against stored hash const user = result.rows[0]; const valid = await bcrypt.compare(password, user.password_hash); if (!valid) return res.status(401).json({ error: 'Invalid credentials' }); // Sign a JWT — valid for 24 hours const token = jwt.sign( { sub: user.id, email: user.email }, process.env.JWT_SECRET, { expiresIn: '24h' } ); res.json({ token }); });
  • 401 Same error message for "user not found" and "wrong password" — never reveal which one is true, or an attacker can enumerate valid emails
  • jwt.sign Creates the token. Payload: {sub, email}. Secret from env. Expiry: 24h. The library encodes, signs, and base64-encodes automatically.
  • JWT_SECRET Must be a long, random, kept-private string. If an attacker learns it, they can forge tokens for any user.
File: middleware/authenticate.js

The Middleware Function

middleware/authenticate.js
import jwt from 'jsonwebtoken'; export function authenticate(req, res, next) { // 1. Extract token from Authorization header const authHeader = req.headers.authorization; if (!authHeader?.startsWith('Bearer ')) { return res.status(401).json({ error: 'No token provided' }); } // 2. Strip "Bearer " prefix to get the token string const token = authHeader.slice(7); try { // 3. Verify signature + expiry const payload = jwt.verify(token, process.env.JWT_SECRET); // 4. Attach user info to request for route handlers to use req.user = payload; next(); // ← pass control to the route handler } catch (err) { return res.status(401).json({ error: 'Invalid or expired token' }); } }
  • next() The Express middleware signature is always (req, res, next). Calling next() tells Express to proceed to the next handler. Not calling it stops the chain.
  • req.user After verification, we attach the decoded payload to req. Route handlers can then read req.user.sub (the user id) or req.user.email.
  • jwt.verify Throws if the signature is invalid or the token has expired. The catch block returns 401 in both cases.
File: server.js

Wiring It All Together

server.js — changes only
// Add two new imports at the top import authRouter from './auth.js'; import { authenticate } from './middleware/authenticate.js'; // Mount the auth router — no authentication required on these routes app.use('/auth', authRouter); // POST /auth/register, POST /auth/login // Add authenticate as the second argument to every books route app.get('/api/books', authenticate, async (req, res) => { ... }); app.get('/api/books/stats', authenticate, async (req, res) => { ... }); app.get('/api/books/:id', authenticate, async (req, res) => { ... }); app.post('/api/books', authenticate, async (req, res) => { ... }); app.patch('/api/books/:id', authenticate, async (req, res) => { ... }); app.delete('/api/books/:id', authenticate, async (req, res) => { ... });
The middleware pattern: Express route handlers accept (method, path, ...handlers). By inserting authenticate before the async function, Express runs it first. If authenticate calls next(), the async function runs. If it returns 401, the async function never runs.

Testing — Register & Login

Register, Login, Capture the Token

bash — register + login
# Register a new user $ curl -s -X POST http://localhost:3001/auth/register \ -H "Content-Type: application/json" \ -d '{"email":"alice@example.com","password":"correct-horse-battery"}' \ | jq . { "id": 1, "email": "alice@example.com", "created_at": "2026-03-04T..." } # Login and capture the JWT in one step $ TOKEN=$(curl -s -X POST http://localhost:3001/auth/login \ -H "Content-Type: application/json" \ -d '{"email":"alice@example.com","password":"correct-horse-battery"}' \ | jq -r '.token') # Confirm token was captured (first 50 chars) $ echo ${TOKEN:0:50} eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOjE...
The token is stored in $TOKEN for the rest of the shell session. No copy-pasting. Every subsequent request reuses it automatically.
Testing — Using the Token

The Authorization: Bearer Pattern

bash — authenticated requests
# Add a book — note Authorization: Bearer header $ curl -s -X POST http://localhost:3001/api/books \ -H "Authorization: Bearer $TOKEN" \ -H "Content-Type: application/json" \ -d '{"title":"The Pragmatic Programmer","author":"Hunt & Thomas"}' \ | jq {id,title,status}' { "id": 1, "title": "The Pragmatic Programmer", "status": "want-to-read" } # Fetch books $ curl -s http://localhost:3001/api/books \ -H "Authorization: Bearer $TOKEN" \ | jq '.[].title' "The Pragmatic Programmer" # Mark it as done with a rating $ curl -s -X PATCH http://localhost:3001/api/books/1 \ -H "Authorization: Bearer $TOKEN" \ -H "Content-Type: application/json" \ -d '{"status":"done","rating":5}' \ | jq '{status,rating}' { "status": "done", "rating": 5 }

Testing — Inspect the Token

Decoding a JWT — It's Just Base64

The payload is not encrypted — only signed. You can decode and read it without the secret.

bash — decode JWT payload
# A JWT has three parts: header.payload.signature # Extract the payload (part 2) and base64-decode it $ echo $TOKEN | cut -d. -f2 | base64 -d 2>/dev/null | jq . { "sub": 1, "email": "alice@example.com", "iat": 1709552000, "exp": 1709638400 } # Convert exp to a human-readable date $ date -r 1709638400 Wed 5 Mar 2026 10:00:00 GMT ← 24 hours after login
⚠ The payload is visible to anyone who has the token. The token travels over the network (HTTPS encrypts it in transit, but not at rest). Never put anything sensitive in the payload.
But nobody can forge it. Changing "sub": 1 to "sub": 99 would invalidate the signature. jwt.verify() would throw and the request would get 401.
Part 4

The Alternatives

JWT is not always the right choice. Understanding the tradeoffs helps you pick the right tool.

Alternative 1

Session Tokens — Simple and Revokable

How it works:
  • 1 User logs in → server generates a 32-byte random token
  • 2 Token stored in sessions table with user_id + expires_at
  • 3 Client sends token in header: x-session-token: abc123
  • 4 Server does SELECT * FROM sessions WHERE token=$1 AND expires_at > NOW()
Instant revocation: delete the row from the sessions table and the token stops working immediately — no need to wait for expiry.
Advantages over JWT:
  • Can revoke a specific session instantly (logout, security breach)
  • Simpler to reason about — it's just a database lookup
  • Payload is not visible to the client
Disadvantages vs JWT:
  • Database lookup on every request (slower at scale)
  • Doesn't work across multiple servers without a shared DB
Used in: the Vibe Coding Study admin API — admin_sessions table, x-admin-token header.
Alternative 2

API Keys — For Machine-to-Machine

How it works:

  • Admin generates a long random key: sk-abc123...
  • Key (or its hash) stored in the database
  • Client sends it in every request:
    Authorization: Bearer sk-abc123...
    or X-API-Key: sk-abc123...
  • Server looks it up in the DB
Best for: server-to-server communication where a human doesn't log in. A cronjob hitting your API. A CI pipeline deploying your app. A third-party service calling a webhook.
Limitations: keys are usually long-lived (no automatic expiry) — if leaked, they must be manually rotated. Not suitable for end-user authentication.
You've seen this pattern everywhere: Stripe sk_live_..., OpenAI sk-proj-..., Anthropic sk-ant-... — all API keys.
Alternative 3

OAuth 2.0 / OpenID Connect — Delegated Identity

User Your App Google 1. Click "Sign in with Google" ↓ 2. ──redirect──▶ 3. User logs in at Google 4. ◀──code───── 5. Exchange code for tokens ──▶ 6. ◀──id_token── 7. Verify token, extract email 8. Create/find user in your DB 9. Issue your own JWT/session ↑ your app never sees the password
Advantages:
  • You never handle passwords at all
  • Users trust Google/GitHub more than you
  • MFA comes free (if the user has it on Google)
  • No "forgot password" flow to build
Complexity cost: OAuth involves redirect flows, PKCE, token exchange, and handling multiple providers. Libraries like passport.js or lucia-auth do the heavy lifting, but there is still significant setup.
When to use it: consumer-facing apps where users have Google/GitHub accounts. Not worth the complexity for internal tools or research platforms.

Security Notes

JWT Security — What to Get Right

  • ! Keep JWT_SECRET secret and long. At least 32 random characters. Generate with: node -e "console.log(require('crypto').randomBytes(32).toString('hex'))". Never commit it.
  • ! Always verify with jwt.verify(), never jwt.decode(). decode() skips signature verification — it just base64-decodes. Using it for auth is like accepting a passport without checking if it's real.
  • ! Set a short expiry. expiresIn: '24h' is reasonable. Avoid "never expires" tokens — if one is leaked, the damage is unbounded.
  • ~ Use HTTPS in production. JWT tokens in headers are encrypted by TLS — but only in transit. If you use HTTP, tokens can be intercepted.
  • ✓ Never put sensitive data in the payload. It is readable by anyone who has the token. User id and email are fine. Passwords, credit card numbers, admin flags — never.
  • ✓ Same error message for wrong email and wrong password. Returning different messages lets attackers enumerate valid accounts.
Summary

Key Takeaways

  • 1 Authentication = who you are. Authorisation = what you can do. They are separate problems solved separately.
  • 2 Never store plaintext passwords. Always hash with bcrypt using at least 12 salt rounds. You can never reverse a bcrypt hash.
  • 3 A JWT is signed, not encrypted. The payload is readable by anyone. Put only non-sensitive identity data inside (sub, email).
  • 4 Middleware is the right place for auth. One function, added to every protected route as a second argument. Routes stay clean.
  • 5 Return the same error for wrong email and wrong password. Different messages let attackers enumerate valid accounts.
  • 6 JWT_SECRET must be secret, long, and random. It is the only thing protecting every user account in your system.
Going Further

Where to Go From Here

Authorisation — per-user data
Add user_id to the books table. Use req.user.sub in queries so users only see their own books: WHERE user_id = $1. Return 403 if someone tries to modify another user's book.
Refresh tokens
Short-lived access tokens (15 min) + long-lived refresh tokens (30 days, stored in DB). Better security: a leaked access token expires quickly. Clients use the refresh token to get a new access token silently.
Rate limiting
Protect /auth/login from brute-force attacks. Add express-rate-limit: max 5 login attempts per IP per 15 minutes. Prompt: "Add rate limiting to the auth routes using express-rate-limit."
