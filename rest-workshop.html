What is an API?

API = Application Programming Interface — a defined contract for how software talks to software. A Web API is an API that communicates over HTTP.

Think of a restaurant menu: it's a contract — you don't go into the kitchen, you order from the menu. The chef doesn't ask how you want the dish cooked beyond what the menu specifies. The API is the menu.

GitHub API Your code can create repos, open issues, read commit history — all via HTTP requests to GitHub's defined endpoints.
Stripe API Charge cards, create subscriptions, issue refunds — your app sends HTTP requests; Stripe handles the banking.

REST: Six Constraints

REST (Representational State Transfer) is an architectural style defined by 6 constraints — not a standard or a protocol.

  • 1 · Client–serverUI and data storage are separated; each can evolve independently.
  • 2 · StatelessEvery request contains all information needed; server stores no session state.
  • 3 · CacheableResponses can declare themselves cacheable; improves performance at scale.
  • 4 · Uniform interfaceConsistent, predictable URLs and methods — the core of REST.
  • 5 · Layered systemClient can't tell if it's talking to the real server or a proxy/load balancer.
  • 6 · Code on demand(Optional) Server can send executable code (e.g. JavaScript) to the client.
Most 'REST APIs' only implement constraints 1, 2, and 4. That's still fine — REST is a spectrum, not a binary.

The Uniform Interface in Practice

Constraint 4 is the one that matters most day-to-day. It has four sub-constraints:

  • Resource IDs Resources are identified by URI — /api/books/123, not /getBook?id=123.
  • Representations You receive a JSON representation of a book; you send a modified JSON to update it — you never manipulate the resource directly.
  • Self-descriptive Each request/response includes enough information to describe how to process it (Content-Type, status codes, etc.).
  • HATEOAS Hypermedia as the Engine of Application State — responses include links to related actions. Most APIs skip this.
The reason your API uses /api/books (plural noun) and HTTP verbs rather than /api/getBooks or /api/createBook — that's the Uniform Interface constraint.

Resources and URIs

Resource design is the first design decision when building an API.

✓ Good✗ Avoid
GET /api/booksGET /api/getBooks
POST /api/booksPOST /api/createBook
GET /api/books/123GET /api/book?id=123
PATCH /api/books/123POST /api/updateBook/123
DELETE /api/books/123POST /api/deleteBook
GET /api/users/42/booksGET /api/getUserBooks?userId=42
  • NounsNot verbs — the HTTP method IS the verb.
  • PluralCollections use plural: /books, /users.
  • NestedUse nesting for ownership: /users/42/books.
  • LowercaseHyphens not underscores: /reading-sessions.

HTTP Methods in Depth

MethodSafe?Idempotent?Body?Use for
GET ✓ ✓ No Retrieve a resource or collection
POST ✗ ✗ Yes Create a new resource
PUT ✗ ✓ Yes Replace a resource entirely
PATCH ✗ ✗* Yes Partial update (modify specific fields)
DELETE ✗ ✓ Rarely Delete a resource
Safe: doesn't modify server state — can be called freely, cached, prefetched by browsers.
Idempotent: calling it N times has the same effect as calling it once — important for retry logic.
Your Reading List API uses PATCH for updates (not PUT) because it only updates the fields you send — thanks to COALESCE($2, title) in PostgreSQL or $set in MongoDB.

Status Codes: The Full Picture

2xx — Success

200 OKGET, PATCH, DELETE succeeded
201 CreatedPOST created a resource — include Location header with the new URL
204 No ContentSuccess with no body — common for DELETE

3xx — Redirection

301 Moved PermanentlyResource has a new permanent URL
304 Not ModifiedCached response is still valid

4xx — Client Errors

400 Bad RequestMalformed body or missing required field
401 UnauthorizedNot authenticated — no or invalid token
403 ForbiddenAuthenticated but not allowed
404 Not FoundResource doesn't exist
409 ConflictDuplicate unique field (email already registered)
422 Unprocessable EntitySyntactically valid but semantically wrong (failed validation)

5xx — Server Errors

500 Internal Server ErrorUnhandled exception — something crashed
503 Service UnavailableDB connection failed, rate limited, overloaded
The distinction between 401 and 403 matters: 401 = "who are you?", 403 = "I know who you are but no".

HTTP Request

POST /api/books
POST /api/books HTTP/1.1 Host: api.example.com Content-Type: application/json Authorization: Bearer eyJhbGci... { "title": "The Pragmatic Programmer", "author": "Hunt & Thomas" } ↑ method + path + version ↑ headers ↑ blank line separates headers/body ↑ body (JSON)

HTTP Response

201 Created
HTTP/1.1 201 Created Content-Type: application/json Location: /api/books/64f2a3b8 { "id": "64f2a3b8", "title": "The Pragmatic Programmer", "author": "Hunt & Thomas", "status": "unread", "createdAt": "2026-03-08T10:00:00Z" } ↑ status line ↑ headers ↑ body
The Location header on a 201 tells the client where to find the newly created resource — often omitted but technically required by the spec.

Query Strings, Filtering & Pagination

Query strings carry optional parameters — ?key=value&key2=value2

filter + pagination pattern
-- filter by status GET /api/books?status=reading -- first page of 10 GET /api/books?limit=10&offset=0 -- second page GET /api/books?limit=10&offset=10 -- sorted descending GET /api/books?sort=createdAt&order=desc -- response envelope (collection endpoint) { "data": [ ... ], "total": 47, "limit": 10, "offset": 0 }
Never return unlimited results from a collection endpoint — always paginate. Even if you only have 5 records now.

Statelessness in Practice

The most important — and most misunderstood — REST constraint.

What stateless means

  • No sessionThe server stores no session data between requests.
  • Self-containedEvery request must carry its own authentication, context, and intent.
  • StatelessThe server doesn't remember the previous request.

How it's implemented in the course API

  • JWTAuthorization: Bearer <token> carries user identity on every request.
  • No sessionsNo req.session, no server-side session store.
  • ScaleAny server instance can handle any request — horizontal scaling works.

What would break statelessness

  • Server sessionsStoring session data in memory or a DB per login — sticky session problem.
  • "Remember me""Remember what I said last request" — the server doesn't, by design.
Statelessness is why your API can scale to multiple server instances without a sticky session problem. The token IS the state — it travels with every request.
Sessions (like express-session) aren't "wrong" — they're a deliberate trade-off. They're stateful by design. That makes them non-RESTful, but perfectly valid.

Content Negotiation & Headers

Key Request Headers

  • Content-Type: application/jsonTells the server what format the body is in.
  • Accept: application/jsonTells the server what format the client wants back.
  • Authorization: Bearer <token>Authentication credential.
  • Cache-Control: no-cacheSkip the cache — always fetch fresh.

Key Response Headers

  • Content-Type: application/json; charset=utf-8Format of the response body.
  • Location: /api/books/123Where the new resource is (after 201).
  • X-Total-Count: 47Total records for pagination (alternative to envelope).
Express sets headers for you
// Express does this for you: res.status(201).json({ id, title, author }); // Sets: Content-Type: application/json; charset=utf-8 // Status: 201 Created
Always use res.json() not res.send() for API responses — it sets Content-Type correctly and serialises the object.

Error Response Design

Consistent error responses are as important as successful ones.

error response formats
// Detailed validation error { "error": "Validation failed", "details": [ { "field": "title", "message": "Title is required" }, { "field": "author", "message": "Author must be a string" } ] } // Minimal error for simpler cases { "error": "Book not found" } // Express centralised error handler app.use((err, req, res, next) => { console.error(err); res.status(err.status || 500).json({ error: err.message || 'Internal server error' }); });
Never expose stack traces or internal error messages to API clients in production — they reveal your implementation and can be a security risk.

REST vs Alternatives

Brief comparative overview — you'll encounter these in the wild.

ApproachTransportFormatWhen used
REST HTTP JSON/XML Most web APIs — simple, widely understood
GraphQL HTTP JSON Complex data needs; client controls shape of response
gRPC HTTP/2 Protocol Buffers Internal microservices, high performance
WebSocket WS Any Real-time: chat, live dashboards, collaborative tools
tRPC HTTP JSON TypeScript full-stack — type-safe end-to-end
REST is the right default for public APIs and most web applications. Consider GraphQL when clients need to request exactly the fields they want across multiple resources in one call.

Versioning & Documentation

API Versioning — two common approaches

URI versioning (preferred)
/api/v1/books /api/v2/books ← breaking change? bump the version // Header versioning (cleaner URLs, less common) Accept: application/vnd.myapi.v2+json
URI versioning is more common because it's explicit and easy to test in a browser. Use it.

REST is a design language — AI helps you speak it

URI design When starting a new API, describe your domain to AI: "I'm building an app that manages X, Y, Z with these relationships." Ask it to design the URI structure following REST conventions — then push back: "Why plural? Why nested here? What if Z belongs to both X and Y?"
Status codes as communication Your API's status codes are a contract with its clients. When AI generates route handlers, check every res.status() call — are 400s used for client errors? Is 201 returned (not 200) for POST? Is 404 returned when a resource isn't found? These details matter.
Error design Ask AI: "Review my error handling — are all error responses JSON? Do 4xx and 5xx errors have consistent structure? Am I leaking any stack traces?" Error design is where most APIs cut corners.
REST is learnable from reading. Fielding's original dissertation is freely available. The HTTP spec (RFC 9110) is dense but authoritative. AI can summarise both — but reading primary sources deepens understanding.
