React Routing

React Router v6 · URL params · Programmatic navigation · Protected routes

A single-page React app without routing has one URL — the user cannot bookmark a page, share a link, or press the back button. React Router gives each view its own URL while keeping the SPA model. This deck covers the essentials, including how to block unauthenticated users from protected pages.

Client-Side Routing vs Server-Side Routing

Traditional web apps request a new HTML page from the server for every URL. React SPAs load once and swap components in the browser — the server never changes.

Traditional multi-page app

Every link triggers a server round-trip. State is lost. Page flashes white on every navigation.

React SPA with React Router

React Router intercepts navigation, updates the URL, and swaps the matching component — all without touching the server.

Setting Up React Router v6

Install the package, wrap your app in BrowserRouter, then declare your routes. AI generates this correctly almost every time — understand it so you can extend it.

terminal
$ npm install react-router-dom
src/main.tsx
import { BrowserRouter } from 'react-router-dom'; ReactDOM.createRoot(document.getElementById('root')!) .render( <BrowserRouter> <App /> </BrowserRouter> );
src/App.tsx
import { Routes, Route } from 'react-router-dom'; export function App() { return ( <Routes> <Route path="/" element={<HomePage />} /> <Route path="/books" element={<BooksPage />} /> <Route path="/login" element={<LoginPage />} /> <Route path="*" element={<NotFound />} /> </Routes> ); }
BrowserRouter uses the HTML5 History API to keep the UI in sync with the URL. It must wrap everything that uses routing hooks or components.
Routes looks at the current URL and renders the first matching Route. Unlike React Router v5, it no longer requires the exact prop — v6 always matches exactly by default.
path="*" is a catch-all that renders when no other route matches. Always add a 404 route — without it, unknown URLs render nothing at all.
Version check: ask AI to use React Router v6 explicitly. Some AI models still generate v5 syntax (<Switch>, component=, exact) from training data. The two APIs are incompatible.

Navigation — Link and NavLink

Never use <a href="..."> for internal navigation in a React Router app — it triggers a full page reload and discards all React state. Use Link instead.

NavBar.tsx
import { Link, NavLink } from 'react-router-dom'; // Link — basic navigation, no active styling <Link to="/">Home</Link> <Link to="/books">My Books</Link> // NavLink — adds aria-current and active class // when the URL matches its to= prop <NavLink to="/books" className={({ isActive }) => isActive ? 'nav-link active' : 'nav-link' } > My Books </NavLink> // NavLink with style prop — inline active style <NavLink to="/books" style={({ isActive }) => ({ color: isActive ? '#bc8cff' : '#8b949e', fontWeight: isActive ? '600' : '400', })} > My Books </NavLink>
Never <a href> for internal links. It causes a full page reload. Your token in localStorage survives, but all React state is gone — any open modals, unsaved form data, and scroll position are lost.
NavLink receives a function for className and style props. The function receives an isActive boolean — use it to highlight the current route in your navigation bar.
NavLink also adds aria-current="page" automatically when active. This tells screen readers which link is the current page — a free accessibility win.
to="/" is active on every page unless you add end to the NavLink. <NavLink to="/" end> only activates when the URL is exactly /, not on /books.

URL Parameters — useParams

URL parameters let you encode dynamic values in the path — like a book ID. The useParams hook reads them from the current URL inside any component rendered by that route.

App.tsx + BookDetailPage.tsx
// Declare the param with a colon in the path <Route path="/books/:id" element={<BookDetailPage />} /> // ───────────────────────────────────────────── // In BookDetailPage — read the param import { useParams } from 'react-router-dom'; function BookDetailPage() { const { id } = useParams<{ id: string }>(); useEffect(() => { if (!id) return; api.get(`/api/books/${id}`) .then(data => setBook(data)); }, [id]); if (!book) return <p>Loading…</p>; return <h1>{book.title}</h1>; } // Link to a specific book from a list <Link to={`/books/${book.id}`}> {book.title} </Link>
The colon syntax (/books/:id) declares a named placeholder. React Router captures whatever is in that URL segment and makes it available via useParams.
All params are strings. If your API expects a number, convert with parseInt(id!, 10). Forgetting this passes "42" instead of 42 — which may or may not cause a bug depending on your API.
TypeScript generic: useParams<{ id: string }>() tells TypeScript which params to expect. Without the generic, id is typed as string | undefined — which is actually correct, so always check for it before using.
Re-fetch when the param changes by including id in the useEffect dependency array. Without it, navigating from /books/1 to /books/2 reuses the component without re-fetching.

Programmatic Navigation — useNavigate

Link handles navigation triggered by user clicks. useNavigate handles navigation triggered by code — after a form submission, after login, or after an error.

LoginPage.tsx
import { useNavigate } from 'react-router-dom'; function LoginPage() { const navigate = useNavigate(); const [form, setForm] = useState({ email: '', password: '', }); async function handleSubmit(e: FormEvent) { e.preventDefault(); try { const { token } = await api.post( '/auth/login', form ); localStorage.setItem('token', token); // Navigate to /books after successful login navigate('/books'); } catch (err) { setError('Invalid credentials'); } } // ... } // Go back one step in history navigate(-1); // Replace current history entry (no back button) navigate('/books', { replace: true });
navigate('/books') pushes a new entry onto the browser history stack. The user can press Back to return to the previous page.
navigate('/books', { replace: true }) replaces the current entry — useful after login so pressing Back doesn't return to the login page with a valid token already in localStorage.
navigate(-1) is equivalent to pressing the browser's Back button. Use it on a Cancel button in a detail view to return wherever the user came from.
Do not call navigate during render. Only call it inside event handlers or effects. Calling it during render causes an infinite loop as React re-renders after every navigation.

Layout Routes — Outlet

Most apps share a navigation bar, header, or footer across multiple pages. Layout routes let you wrap child routes in a shared component without repeating it in every page.

App.tsx + Layout.tsx
// Layout component — renders shared UI + Outlet import { Outlet } from 'react-router-dom'; function Layout() { return ( <div> <NavBar /> // rendered on every child route <main> <Outlet /> // child route renders here </main> <Footer /> </div> ); } // ───────────────────────────────────────────── // App.tsx — nest routes inside the layout route <Routes> // Layout route — no path of its own <Route element={<Layout />}> <Route path="/" element={<HomePage />} /> <Route path="/books" element={<BooksPage />} /> <Route path="/books/:id" element={<BookDetailPage />} /> </Route> // Login has no layout (no navbar) <Route path="/login" element={<LoginPage />} /> <Route path="*" element={<NotFound />} /> </Routes>
<Outlet /> is a placeholder. When the URL matches a child route, React Router renders that child's element in place of <Outlet>. The Layout component itself stays mounted.
Layout routes have no path. They match any URL and pass through — their only job is to wrap child routes with shared UI.
Login typically has no layout. A login page with a navigation bar showing "My Books" for an unauthenticated user is confusing. Place the login route outside the layout wrapper.
The NavBar stays mounted as you navigate between child routes. This means it doesn't re-render from scratch — animations, dropdowns, and focus are preserved across page transitions.

The Auth Problem

Without protection, any user can navigate directly to /books — they get an empty page or an error when the API rejects the request. A protected route checks for a token and redirects to login if it's missing.

Without protection

  • 1User opens /books directly in a new tab
  • 2React renders <BooksPage /> immediately
  • 3useEffect fires — api.get('/api/books') sends no token
  • 4API returns 401 — api.ts redirects to /login
  • 5User sees a flash of broken UI before being redirected

With ProtectedRoute

  • 1User opens /books directly in a new tab
  • 2ProtectedRoute checks localStorage for a token
  • 3No token found — immediately renders <Navigate to="/login" />
  • 4User is on /login before any API call is made
  • 5No flash of broken UI — smooth redirect
Frontend auth is always advisory. A user can manually set a fake token in localStorage to get past the route guard. The API must still validate every request — the ProtectedRoute is a UX improvement, not a security boundary.

Building a ProtectedRoute Component

A ProtectedRoute is a wrapper component — it either renders its children or redirects to login, depending on whether a token exists.

ProtectedRoute.tsx + App.tsx
import { Navigate, Outlet } from 'react-router-dom'; function ProtectedRoute() { const token = localStorage.getItem('token'); if (!token) { // Replace so Back button doesn't loop return <Navigate to="/login" replace />; } return <Outlet />; // render the child route } // ───────────────────────────────────────────── // App.tsx — wrap protected routes <Routes> // Public routes <Route path="/login" element={<LoginPage />} /> <Route path="/register" element={<RegisterPage />} /> // Layout wrapping protected routes <Route element={<Layout />}> <Route element={<ProtectedRoute />}> <Route path="/" element={<HomePage />} /> <Route path="/books" element={<BooksPage />} /> <Route path="/books/:id" element={<BookDetailPage />} /> </Route> </Route> <Route path="*" element={<NotFound />} /> </Routes>
<Navigate> is a component that performs a redirect when rendered. Using replace means the login page replaces the protected page in history — pressing Back won't try to re-visit /books.
Nesting works left to right: the URL must pass through Layout then ProtectedRoute before reaching the page component. Both are layout-style routes with Outlet.
Token presence ≠ token validity. An expired or revoked token will pass this check. The API call will fail with a 401, and api.ts's global 401 handler will redirect to login at that point.
Logout is just localStorage.removeItem('token') followed by navigate('/login', { replace: true }). No server call is required (JWTs are stateless) — though a token blocklist is better practice for production.

Reading the AI-Generated Router

Before running the app, check these five things. AI gets the route tree right most of the time but makes predictable mistakes in the details.

  • 1Version check: search the generated code for Switch or component=. If you find either, the AI used v5 syntax. Ask it to rewrite using v6 — Routes, Route element=.
  • 2ProtectedRoute uses Navigate, not navigate: <Navigate to="/login" replace /> is the v6 component. navigate('/login') is the hook — it can't be called conditionally at the top level of a component.
  • 3Nesting order: confirm the tree is Layout > ProtectedRoute > page routes. If ProtectedRoute is outside Layout, protected pages won't have the navbar. If Layout is inside ProtectedRoute, the login page may accidentally get a navbar.
  • 4NavLink active styling: className must receive a function ({'{'} isActive {'}'}) => ..., not a plain string. A plain string class never changes on navigation.
  • 5Catch-all route last: path="*" must be the final route. In v6 Routes already picks the most specific match, but putting * first causes confusion and may shadow other routes in complex configurations.

Common Pitfalls

SymptomCauseFix
Refreshing a page gives a 404 from the server The server returns 404 for paths like /books because it has no route for them — only the React app knows about those paths Configure the dev server to fall back to index.html. In Vite this is automatic. In production with Express: app.get('*', (req, res) => res.sendFile(...)) after your API routes
Clicking Back after login returns to the login page navigate('/books') pushes onto history — login is still in the stack Use navigate('/books', { replace: true }) after login so the login page is replaced, not stacked
NavLink never shows as active className is a plain string, not a function; or the path doesn't match exactly Use the function form: className={'({'} isActive {'}'}) => isActive ? 'active' : ''}
URL param change doesn't reload data id is not in the useEffect dependency array Add id to the array: useEffect(() => { ... }, [id])
Protected page briefly flashes before redirect Component renders before the token check completes Return null or a spinner while checking; keep the check synchronous (localStorage) to avoid the flash entirely
