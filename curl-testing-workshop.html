Motivation

Why curl?

curl is a command-line tool that sends HTTP requests and shows responses. It is the universal language of web API testing.

  • ✓ No install friction — ships with macOS, Linux, WSL; zero setup
  • ✓ Scriptable — embed in bash scripts, CI pipelines, Makefiles
  • ✓ Exact — you see precisely what is sent and received, no abstraction
  • ✓ Universal — every API, every language, every server
  • ✓ Agent-readable — AI coding assistants reason about curl natively
The mental model shift:

A browser hides everything. A GUI client (Postman) adds a UI layer. curl forces you to think in raw HTTP — exactly what the server sees.
Real context: Every command in this deck was used to test the Reading List API we built in Parts 1 and 2.
Fundamentals

Anatomy of a curl Command

bash
$ curl -s -X POST -H "Content-Type: application/json" -d '{"key":"value"}' http://localhost:3001/api/endpoint
  • -s Silent mode — suppresses the progress bar, keeps output clean
  • -X POST HTTP method — GET is default; specify POST, PATCH, DELETE explicitly
  • -H Header — add any HTTP header; repeat for multiple headers
  • -d Data / body — the request body; tells curl to POST automatically
  • -o file Output to file — saves response body to disk instead of stdout
  • | jq . Pretty-print — pipe JSON output through jq to format and colour it
Rule of thumb: always use -s and pipe to jq when testing JSON APIs. The signal-to-noise ratio is much better.
Fundamentals

HTTP Methods — What Each One Means

REST APIs use HTTP methods as verbs. Understanding them is essential before testing anything.

Methodcurl flagMeaningReading List API
GET(default)Read — never modifies anythingList books, get one book, stats
POST-X POSTCreate or trigger an actionRegister, login, add a book
PATCH-X PATCHPartially update an existing resourceUpdate status, rating, notes
DELETE-X DELETERemove a resourceDelete a book
GET is safe and idempotent. Run it as many times as you like — no side effects. POST and PATCH change server state — be deliberate.
Part 1

The Testing Strategy

Start simple. Confirm the server is alive. Then work outward — auth first, then data.

Step 1 — Confirm the server is running

The Health Check

Always your first call. No auth needed. Confirms the server is running and responsive.

bash — health check
$ curl -s http://localhost:3001/api/health | jq . { "status": "ok", "ts": "2026-03-04T10:22:14.887Z" }
If this works: Node.js is running, Express is listening on port 3001, database connection is configured. Proceed to auth.
If this fails: curl: (7) Failed to connect — the server isn't running. Start it: npm run dev
Lesson: Never assume the server is running. Verify it explicitly. This one habit saves enormous debugging time.
Part 2

Authentication — Getting a Token

Register once, log in to get a JWT, capture it in a variable. Every protected request carries that token.

Authentication — Step 1

Register a New Account

Registration is a one-time step. It creates a user record with a hashed password — no token is returned at this stage.

bash — register
$ curl -s -X POST http://localhost:3001/auth/register \ -H "Content-Type: application/json" \ -d '{"email":"alice@example.com","password":"correct-horse-battery"}' \ | jq . { "id": 1, "email": "alice@example.com", "created_at": "2026-03-04T10:01:00.000Z" } ← no password_hash in response — intentional # Try to register the same email again $ curl -s -X POST http://localhost:3001/auth/register \ -H "Content-Type: application/json" \ -d '{"email":"alice@example.com","password":"different"}' | jq . { "error": "email already registered" } ← 409 Conflict
Authentication — Step 2

Login and Capture the JWT

Login exchanges your credentials for a JWT. Capture it immediately into a shell variable — never copy-paste tokens by hand.

bash — login + capture token
# Login — capture JWT in one step using $() command substitution $ TOKEN=$(curl -s -X POST http://localhost:3001/auth/login \ -H "Content-Type: application/json" \ -d '{"email":"alice@example.com","password":"correct-horse-battery"}' \ | jq -r '.token') # Confirm token was captured $ echo ${TOKEN:0:60} eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOjEsImVtYWls... # Decode and inspect the payload — it's just base64 $ echo $TOKEN | cut -d. -f2 | base64 -d 2>/dev/null | jq . { "sub": 1, "email": "alice@example.com", "iat": 1709552000, "exp": 1709638400 } ← "exp" is 24h after "iat"
Authentication — Concept

How JWT Authentication Works

Client (curl) Server (Express) 1. POST /auth/login ─────────────────▶ bcrypt.compare(password, hash) { email, password } jwt.sign({ sub, email }, JWT_SECRET) 2. ◀───────────────── { "token": "eyJ..." } 3. GET /api/books Authorization: Bearer eyJ... ────▶ jwt.verify(token, JWT_SECRET) Attach payload to req.user Call next() → run route handler 4. ◀───────────────── [ { book data... } ] Token valid for 24h. No database lookup on steps 3/4 — stateless. Secret key is the only thing that must stay private.
Authorization: Bearer — the standard HTTP header format for token authentication. Bearer signals a token follows (as opposed to Basic which uses base64-encoded username:password).
Part 3

Reading & Writing Data

Full CRUD — every route, every response, every error case.

CRUD — Create

POST — Adding Books

bash — POST /api/books
# Add a book — Authorization header required on all /api/books routes $ curl -s -X POST http://localhost:3001/api/books \ -H "Authorization: Bearer $TOKEN" \ -H "Content-Type: application/json" \ -d '{"title":"The Pragmatic Programmer","author":"Hunt & Thomas","genre":"CS"}' \ | jq . { "id": 1, "title": "The Pragmatic Programmer", "author": "Hunt & Thomas", "genre": "CS", "status": "want-to-read", "rating": null, "notes": null, "created_at": "2026-03-04T10:05:00.000Z" } # Test validation — missing required field $ curl -s -X POST http://localhost:3001/api/books \ -H "Authorization: Bearer $TOKEN" \ -H "Content-Type: application/json" \ -d '{"title":"No Author"}' | jq . { "error": "title and author are required" } ← 400 Bad Request
CRUD — Read

GET — Listing, Filtering, Single Book

bash — GET routes
# List all books $ curl -s http://localhost:3001/api/books \ -H "Authorization: Bearer $TOKEN" \ | jq '.[].title' "The Pragmatic Programmer" "Clean Code" "Designing Data-Intensive Applications" # Filter by status — ?status= is a query parameter $ curl -s "http://localhost:3001/api/books?status=reading" \ -H "Authorization: Bearer $TOKEN" \ | jq '.[].title' "Clean Code" # Get one book by id $ curl -s http://localhost:3001/api/books/1 \ -H "Authorization: Bearer $TOKEN" \ | jq '{id,title,status}' { "id": 1, "title": "The Pragmatic Programmer", "status": "want-to-read" } # 404 — id that doesn't exist $ curl -s http://localhost:3001/api/books/999 \ -H "Authorization: Bearer $TOKEN" | jq . { "error": "Not found" }
CRUD — Update & Delete

PATCH and DELETE

bash — PATCH + DELETE
# Mark a book as done — only send the fields that change (COALESCE handles the rest) $ curl -s -X PATCH http://localhost:3001/api/books/1 \ -H "Authorization: Bearer $TOKEN" \ -H "Content-Type: application/json" \ -d '{"status":"done","rating":5,"notes":"Essential reading."}' \ | jq '{id,title,status,rating}' { "id": 1, "title": "The Pragmatic Programmer", "status": "done", "rating": 5 } ← title and author unchanged — COALESCE preserved them # Delete a book $ curl -s -X DELETE http://localhost:3001/api/books/3 \ -H "Authorization: Bearer $TOKEN" | jq . { "deleted": 3 } # Confirm it's gone $ curl -s http://localhost:3001/api/books/3 \ -H "Authorization: Bearer $TOKEN" | jq . { "error": "Not found" }
CRUD — Aggregates

Reading Statistics

bash — GET /api/books/stats
$ curl -s http://localhost:3001/api/books/stats \ -H "Authorization: Bearer $TOKEN" \ | jq . { "total": "5", "want_to_read": "2", "reading": "2", "done": "1", "avg_rating": "5.0" }
This is a single SQL query using COUNT(*) FILTER (WHERE ...) — the database does all the aggregation, no post-processing in JavaScript. One request to the server, one result object back.
Route ordering matters: /api/books/stats must be defined before /api/books/:id in server.js, otherwise Express treats "stats" as an id parameter and the route never matches.
Debugging

Reading Error Responses

APIs communicate failures through HTTP status codes and JSON error bodies. Use -i to see both.

bash — -i shows response headers
# No token $ curl -s -i http://localhost:3001/api/books HTTP/1.1 401 Unauthorized Content-Type: application/json {"error":"No token provided"} # Malformed/expired token $ curl -s -i http://localhost:3001/api/books \ -H "Authorization: Bearer not-a-real-jwt" HTTP/1.1 401 Unauthorized {"error":"Invalid or expired token"}
StatusMeaningCommon cause
200 OKSuccess—
201 CreatedResource createdSuccessful POST that creates a new record
400 Bad RequestClient sent bad dataMissing required field, validation failure
401 UnauthorizedAuth failedNo token, invalid token, expired token, wrong password
404 Not FoundResource missingWrong id, typo in route
409 ConflictDuplicate resourceEmail already registered
500 Internal Server ErrorServer crashedCheck server console logs
Part 4

Chaining Commands — The Full Workflow

Real testing strings multiple curl calls together into a repeatable script.

Tool: jq

jq — Your JSON Swiss Army Knife

jq is a command-line JSON processor. Pair it with curl constantly.

jq patterns
# Pretty-print everything ... | jq . # Extract one field as raw string (no quotes) ... | jq -r '.token' # Pick specific fields from an object ... | jq '{id,title,status,rating}' # Extract titles from array of books ... | jq '.[].title' # First 3 items of array ... | jq '.[0:3]' # Filter array — only books with rating >= 4 ... | jq '[.[] | select(.rating >= 4)]' # Count items ... | jq 'length'
Install: brew install jq (macOS) · winget install jqlang.jq (Windows) · sudo apt install jq (Linux). One of the most useful tools any backend developer can know. jqplay.org — interactive playground. jq Tutorial ↗
Putting it all together

A Complete Test Script

bash — full Reading List API test
#!/bin/bash # Full CRUD test: health → register → login → create → read → update → delete # 1. Health check curl -s http://localhost:3001/api/health | jq -r '.status' # 2. Register (skip if user already exists) curl -s -X POST http://localhost:3001/auth/register \ -H "Content-Type: application/json" \ -d '{"email":"test@example.com","password":"test-password-1"}' | jq -r '.email // .error' # 3. Login — capture JWT TOKEN=$(curl -s -X POST http://localhost:3001/auth/login \ -H "Content-Type: application/json" \ -d '{"email":"test@example.com","password":"test-password-1"}' | jq -r '.token') # 4. Create a book — capture the id BOOK_ID=$(curl -s -X POST http://localhost:3001/api/books \ -H "Authorization: Bearer $TOKEN" \ -H "Content-Type: application/json" \ -d '{"title":"Clean Code","author":"Robert C. Martin"}' | jq -r '.id') # 5. Mark as done + rate it curl -s -X PATCH http://localhost:3001/api/books/$BOOK_ID \ -H "Authorization: Bearer $TOKEN" \ -H "Content-Type: application/json" \ -d '{"status":"done","rating":4}' | jq '{id,status,rating}' # 6. Check stats curl -s http://localhost:3001/api/books/stats \ -H "Authorization: Bearer $TOKEN" | jq .
Part 5

Why This Still Matters

Even as AI agents take on more development work, understanding what happens at the HTTP level remains essential.

The Bigger Picture

AI Agents Use curl Too

The commands in this deck were not written ahead of time. They were generated by Claude Code during live development of the Vibe Coding Study research platform, executed to verify each change worked.

What the agent does:
  • Writes server code
  • Generates curl commands to test it
  • Reads the JSON response
  • Diagnoses errors from the body + status code
  • Fixes the code and re-tests
What the human still does:
  • Approves or rejects each action
  • Interprets unexpected results
  • Decides when the test is sufficient
  • Understands the intent behind the API
  • Spots what the agent missed
The skill compounds: A developer who understands curl can supervise an AI agent's API testing far more effectively. You know what to look for, what to question, and when something is wrong.
The Bigger Picture

The Development Loop

Write code │ ▼ curl -s /api/health ← Is the server running? │ ▼ TOKEN=$(curl -s -X POST /auth/login) ← Can I authenticate? │ ▼ curl -s -X POST /api/books -H "Authorization: Bearer $TOKEN" ... │ ┌──────────┴──────────────┐ ▼ ▼ { "id": 1, "title": ... } { "error": "..." } │ │ Ship it Read the error → Fix → Repeat

This loop — write, test with curl, read the response, diagnose, fix — is the core of backend development. Fast, precise, and completely independent of any browser or GUI tool.

Summary

Key Takeaways

  • 1 Start with the health check. Always confirm the server is running before testing anything else.
  • 2 Register once, capture the JWT immediately. Use TOKEN=$(curl ... | jq -r '.token'). Never copy-paste tokens by hand.
  • 3 Authorization: Bearer, not x-custom-token. The standard header for JWT authentication is Authorization: Bearer <token>.
  • 4 Use -i when debugging auth. Seeing the HTTP status (401 vs 404 vs 500) tells you immediately where the failure is.
  • 5 Chain your commands. Health → register → login → create → read → update → delete is a script, not seven separate manual steps.
  • 6 This is the language of APIs. Every web framework, cloud service, and AI API speaks HTTP. curl speaks it fluently.
