Git & GitHub

Key concept

Every professional project uses version control. Git lets you save snapshots of your work, undo mistakes, collaborate without overwriting each other's code, and publish to the web. This deck gives you the vocabulary and the daily workflow.

Why Version Control?

Without git, projects look like this:

  • History — Every saved state is accessible forever. No more backup copies — git is the backup.
  • Rollback — Break something? Revert to any previous commit in seconds.
  • Collaboration — Multiple people work on the same codebase without overwriting each other.
  • Blame — git log shows who changed what and when — invaluable for debugging.

Git tracks changes, not files — every commit is a snapshot of your whole project.

Git's Mental Model — Three Zones

Key concept

Working Tree Where you edit files. Changes here are untracked until you git add them.

Key concept

Staging Area A holding area. You choose exactly which changes go into the next commit — file by file if needed.

Key concept

Commit History The permanent record. Each commit has a unique hash, a message, and a pointer to its parent.

Install & First-Time Setup

  • --version — If this prints a version number, git is installed. macOS ships with a basic version via Xcode CLI tools.
  • user.name / email — Attached to every commit you make. Use the same email as your GitHub account so commits link to your profile.
  • defaultBranch — Sets new repos to use main instead of the legacy master default.
  • ~/.gitconfig — All --global settings are stored here. One file, applies to every repo on the machine.

These go in ~/.gitconfig — only do this once per machine. Check with git config --global --list.

Starting a Project

  • git init — Creates a hidden .git/ directory — this is the entire repository. Delete .git/ to un-git a project.
  • git add — Moves changes from the working tree to the staging area. Required before every commit.
  • git commit -m — Takes a snapshot of staged changes. The -m flag sets the message inline.
  • git clone — Downloads an existing repo and sets up origin automatically. The alternative to git init.

The Daily Commit Workflow

  • git status — The command to run first, always. Shows modified, staged, and untracked files at a glance.
  • git diff — Shows exact line-by-line changes in unstaged files. git diff --staged shows staged changes.
  • git add . — Stages everything in the current directory. Convenient but check git status first.

Good commit messages: present-tense imperative. "Add pagination" — not "Added pagination" or "pagination stuff".

Reading History

  • --oneline — Compact view: short hash + message. Fits many commits on screen. Good for a quick audit.
  • --graph --all — ASCII art branch diagram. Shows where branches diverge and merge across the whole repo.
  • git show — Full details of one commit: author, date, message, and the diff. Uses the short hash.
  • HEAD~1 — HEAD means the current commit. HEAD~1 is one commit back, HEAD~2 is two, and so on.

Undoing Things Safely

  • git restore — Discard changes in the working tree. The file goes back to how it was at the last commit. Irreversible for those edits.
  • --staged — Moves a file back out of the staging area without touching the file contents. Safe — your edits are preserved.
  • git revert — The safe undo. Creates a new commit that reverses the named one. History is preserved — teammates see the revert.
Gotcha

Avoid git reset --hard until you understand it — it discards uncommitted work permanently.

Branches

  • Branch — Just a pointer to a commit — creating one is instant and costs almost nothing. Git is built for branching.
  • checkout -b — Create + switch in one step. The modern equivalent is git switch -c — both work.
  • git branch — Lists branches. * marks the current one. -a includes remote branches.
  • -d — Delete a branch that has been merged. Use -D to force-delete an unmerged branch.
Key concept

Convention — main for stable, always-deployable code. Feature branches for everything else. Never commit untested code directly to main.

Merging & Conflicts

  • git merge — Integrates changes from one branch into another. Run it while on the destination branch.
  • Conflict — Happens when both branches changed the same lines. Git cannot decide which version to keep — you must.
  • <<< / === / >>> — HEAD = your current branch. Below ======= = the incoming branch. Delete the markers and keep what you want.

GitHub — Remotes & Pushing

  • remote — A named URL. origin is the conventional name for the primary remote — set it once, use forever.
  • git push -u — The -u flag links your local branch to the remote branch so future git push/git pull need no arguments.
  • git pull — Shorthand for git fetch + git merge. Downloads remote commits and merges them into your local branch.
  • HTTPS vs SSH — HTTPS works anywhere. SSH is more convenient if you set up a key. GitHub's docs cover both.
Tip

Clone = remote + copy in one step. git clone <url> sets up origin automatically.

GitHub Pages — Free Static Hosting

  • GitHub Pages — Serves static files (HTML, CSS, JS) directly from a branch and folder. No server needed.
  • docs/ folder — The /docs option lets you keep source code in root and publishable content in docs/ — ideal for course material.
  • Auto-deploy — Every push to the configured branch triggers a redeploy. No CI setup required for static sites.
  • Custom domain — Add a CNAME file to docs/ and configure your DNS to point to GitHub Pages.

All the decks in this course are plain HTML — no build step. GitHub Pages works out of the box.

Pull Requests

  • Pull Request — A proposal to merge one branch into another. Named "PR" on GitHub, "MR" (Merge Request) on GitLab — same concept.
  • Code review — Teammates comment on specific lines. Discussion happens in the PR thread before anything merges to main.
  • CI checks — GitHub Actions (or other CI) can run tests automatically on every PR. Green checks required before merge.
  • Fork workflow — For open source: fork the repo, work on your fork, open a PR from fork → upstream. Git handles the cross-repo diff.

.gitignore — What Git Should Never Track

  • node_modules/ — Hundreds of megabytes of installed packages. Never commit — regenerate with npm install.
  • .env — Contains database URLs, API keys, JWT secrets. One leaked secret can compromise an entire system.
  • dist/ — Build output — generated from source. Commit the source, not the output.
  • *.log — Glob pattern. The * wildcard matches any filename ending in .log.
  • git rm --cached — Stops tracking a file without deleting it from disk. Use this if you accidentally staged a secret.
Gotcha

Never commit .env — it contains secrets. Add it to .gitignore before your first commit. If a secret reaches a public repo, assume it is compromised — rotate it immediately.

Git is Where AI Collaboration Becomes Visible

Commit messages Describe what you built with AI in natural language. git log becomes a learning diary — a record of every session, every feature, every fix.

Diffs as prompts Paste git diff directly into the AI chat. Ask it to explain what changed, spot bugs, or suggest improvements. The diff is the context.

Branching strategies Ask AI to design a branching strategy for your project — when to branch, naming conventions, merge vs rebase, how many long-lived branches to keep.

Your git history is a record of every AI session. Make it readable.

Every commit message you write in this course is a data point. Future you — or a collaborator — should be able to read git log --oneline and understand exactly what was built, when, and why.

Practical work

Branch, commit, message (practical)
In a practice repo: create a new branch, make a small change, commit with a message explaining *why* (not what), and push. What does git diff show before staging vs after?
  • Your commit message starts with a verb and explains why the change was made, not what changed
  • git diff shows exactly the change you intended and nothing else
  • You can explain the difference between staged and unstaged changes
.gitignore + git status (practical)
Add a .gitignore to a project that excludes: .env, node_modules/, and any OS files (.DS_Store). Verify with git status that those files no longer appear as untracked.
  • git status no longer shows .env, node_modules/, or .DS_Store as untracked
  • The .gitignore file itself is tracked by git (it should not ignore itself)
  • You tested it with the actual files present in the directory, not just empty patterns
Accidental commit (reflect)
What would you do if you accidentally committed a secret key? Walk through the exact git commands you would use, and explain why a simple git rm isn't sufficient.
  • You mentioned git revert or git reset and know which is safer on a shared branch
  • You explained why git rm --cached alone is insufficient (the commit history still contains the secret)
  • You noted that removing from history requires a tool like git filter-repo or BFG Repo-Cleaner
