Research Agent: Book Recommendations

Goal: given a topic, recommend books not already in the reading list. The agent uses Claude's training knowledge as its "search" and the API to check for duplicates.

Research Agent — System Prompt

You are a book recommendation assistant. The user will give you a topic and optional genre. Your task: 1. Call list_books to get the current reading list. 2. Generate 5 book recommendations relevant to the topic from your training knowledge. 3. For each recommendation, check whether it already appears in the list (by title). 4. Return only books NOT already in the list. Include: title, author, year, and one sentence explaining why it fits the topic. Respond in plain text, not JSON.

Why the agent checks the list before recommending: without this step, it will recommend books already in the list — duplicates. The explicit instruction makes the deduplication step a required reasoning step, not a UI concern.

Research Agent: What to Watch For

It works well when

  • ✓ — The topic is specific — "distributed systems databases" gives better recommendations than "books"
  • ✓ — The system prompt requires checking the list first — prevents most duplicates
  • ✓ — The output format is constrained — plain text with a standard structure

Extension: Add an add_books tool and a second step — "Would you like me to add any of these to your list?" — with a human approval before the POST.

Common failure modes

  • ! — Hallucinated books: Claude may invent plausible-sounding titles. Mitigate: ask for well-known books (publication year before 2022), not obscure ones.
  • ! — Duplicate check misses: "DDIA" vs "Designing Data-Intensive Applications" — fuzzy matching in the system prompt helps: "check by both full title and common abbreviations".
  • ! — No list_books call: agent skips the first step. Fix: restate it as a constraint: "You MUST call list_books before generating recommendations."

Summarise & Tag: Batch Processing

Goal: for each book without a summary, generate a one-sentence description and assign a category. Run on a schedule — any book added since the last run gets processed.

Basic LLM Chain vs AI Agent Node: this pipeline does not need tools or a loop — the LLM gets a book title and returns a summary. Use Basic LLM Chain here, not the full AI Agent node. Simpler, faster, cheaper.

The IF node filters to books where notes is empty or null — idempotent by design. Run the workflow 100 times; only unprocessed books get an API call. Books already summarised are skipped.

Summarise & Tag: The Prompt and Output

Basic LLM Chain — Prompt

Book title: {{ $json.title }} Author: {{ $json.author }} Year: {{ $json.year }} Return JSON only — no other text: {"summary": "...", "category": "..."} Summary: one sentence describing what the book covers. Category: exactly one of [Computer Science, Systems, Programming, Career, Mathematics, Other].

JSON-only output is critical here. Without it, the LLM may wrap its answer in prose, breaking the downstream Code node that parses it.

Code node: parse + validate output

const raw = $json.text;  // LLM output
let parsed;
try {
  parsed = JSON.parse(raw);
} catch(e) {
  // Strip markdown code fences if present
  const m = raw.match(/\{[\s\S]*\}/);
  parsed = m ? JSON.parse(m[0]) : null;
}

if (!parsed?.summary || !parsed?.category) {
  throw new Error('Invalid LLM output');
}

return [{ json: {
  ...($input.first().json),
  notes: `${parsed.category}: ${parsed.summary}`
}}];

Monitor & Notify: Condition + Alert

Goal: run daily and alert the user if any book has been in "reading" status for more than 30 days without progress. Forces a habit check — are you still actually reading that?

// Age Check — Code node
const book = $json;
const updated = new Date(book.updated_at);
const daysAgo = (Date.now() - updated)
  / (1000 * 60 * 60 * 24);
return [{ json: { ...book,
  days_in_reading: Math.floor(daysAgo)
}}];

IF node condition: {{ $json.days_in_reading }} greater than 30. Only stale books pass through. The Aggregate collects them and formats a digest. If no books are stale, the IF node's false branch goes to a No-op — no email is sent.

Connecting Pieces: Chaining Agents & Deciding When to Stop

When one agent's output becomes another's input — and when to hand control to a human.

Chaining Agents

Sometimes the output of one agent becomes the prompt for another. This is multi-agent chaining — not orchestration (which uses an explicit orchestrator node), but sequential specialisation.

Agent 1 — Researcher
  Input:  user query ("recommend CS books on distributed systems")
  Output: list of 5 book recommendations with title, author, year
                     ↓
Set node — format Agent 1's output as a prompt string:
  "Review these book recommendations and rank them by accessibility
   for a first-year CS student: {{ $json.recommendations }}"
                     ↓
Agent 2 — Reviewer
  Input:  formatted prompt from Set node
  Output: ranked list with brief justification per book

The key is the Set node between agents. It transforms Agent 1's output JSON into a natural-language prompt that Agent 2 can reason over. The Set node is the handoff point — it explicitly controls what context the second agent receives.

Keep chain length short. Each agent adds latency and cost. Two agents chained is often the practical maximum before the compounding error rate becomes a problem.

When to Stop and Ask a Human

Every agentic workflow has a decision point: at what stage does the agent's confidence justify acting autonomously, and when must it pause for human input?

Action typeAgent autonomy appropriate?Pattern
Read-only: list books, get statsYesFull autonomy — no gate needed
Low-stakes write: add a notes fieldUsuallyLog the action; allow undo via PATCH
Status update: mark a book as readMaybeConfirm with the user before PATCH if unsure of the ID
External communication: send emailNoAlways require human approval — Wait node + approval link
Irreversible: DELETENeverHard gate — human must explicitly trigger, not approve

The rule: reversibility determines autonomy. The easier it is to undo an action, the less supervision it needs. The moment an action becomes hard to reverse, add a gate.

Testing Strategy for Agents

Agents are harder to test than deterministic code because the LLM's reasoning varies. Structure your testing to catch the categories of failure, not every possible input.

  • 1 — Happy path first: the canonical input the system was designed for. Does the agent call the right tools in the right order and return a correct answer?
  • 2 — Tool failure: deliberately break a tool (wrong URL, missing auth). Does the agent handle the error gracefully, or does it loop? Does it report the failure clearly?
  • 3 — Ambiguous input: give the agent an under-specified query ("add that book"). Does it ask for clarification or make something up?
  • 4 — Out-of-scope input: ask the agent to do something outside its tools ("book me a flight"). Does the system prompt constraint apply correctly?
  • 5 — Boundary conditions: empty reading list, 200-book list, book with no author. These stress the data assumptions baked into your prompts and tool descriptions.

Practical work

Build the Summarise & Tag pipeline (practical)
Build the complete Summarise & Tag workflow. Trigger on a schedule (or manual run). Fetch all books, split out, filter to books with no notes, call Basic LLM Chain to generate summary and category, parse the JSON output in a Code node, PATCH each book's notes field. Run twice — confirm idempotency (second run makes no API calls for already-tagged books).
  • The IF node filters correctly — books with existing notes are skipped
  • The Code node handles malformed LLM output (markdown-wrapped JSON) without crashing
  • Running the workflow twice produces no duplicate PATCH calls
Build the Monitor & Notify workflow (practical)
Build the Monitor & Notify workflow. Filter to books with status="reading". Compute days since last update in a Code node. Use an IF node to select books where days > 30. Aggregate the stale books. Output a formatted alert (console log, email, or Slack — your choice). Test with a book you manually set updated_at to an old date via psql.
  • The Code node correctly computes days since updated_at as a number
  • The IF node threshold is configurable (not hardcoded deep in a Code node)
  • If no books are stale, the workflow completes without sending an alert
Reversibility audit (reflect)
Review all three workflows you built in E5. For each action node that writes data (PATCH, POST, email, Slack): classify it as reversible, partially reversible, or irreversible. For each irreversible action, describe whether you added a gate and why or why not.
  • You correctly classified each write action by reversibility
  • For at least one irreversible action, you described the gate (or explained why one is not needed in this specific context)
  • Your reasoning is consistent with the principle from slide 10
