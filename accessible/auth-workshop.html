Authentication vs Authorisation

These two words are often confused. They solve different problems and live in different parts of your code.

Authentication "Who are you?"

Verifying identity. The user proves they are who they claim to be — typically with a password, a token, or a biometric.

Examples: logging in with email + password, OAuth with Google, a hardware security key.

In our app: POST /auth/login — verify password, issue a JWT.

Authorisation "What are you allowed to do?"

Determining what an authenticated identity is permitted to access or modify. You can be logged in but not permitted to do everything.

Examples: admin vs regular user, read-only vs read-write, your books vs other users' books.

In our app: future work — for now, any authenticated user can do everything.

This workshop covers authentication only. Authorisation (roles, permissions, ownership) is the natural next step once auth is working.

Part 1: Understanding JWT

Before writing a line of code — understand exactly what a JWT is, what it contains, and why it can be trusted.

A JWT is Three Base64 Strings Joined by Dots

Every JWT looks like this — three sections, each separately encoded, joined by .

eyJhbGciOiJIUzI1NiIsInR5cCI6IkpXVCJ9.eyJzdWIiOjEsImVtYWlsIjoidXNlckBleGFtcGxlLmNvbSIsImlhdCI6MTcwOTU1MjAwMCwiZXhwIjoxNzA5NjM4NDAwfQ.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

Header Algorithm + token type. Decodes to: {"alg":"HS256","typ":"JWT"}

Payload The claims — who you are, when the token expires. Decodes to: {"sub":1,"email":"user@example.com","exp":...}

Signature HMAC of header + payload, signed with the server's JWT_SECRET. Cannot be faked without the secret.

What Goes Inside — Claims

The payload is a JSON object of claims — statements about the user and the token itself. Standard claim names are short for compactness.

Gotcha

⚠ The payload is NOT encrypted It is only Base64-encoded — anyone can decode it and read it. Never put passwords, credit card numbers, or secrets in a JWT payload. Only put data that is safe to be public: user id, email, role.

Key concept

The signature IS tamper-proof If anyone modifies the payload (e.g., changes sub: 1 to sub: 99 ), the signature no longer matches. jwt.verify() throws an error and the request is rejected.

How JWT Authentication Works End-to-End

Registration (once)
  POST /auth/register { email, password }
  → Server hashes password with bcrypt → stores in users table
  → Returns { id, email, created_at }       ← no token yet

Login
  POST /auth/login { email, password }
  → Server fetches user from DB, runs bcrypt.compare()
  → If valid: jwt.sign({ sub: id, email }, JWT_SECRET, { expiresIn: '24h' })
  → Returns { token: "eyJ..." }             ← client stores this token

Every protected request
  GET /api/books
  Authorization: Bearer eyJ...
  → Middleware calls jwt.verify(token, JWT_SECRET)
  → If valid: attaches payload to req.user, calls next()
  → Route handler runs                      ← response returned

  The server never stores the token. No DB lookup on every request.
  The secret is the only thing that must be kept safe.

Two new packages:

  • bcrypt — hashes passwords before storing
  • One-way: verify a password against a hash, but cannot reverse
  • jsonwebtoken — signs and verifies JWTs using your secret

The middleware pattern:

  • Runs between receiving a request and the route handler
  • Verifies the JWT and attaches the user to req.user
  • Calls next() to proceed, or returns 401 to reject

The Users Table

  • UNIQUE — Unique constraint on email — the database rejects duplicate registrations with error code 23505. Our register route catches this and returns 409 Conflict.
  • password_hash — Never store passwords. We store only the bcrypt hash. Even if the database is compromised, an attacker cannot recover the original passwords.
  • NOT password — The column is deliberately named password_hash to make it obvious in code reviews that this is a hash, not a plaintext password.
Warning

Run the migration: psql $DATABASE_URL -c "CREATE TABLE IF NOT EXISTS users (id SERIAL PRIMARY KEY, email TEXT UNIQUE NOT NULL, password_hash TEXT NOT NULL, created_at TIMESTAMPTZ NOT NULL DEFAULT NOW());"

bcrypt — Why We Hash Passwords

Key concept

The salt rounds (12): bcrypt deliberately runs slowly — 2¹² = 4096 iterations. This means an attacker brute-forcing millions of password guesses per second is slowed to a few hundred per second. Higher rounds = more security, but slower login.

Salted by default: bcrypt automatically generates a random salt and embeds it in the hash. Two users with the same password will have different hashes. You never handle the salt explicitly.

Gotcha

bcrypt is one-way. You cannot recover a password from a hash. If a user forgets their password, you must let them reset it — you cannot "look it up".

The Register Route

  • 400 — Bad Request for missing fields or weak password — client error, client should fix it
  • 409 — Conflict for duplicate email — the resource already exists
  • err.code 23505 — PostgreSQL's error code for UNIQUE constraint violation — we catch it to return a helpful message instead of a 500
  • RETURNING — Returns id, email, created_at — but never password_hash

The Login Route

  • 401 — Same error message for "user not found" and "wrong password" — never reveal which one is true, or an attacker can enumerate valid emails
  • jwt.sign — Creates the token. Payload: {sub, email}. Secret from env. Expiry: 24h. The library encodes, signs, and base64-encodes automatically.
  • JWT_SECRET — Must be a long, random, kept-private string. If an attacker learns it, they can forge tokens for any user.

The Middleware Function

  • next() — The Express middleware signature is always (req, res, next). Calling next() tells Express to proceed to the next handler. Not calling it stops the chain.
  • req.user — After verification, we attach the decoded payload to req. Route handlers can then read req.user.sub (the user id) or req.user.email.
  • jwt.verify — Throws if the signature is invalid or the token has expired. The catch block returns 401 in both cases.

Wiring It All Together

Tip

The middleware pattern: Express route handlers accept (method, path, ...handlers). By inserting authenticate before the async function, Express runs it first. If authenticate calls next(), the async function runs. If it returns 401, the async function never runs.

Part 4: The Alternatives

JWT is not always the right choice. Understanding the tradeoffs helps you pick the right tool.

Session Tokens — Simple and Revokable

How it works:

  1. User logs in → server generates a 32-byte random token
  2. Token stored in sessions table with user_id + expires_at
  3. Client sends token in header: x-session-token: abc123
  4. Server does SELECT * FROM sessions WHERE token=$1 AND expires_at > NOW()

Instant revocation: delete the row from the sessions table and the token stops working immediately — no need to wait for expiry.

Advantages over JWT:

  • Can revoke a specific session instantly (logout, security breach)
  • Simpler to reason about — it's just a database lookup
  • Payload is not visible to the client

Disadvantages vs JWT:

  • Database lookup on every request (slower at scale)
  • Doesn't work across multiple servers without a shared DB

Used in: the Vibe Coding Study admin API — admin_sessions table, x-admin-token header.

API Keys — For Machine-to-Machine

How it works:

  • Admin generates a long random key: sk-abc123...
  • Key (or its hash) stored in the database
  • Client sends it in every request: Authorization: Bearer sk-abc123... or X-API-Key: sk-abc123...
  • Server looks it up in the DB

Best for: server-to-server communication where a human doesn't log in. A cronjob hitting your API. A CI pipeline deploying your app. A third-party service calling a webhook.

Limitations: keys are usually long-lived (no automatic expiry) — if leaked, they must be manually rotated. Not suitable for end-user authentication.

You've seen this pattern everywhere: Stripe sk_live_..., OpenAI sk-proj-..., Anthropic sk-ant-... — all API keys.

OAuth 2.0 / OpenID Connect — Delegated Identity

User            Your App           Google

  1. Click "Sign in with Google"
         ↓
  2.                ──redirect──▶
  3.                             User logs in at Google
  4.                ◀──code─────
  5. Exchange code for tokens ──▶
  6.                ◀──id_token──
  7. Verify token, extract email
  8. Create/find user in your DB
  9. Issue your own JWT/session
  ↑ your app never sees the password

Advantages:

  • You never handle passwords at all
  • Users trust Google/GitHub more than you
  • MFA comes free (if the user has it on Google)
  • No "forgot password" flow to build

Complexity cost: OAuth involves redirect flows, PKCE, token exchange, and handling multiple providers. Libraries like passport.js or lucia-auth do the heavy lifting, but there is still significant setup.

When to use it: consumer-facing apps where users have Google/GitHub accounts. Not worth the complexity for internal tools or research platforms.

Practical rule: JWT for new APIs where scalability matters. Session tokens if you need instant revocation or are building something simple. OAuth when your users are consumers who already have Google/GitHub. API keys for machine-to-machine only.

JWT Security — What to Get Right

  • ! — Keep JWT_SECRET secret and long. At least 32 random characters. Generate with: node -e "console.log(require('crypto').randomBytes(32).toString('hex'))". Never commit it.
  • ! — Always verify with jwt.verify(), never jwt.decode(). decode() skips signature verification — it just base64-decodes. Using it for auth is like accepting a passport without checking if it's real.
  • ! — Set a short expiry. expiresIn: '24h' is reasonable. Avoid "never expires" tokens — if one is leaked, the damage is unbounded.
  • ~ — Use HTTPS in production. JWT tokens in headers are encrypted by TLS — but only in transit. If you use HTTP, tokens can be intercepted.
  • ✓ — Never put sensitive data in the payload. It is readable by anyone who has the token. User id and email are fine. Passwords, credit card numbers, admin flags — never.
  • ✓ — Same error message for wrong email and wrong password. Returning different messages lets attackers enumerate valid accounts.

Key Takeaways

  1. Authentication = who you are. Authorisation = what you can do. They are separate problems solved separately.
  2. Never store plaintext passwords. Always hash with bcrypt using at least 12 salt rounds. You can never reverse a bcrypt hash.
  3. A JWT is signed, not encrypted. The payload is readable by anyone. Put only non-sensitive identity data inside (sub, email).
  4. Middleware is the right place for auth. One function, added to every protected route as a second argument. Routes stay clean.
  5. Return the same error for wrong email and wrong password. Different messages let attackers enumerate valid accounts.
  6. JWT_SECRET must be secret, long, and random. It is the only thing protecting every user account in your system.

Where to Go From Here

Authorisation — per-user data Add user_id to the books table. Use req.user.sub in queries so users only see their own books: WHERE user_id = $1. Return 403 if someone tries to modify another user's book.

Refresh tokens Short-lived access tokens (15 min) + long-lived refresh tokens (30 days, stored in DB). Better security: a leaked access token expires quickly. Clients use the refresh token to get a new access token silently.

Rate limiting Protect /auth/login from brute-force attacks. Add express-rate-limit: max 5 login attempts per IP per 15 minutes. Prompt: "Add rate limiting to the auth routes using express-rate-limit."
