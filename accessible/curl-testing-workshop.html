What you'll be able to do

By the end of this module you will be able to:

  • Use curl to send HTTP requests and interpret response bodies, headers, and status codes
  • Capture a JWT from a login response and use it in subsequent authenticated requests
  • Write a shell script that runs a complete CRUD test sequence automatically
  • Use jq to filter and extract data from JSON API responses in the terminal
  • Diagnose common API failures — connection refused, 401, 404, 422 — using curl output alone

Why curl?

curl is a command-line tool that sends HTTP requests and shows responses. It is the universal language of web API testing.

  • ✓ — No install friction — ships with macOS, Linux, WSL; zero setup
  • ✓ — Scriptable — embed in bash scripts, CI pipelines, Makefiles
  • ✓ — Exact — you see precisely what is sent and received, no abstraction
  • ✓ — Universal — every API, every language, every server
  • ✓ — Agent-readable — AI coding assistants reason about curl natively
Key concept

The mental model shift: A browser hides everything. A GUI client (Postman) adds a UI layer. curl forces you to think in raw HTTP — exactly what the server sees.

Real context: Every command in this deck was used to test the Reading List API we built in Parts 1 and 2.

Anatomy of a curl Command

  • -s — Silent mode — suppresses the progress bar, keeps output clean
  • -X POST — HTTP method — GET is default; specify POST, PATCH, DELETE explicitly
  • -H — Header — add any HTTP header; repeat for multiple headers
  • -d — Data / body — the request body; tells curl to POST automatically
  • -o file — Output to file — saves response body to disk instead of stdout
  • | jq . — Pretty-print — pipe JSON output through jq to format and colour it
Tip

Rule of thumb: always use -s and pipe to jq when testing JSON APIs. The signal-to-noise ratio is much better.

HTTP Methods — What Each One Means

REST APIs use HTTP methods as verbs. Understanding them is essential before testing anything.

Methodcurl flagMeaningReading List API
GET(default)Read — never modifies anythingList books, get one book, stats
POST-X POSTCreate or trigger an actionRegister, login, add a book
PATCH-X PATCHPartially update an existing resourceUpdate status, rating, notes
DELETE-X DELETERemove a resourceDelete a book
Key concept

GET is safe and idempotent. Run it as many times as you like — no side effects. POST and PATCH change server state — be deliberate.

Part 1: The Testing Strategy

Start simple. Confirm the server is alive. Then work outward — auth first, then data.

The Health Check

Always your first call. No auth needed. Confirms the server is running and responsive.

If this works: Node.js is running, Express is listening on port 3001, database connection is configured. Proceed to auth.

Gotcha

If this fails: curl: (7) Failed to connect — the server isn't running. Start it: npm run dev

Gotcha

Lesson: Never assume the server is running. Verify it explicitly. This one habit saves enormous debugging time.

Part 2: Authentication — Getting a Token

Register once, log in to get a JWT, capture it in a variable. Every protected request carries that token.

Register a New Account

Registration is a one-time step. It creates a user record with a hashed password — no token is returned at this stage.

Login and Capture the JWT

Login exchanges your credentials for a JWT. Capture it immediately into a shell variable — never copy-paste tokens by hand.

How JWT Authentication Works

Client (curl)                              Server (Express)

  1. POST /auth/login  ─────────────────▶  bcrypt.compare(password, hash)
     { email, password }                   jwt.sign({ sub, email }, JWT_SECRET)
  2.                   ◀─────────────────  { "token": "eyJ..." }

  3. GET /api/books
     Authorization: Bearer eyJ...  ────▶  jwt.verify(token, JWT_SECRET)
                                            Attach payload to req.user
                                            Call next() → run route handler
  4.                   ◀─────────────────  [ { book data... } ]

  Token valid for 24h. No database lookup on steps 3/4 — stateless.
  Secret key is the only thing that must stay private.
Key concept

Authorization: Bearer — the standard HTTP header format for token authentication. Bearer signals a token follows (as opposed to Basic which uses base64-encoded username:password).

AI Agents Use curl Too

The commands in this deck were not written ahead of time. They were generated by Claude Code during live development of the Vibe Coding Study research platform, executed to verify each change worked.

What the agent does:

  • Writes server code
  • Generates curl commands to test it
  • Reads the JSON response
  • Diagnoses errors from the body + status code
  • Fixes the code and re-tests

What the human still does:

  • Approves or rejects each action
  • Interprets unexpected results
  • Decides when the test is sufficient
  • Understands the intent behind the API
  • Spots what the agent missed
Tip

The skill compounds: A developer who understands curl can supervise an AI agent's API testing far more effectively. You know what to look for, what to question, and when something is wrong.

The Development Loop

Write code
                         │
                         ▼
              curl -s /api/health                  ← Is the server running?
                         │
                         ▼
              TOKEN=$(curl -s -X POST /auth/login)  ← Can I authenticate?
                         │
                         ▼
              curl -s -X POST /api/books -H "Authorization: Bearer $TOKEN" ...
                         │
              ┌──────────┴──────────────┐
              ▼                         ▼
        { "id": 1, "title": ... }     { "error": "..." }
              │                         │
         Ship it                Read the error → Fix → Repeat

This loop — write, test with curl, read the response, diagnose, fix — is the core of backend development. Fast, precise, and completely independent of any browser or GUI tool.

Key Takeaways

  1. Start with the health check. Always confirm the server is running before testing anything else.
  2. Register once, capture the JWT immediately. Use TOKEN=$(curl ... | jq -r '.token'). Never copy-paste tokens by hand.
  3. Authorization: Bearer, not x-custom-token. The standard header for JWT authentication is Authorization: Bearer <token>.
  4. Use -i when debugging auth. Seeing the HTTP status (401 vs 404 vs 500) tells you immediately where the failure is.
  5. Chain your commands. Health → register → login → create → read → update → delete is a script, not seven separate manual steps.
  6. This is the language of APIs. Every web framework, cloud service, and AI API speaks HTTP. curl speaks it fluently.

Practical work

Write a full test script (practical)
Write a shell script that: registers a user, logs in and captures the JWT, then runs at least 5 API tests (GET, POST, PATCH, DELETE, one error case). Use jq to validate each response.
  • The script runs end-to-end without manual intervention
  • Each response is validated with jq (not just printed to the terminal)
  • At least one test checks an error case, not just the happy path
Trigger error responses (practical)
Using curl, deliberately trigger: a 401 (invalid/missing token), a 404 (nonexistent resource), and a 400 (invalid input). Confirm each matches your route's error handling logic.
  • You can show the exact curl command used for each case
  • Each returns the expected status code (not 500, not 200)
  • You traced each error back to the specific line in your route handler that produces it
