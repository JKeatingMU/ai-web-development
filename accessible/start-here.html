The Development Loop

Most people assume AI-assisted development looks like: write a prompt, get working code, ship it. The reality is more involved — and that is not a problem.

What people assume

Warning

Write prompt ↓ AI writes code ↓ Ship it ✓

What actually happens

Write a specific prompt ↓ AI generates code ↓ Read every line ↓ Ask questions · Understand patterns ↓ Test edge cases · Fill the gaps ↓ Integrate · Refine · Prompt again

The prompt is the smallest part. Reading, understanding, and integrating the output is the work.

The Reading Promise

Before you accept any AI-generated code in this course, there is one rule:

Read every line before you move on.

If you can explain it — you own it. You can debug it, extend it, and defend it to a colleague in a code review.

If you can't explain it — flag it. Use the Explain move (covered next), look it up, or cut it out. Do not ship what you cannot explain.

Warning

If no one can explain it — it is technical debt, not a feature. Velocity is worthless if the codebase becomes unmaintainable within weeks.

This is not about being slow. It is about the difference between a developer who owns their code and one who is merely a conduit between AI and production.

Two Kinds of AI Use

The same AI tool can be used in two fundamentally different ways. The difference is not the tool — it is the habit that surrounds it.

Surface UseDirected Use
Prompt style"Build me a login page"Stack · state shape · API contract · error handling spec · constraints
After generationPaste and run immediatelyRead every line before running
When it worksShip it and move onUnderstand why it works before extending it
When it breaksAsk the AI to fix itDiagnose the cause first, then prompt to fix
Long-term outcomeFast but fragile — code you do not ownSlower initially, but you can maintain and extend it

Most "vibe coding" failures are surface use failures. The developers who get the most from AI use directed mode — they have just internalised it so well it feels fast.

Anatomy of a Good Prompt

Specific prompts produce specific code. Vague prompts produce guesses. The difference in output quality is dramatic:

Without context

Warning

AI will assume a stack, invent state management, choose its own error messages, and probably import a library you do not want.

With context

AI now has exact state shape, API contract, navigation behaviour, error copy, and constraints. Output matches the actual requirements.

The Four Moves

Every useful AI interaction in software development fits one of four patterns. This course uses them throughout — B1 covers them in full depth.

MovePurposeWhen to use it
ScaffoldGenerate a complete first version of something newStarting a new component, route, schema, or service from scratch
ExplainAsk the AI to explain what it just producedAfter every Scaffold — before running the code
DebugGive the AI an error and ask for a root-cause fixWhen something fails with an error you cannot immediately diagnose
ExtendAdd functionality to existing working codeAfter you understand and own the current implementation

Always Explain after you Scaffold. Never Extend code you cannot explain. Debug by diagnosing first — resist the urge to paste the error and ask for a magic fix.

Part 2: What AI Gets Wrong

Understanding limitations before you trust the output

How AI Fails at Code

AI models produce confident, plausible-looking code. It can be wrong in several distinct ways — knowing the failure modes lets you look for them.

Failure TypeWhat It Looks LikeHow to Catch It
API hallucinationres.sendJSON() — function does not exist in ExpressRun it; check the exact function name in the library docs
Outdated syntaxReact Router v5 <Switch> in a v6 projectKnow your versions — check package.json before reading output
Missing securityNo input validation, no error sanitisation, hardcoded secretAsk: where does user data go? Is any secret visible in the code?
Incomplete error handlingOnly the happy path — no catch, no finally, no 404 caseAsk: what happens if the database is down? If the user sends bad data?
Confident wrong logicOff-by-one in pagination, wrong comparison operator in a filterTest with edge cases — empty list, page 0, boundary values, negative numbers

AI does not know it is wrong. It will not flag uncertainty unless you ask. The confidence of the output is not a signal of its correctness.

The Reading Checklist

Before accepting any AI-generated code block — in this course or in any project — work through these five questions:

  1. Can I explain every line without looking it up? If not, use the Explain move before moving on. Understanding is the gate.
  2. Are there security implications? Look for user input, authentication, SQL queries, environment variables, and hardcoded values.
  3. Does the error handling cover the likely failure modes? Check for missing catch blocks, unhandled rejections, and absent status codes.
  4. Does this pattern match the rest of the codebase? Inconsistent patterns create maintenance burden. Ask the AI to match your existing conventions if needed.
  5. If this breaks in production, will I know why? Adequate logging, clear error messages, and meaningful status codes make future debugging possible.

You will see this checklist at the end of every module in this course. Five questions, every time, for every block of generated code.

The Vibe Coding Debate

Since the term emerged in early 2025, "vibe coding" has divided the developer community. Both sides have a point — and the real answer is in the habit.

Warning

Critics say "You are building technical debt at speed. You ship code you cannot explain. When something breaks at 2am, you will have no idea where to start."

Defenders say "The leverage is extraordinary. You can build real products. Architecture and system design matter more than memorising syntax you can always look up."

This course's position Both are right. The reading habit is the dividing line. With it, vibe coding is a superpower. Without it, it is technical debt manufactured at speed.

The critics describe surface use. The defenders describe directed use. This course is the latter — and the reading habit is what makes the difference.

How to Use This Course

Practical advice before you open Track A.

  1. Follow the track order: A → B → C → D. Later tracks assume vocabulary from earlier ones. You can skip ahead, but you will hit unexplained terms.
  2. Take the quizzes seriously. They reveal gaps. A wrong answer here is cheaper than a wrong assumption in production code.
  3. Run the demo app yourself. Reading code and running code are different experiences. The demo app is there — clone it, run it, break it intentionally.
  4. The prompt reflection at the end of every module is not optional. It is where learning consolidates. Five minutes of structured reflection is worth an hour of passive reading.
  5. When stuck, ask for an explanation — not just a fix. "Explain why this fails and what the correct pattern is" teaches you. "Fix this" teaches the AI.

Practical work

Write a scaffold prompt (build)
Choose a feature (or pick one: a registration form, a book detail page, a search filter component). Write a scaffold prompt for it that includes: stack with version numbers, state shape with field types, API endpoint and expected response shape, error handling for at least one failure mode, and at least one explicit constraint. Then write the one-sentence "bad" version of the same prompt. Explain what information is lost.
  • Your prompt includes a named stack with explicit version numbers
  • The state shape specifies field names and types
  • The API contract names the endpoint and expected response shape
  • Error handling for at least one failure mode is included
  • The bad version is a single sentence without any of this context
Apply the reading checklist (evaluate)
Take any piece of AI-generated code — from a previous project, an online example, or the demo app in this course. Apply the five-point reading checklist to it. For each of the five questions, write one sentence stating whether the code passes or fails that check, and why.
  • All five checklist questions are addressed
  • Each answer is specific to the code, not a generic observation
  • At least one finding is supported with a reference to a specific line or pattern in the code
  • You are honest about any lines you cannot fully explain

  • Your position is clearly stated in the first two sentences
