What you'll be able to do

By the end of this module you will be able to:

  • Build an n8n workflow that authenticates against a JWT-protected REST API at runtime
  • Carry a JWT through a multi-node workflow using named-node expressions
  • Perform all four CRUD operations (GET, POST, PATCH, DELETE) via HTTP Request nodes with expressions
  • Use Set, Code, and Aggregate nodes to reshape and summarise item data between nodes
  • Diagnose and fix the four most common n8n API errors: 401, 404, ECONNREFUSED, and expression errors

What We're Building

By the end of this deck you will have a working n8n workflow that authenticates against your Reading List API and performs full CRUD. This is the foundation every subsequent E-track workflow builds on.

Why not just use a hardcoded token? Tokens expire. A workflow that logs in at runtime always has a fresh token — no manual credential rotation. This is the production-correct pattern.

Prerequisites: Your Reading List API must be running at http://localhost:3001 with at least one registered user and a few books. If using Railway, substitute the production URL.

Login: POST /auth/login

The first node in any authenticated workflow logs in and captures the token. The response goes into the messages array — downstream nodes read from it via expressions.

HTTP Request node config

FieldValue
MethodPOST
URLhttp://localhost:3001/auth/login
AuthenticationNone (public endpoint)
Body Content TypeJSON
Body{ "email": "you@example.com", "password": "..." }

Response you receive

{
  json: {
    token: "eyJhbGciOiJIUzI1NiIs..."
  }
}

Access it downstream: {{ $('Login').item.json.token }}

Naming nodes matters. Give the login node a clear name like "Login" — then any downstream node can reference $('Login').item.json.token without ambiguity. Unnamed nodes default to "HTTP Request", "HTTP Request1", etc. — fragile and hard to read.

Passing the Token to Protected Nodes

There are two ways to carry the JWT forward to protected API nodes. The first is cleaner; the second works but is fragile if the workflow grows.

Option A — Expression in each node (recommended)

In each HTTP Request node that needs auth, set the Header Auth credential type to "None" and instead add a custom Header manually:

Header name:  Authorization
Header value: Bearer {{ $('Login').item.json.token }}

The expression evaluates fresh on every execution — always uses the token from the current run's login step.

Option B — Set node to extract token once

Add a Set node after Login. Set a field token = {{ $json.token }}. Subsequent nodes reference {{ $('Set').item.json.token }}. Useful when many nodes need the same value — change the Set node, not every consumer.

In large workflows, a Set node acting as a "variables" step improves maintainability — one place to update when the field name changes.

GET /api/books — List and Filter

The Reading List API supports a ?status= query parameter. Use it in n8n by adding a Query Parameter field — n8n URL-encodes it automatically.

Data Mapping: Transforming Data Between Nodes

Set, Code, Aggregate — the three nodes for reshaping what flows between steps.

The Set Node: Rename, Extract, Compute

The Set node (also called "Edit Fields") modifies the item's JSON without calling an external service. Use it to rename fields, compute derived values, or drop fields you no longer need.

Common uses

TaskSet node field
Rename id to bookIdbookId = {{ $json.id }}
Build a display stringlabel = {{ $json.title }} by {{ $json.author }}
Uppercase statusstatus = {{ $json.status.toUpperCase() }}
Flag overdue readsoverdue = {{ $json.status === 'reading' && $json.year < 2023 }}

"Keep Only Set Fields" toggle

By default, Set passes all existing fields through and adds/overwrites the ones you specify. Enable Keep Only Set Fields to strip everything else — useful when the downstream node only needs two specific fields from a large API response.

Example: API returns 12 fields per book. The Slack node only needs title and status. Set both fields, enable Keep Only — the item is now clean and minimal.

Code Node and Aggregate

For logic the Set node cannot express, use the Code node (JavaScript). For combining multiple items into one summary, use Aggregate.

Code node — process all items

// Mode: "Run once for all items"
// $input.all() returns all items
const books = $input.all()
  .map(i => i.json);

const summary = books
  .map(b => `• ${b.title}`)
  .join('\n');

return [{ json: {
  count: books.length,
  list: summary
}}];

Aggregate node — no-code summary

Aggregate collects all items flowing through and outputs one item. Common modes:

  • → — Append to array: collect all title fields into one array
  • → — Concatenate: join all label strings with a separator
  • → — Count: output the number of items received

Use Aggregate when: Split Out created multiple items and you need to recombine them before sending one email or one API call.

The Errors You Will Actually Hit

ErrorWhat it meansFix
401 UnauthorizedJWT missing, malformed, or expiredCheck: (1) header name is exactly Authorization, (2) value starts Bearer with a space, (3) the login step ran and $('Login').item.json.token is not undefined
404 Not FoundURL is wrong or ID doesn't existPin the node output and check the URL — log {{ $json.id }} with a Set node before the request to verify the value
Connection refused / ECONNREFUSEDThe API server is not running at that addressCheck the API is running (curl http://localhost:3001/api/health). If using n8n in Docker, localhost refers to the container — use host.docker.internal instead.
Expression error: Cannot read propertyAn expression references a field that doesn't exist at that point in the flowPin the output of the previous node and inspect the actual JSON shape. The field name or nesting may differ from what you expected.
409 ConflictUNIQUE constraint violation — item already existsAdd an IF node before POST to check whether the book already exists. Or use an upsert pattern if the API supports it.

Pin Data: Test Nodes Without Running the Whole Workflow

When building incrementally, you do not want to call the login endpoint every time you adjust a downstream node. Pinning freezes a node's output so downstream nodes use it without the node re-executing.

  • 1 — Run the workflow once to populate real data through all nodes.
  • 2 — Click the node you want to freeze → in the output panel → click the pin icon. The node now shows a pin badge.
  • 3 — Edit downstream nodes freely. Re-run from the pinned node — the login is not called again; the pinned data flows through as if it had just executed.
  • 4 — Unpin when you are happy with the downstream logic and want to run end-to-end again.

Pin the login node while working on data transformation — you avoid repeatedly hitting the auth endpoint and can inspect the exact token and structure being used.

Practical work

Build the authenticated CRUD workflow (practical)
Build the complete workflow shown in slide 2: Webhook → Login → Set (extract token) → GET /api/books → Split Out → PATCH each book's status to "reading". Use expressions throughout. Verify with a GET at the end that statuses changed.
  • The JWT is obtained at runtime via POST /auth/login — no hardcoded token
  • Split Out correctly creates one item per book from the books array
  • The PATCH URL uses {{ $json.id }} to target each book individually
Add a filter and summary (practical)
Extend the workflow: after GET /api/books, add an IF node to filter to only books with status="unread". Then add an Aggregate node to count the unread books and build a formatted list of their titles. Log the result.
  • The IF node correctly filters on $json.status === "unread" (or equivalent expression)
  • The Aggregate node produces one output item with a count and formatted list
  • You can explain why Aggregate is needed here instead of just using Split Out output directly
Debugging: what went wrong? (reflect)
During the build, you will hit at least one error. Document it: what was the error, what did you check first, and what fixed it? Use the debugging patterns from slide 11.
  • You named the specific error message or HTTP status code
  • You described what you checked to diagnose it (pinning, inspecting node output, etc.)
  • Your fix addresses the root cause, not just the symptom
