State & Effects

C1 gave you components and local state. This deck goes deeper — how React handles side effects, how to fetch data from your API, and how to manage loading and error states cleanly. Every pattern here is what AI generates for real applications.

The Render Cycle — What Triggers a Re-render?

Before useEffect makes sense, you need to understand when React re-renders. Everything else follows from this.

State change Calling a setter function (setCount, setBooks ) schedules a re-render. React batches multiple setters in one render.

Props change When a parent re-renders and passes different prop values to a child, the child re-renders too. Same props = no re-render (by default).

Context change If a component consumes a React context and the context value changes, it re-renders. You will meet this in C4 (auth state).

Re-renders are cheap — React only updates the DOM where something actually changed. The concern is not re-renders themselves but side effects (API calls, timers) that must not run on every render. That is why useEffect exists.

Side Effects — What They Are and Why They Need Managing

A side effect is anything a component does that reaches outside the React render cycle: fetching data, setting a timer, subscribing to an event, updating the document title.

useEffect separates what to render from what to do after rendering. AI always wraps fetch calls in useEffect — now you understand why.

useEffect — The Dependency Array

The second argument to useEffect controls when it runs. This is the most important thing to read in any AI-generated effect.

Second argumentWhen the effect runsTypical use
OmittedAfter every renderAlmost never correct — causes infinite loops with state updates
[] (empty array)Once after mountFetch initial data, set up subscriptions, start timers
[id] (with value)After mount, then whenever id changesFetch data that depends on a prop or state value
[id, filter] (multiple)After mount, then when either changesRe-fetch when any dependency changes

AI often gets this right but sometimes omits values from the array. If you use a variable inside useEffect, it should appear in the dependency array — unless it is a setter function (those are stable and can be omitted). Ask AI to explain its dependency array if it is not obvious.

Async/Await Inside useEffect

useEffect cannot take an async function directly — the callback must return either nothing or a cleanup function, not a Promise. AI works around this with an inner async function.

Define then call — define the async function inside the effect, then call it on the next line. AI always uses this two-step pattern.

try/catch/finally — catch handles network errors and non-OK responses. finally always runs — it resets isLoading whether the request succeeded or failed.

res.ok check — fetch only throws on network failure, not HTTP errors. A 404 or 500 response does not throw. Always check res.ok before calling res.json().

Effect Cleanup — Avoiding Memory Leaks

When a component unmounts, any ongoing work (timers, subscriptions, in-flight requests) should be cancelled. useEffect supports a cleanup function — the value you return from the effect.

Return a function — whatever you return from useEffect is called when the component unmounts (or before the effect re-runs). This is the cleanup slot.

AbortController — a browser API for cancelling fetch requests. Pass controller.signal to fetch, call controller.abort() in cleanup. AI generates this for any component that might unmount mid-fetch.

Without cleanup, setting state on an unmounted component causes a React warning. With cleanup, the fetch is cancelled before the state update happens.

Multiple Effects — One Concern Per Effect

You can have as many useEffect calls as you need. AI tends to write one effect per logical concern — this is the right pattern. Mixing unrelated concerns in one effect makes both harder to understand and test.

Each effect has its own dependency array. They run independently. Mixing them into one block means one change triggers unrelated work.

document.title is a classic side effect — it's outside the React tree. useEffect with a dependency is the correct place for it.

When AI generates a component with multiple effects, read each one separately. What is its purpose? What triggers it? What does it clean up?

Custom Hooks: Extracting Logic into Reusable Hooks

When AI generates the same pattern twice, it's time for a hook.

Custom Hooks — Reusing Stateful Logic

A custom hook is just a function whose name starts with use and that calls React hooks internally. It lets you extract and reuse logic without duplicating useState + useEffect across components.

Naming convention — must start with use. This is how React knows it is a hook and enforces the rules of hooks (not called conditionally, not called outside components).

Returns whatever the consumer needs — usually an object { data, isLoading, error }. The component destructures what it needs.

When AI generates a custom hook, ask: what would this component look like without the hook? The answer shows you exactly what complexity the hook is hiding.

Prompting for a Generic useFetch Hook

Once you understand useBooks, the next step is a generic version that works for any endpoint. This is a prompt where specifying the TypeScript generic is important.

Prompt — generic data-fetching hook

I'm building a React + TypeScript app. Please generate a generic useFetch<T> custom hook that:

  • Accepts a URL string as its parameter
  • Returns { data: T | null, isLoading: boolean, error: string | null }
  • Uses AbortController for cleanup on unmount
  • Re-fetches when the URL changes
  • Does not fetch if the URL is an empty string

Show me how to use it to fetch a list of books typed as Book[]. Explain what the TypeScript generic T does here.

Why this prompt works: the generic T requirement forces AI to generate TypeScript-aware code. The "do not fetch if empty string" requirement prevents unnecessary requests when a URL is conditionally built. The usage example forces AI to show the hook in context.

Reading the Generated useFetch Hook

T is a type parameter — it flows from the call site: useFetch<Book[]> makes data typed as Book[] | null. The hook itself is generic — it does not know or care what T is.

setError(null) on each new fetch — clears any previous error so a successful retry is not obscured by the old error message.

json as T — a type assertion. AI uses this because fetch returns any. It is safe here because you control the URL and know the shape. For external APIs, add runtime validation.

State Batching — Why Multiple Setters Don't Mean Multiple Renders

Calling three setters in a row does not cause three re-renders. React batches state updates triggered in the same event handler or effect into a single render.

React 18 automatic batching — batches updates inside async functions, setTimeout, and promises. Earlier React only batched inside event handlers. AI targeting React 18+ assumes automatic batching.

Object state — some AI-generated code combines related state into one object. This is a valid pattern. The spread ...state is required to preserve other fields — omitting it replaces the whole object.

Three separate state variables are easier to read and update independently. Object state reduces setter calls. Both are correct — understand the trade-off.

useCallback and useMemo — Optimisation Hooks

AI sometimes generates these. Know what they do and when they are — and are not — needed.

useCallback — memoises a function so it keeps the same reference between renders. Useful when the function is passed as a prop to a memoised child component.

useMemo — memoises the result of a computation. Useful when filtering/sorting large arrays that would be recalculated on every render.

Do not add these by default. AI sometimes over-optimises. A filter on 20 books does not need useMemo. Ask AI: "Is this actually needed here, or is it premature optimisation?"

Reflect — Reading Effects in AI-Generated Code

When AI generates a component with useEffect, these are the questions that turn reading into understanding.

  • 01 What is the dependency array? Is it empty, does it have values, or is it missing? What does that mean for when this effect runs? If you are not sure, add a console.log and watch the console as you interact.
  • 02 Does the effect return a cleanup function? If it starts a fetch, sets a timer, or adds an event listener, it should clean up. If AI omitted cleanup, ask it why and whether it is intentional.
  • 03 What triggers a re-fetch? Trace from UI interaction → state change → dependency change → effect re-runs. If you cannot trace this path, the data flow is not yet understood.
  • 04 What happens on error? A fetch that only handles the happy path is incomplete. Does AI's error handling display a message, log to console, or silently fail? Is that appropriate for your use case?

Practical work

Trace the render cycle (practical)
Add console.log("render") at the top of a component that has a useEffect with a state update inside. Open the browser console. How many times does it log on load? Now remove the [] from useEffect. What happens? Restore [] and explain what you observed.
  • You can predict how many renders occur for a given useEffect configuration
  • You observed the infinite loop and understand why it happens
  • You can explain in one sentence what the [] dependency array prevents
Build useFetch (practical)
Using the prompt from slide 10, generate a useFetch<T> hook. Use it in a component to fetch your book list from the API (or from a public JSON API if your API is not running). Verify loading and error states both work by temporarily changing the URL to something invalid.
  • The hook returns the correct TypeScript types for data, isLoading, and error
  • The error state is populated when the URL is invalid
  • AbortController cleanup is present and you can explain what it prevents
useCallback audit (reflect)
Ask AI to generate a component that uses useCallback. Then ask it: "Is useCallback actually needed here? What would happen without it?" Record both answers. Do you agree with AI's assessment?
  • You can describe what useCallback does in your own words
  • You identified whether the use case genuinely benefits from memoisation
  • You formed your own opinion and can justify it
