Build & Deploy

A working app on localhost is a prototype. A deployed app with a live database, environment-managed secrets, and a public URL is a product. This deck walks through every step — from npm run build to testing your first live API call.

Prerequisites: This deck deploys a complete fullstack application. You need a working API (B2–B3), a React frontend (C1–C4), the stack connected (D1), and auth wired end-to-end (D2). If any of those are not working locally, fix them before deploying — a broken app becomes a harder-to-debug broken app once it is running on a server you cannot see.

What npm run build Does

Vite transforms your React source — TypeScript, JSX, imports, env vars — into a handful of optimised static files that any web server can serve.

VITE_ variables are baked in at build time. import.meta.env.VITE_API_URL becomes a literal string in the bundle. If your API URL changes after building, you must rebuild.

In production, VITE_API_URL should be empty or omitted — Express serves the API from the same origin, so all /api/... paths resolve without a hostname prefix. Check api.ts : const BASE = import.meta.env.VITE_API_URL ?? ''.

The hashed filenames (e.g. index-Bk9m.js ) change on every build — Vite adds a content hash so browsers don't serve stale cached files after a deploy. This is automatic.

Do not commit client/dist/ to Git. Railway builds it from source. Add client/dist to .gitignore. Committing it bloats the repo and causes confusion about which version is deployed.

Pre-Deploy Checklist

Fix these before pushing to Railway. Most deployment failures trace back to one item on this list.

  1. .gitignore covers secrets: confirm .env is listed. Run git status and verify no .env file appears in the staged or untracked list. A leaked JWT_SECRET or DATABASE_URL is a serious incident.
  2. .env.example is up to date: every environment variable your server reads must appear in .env.example with a placeholder value. This is your deployment reference — Railway config comes from here.
  3. package.json start script: Railway runs npm start. Confirm "start": "node server/index.js" exists in the root or server package.json. Missing this produces "no start script found" deploy errors.
  4. Port is dynamic: const PORT = process.env.PORT || 3001. Railway assigns a random port via the PORT env var. Hardcoding 3001 causes the health check to fail on Railway.
  5. Build command set: Railway needs to build the React app. Either add a root-level build script ("build": "cd client && npm install && npm run build") or configure it in the Railway dashboard settings.
  6. No hardcoded localhost URLs: search the codebase for localhost:3001 and localhost:5173 in non-test files. Any that appear in server code or shared types will break in production.

Part 2 — Railway: Deploying to Railway

Web service · PostgreSQL plugin · Environment variables · Schema setup

Railway Setup — Step by Step

  1. Create project: railway.app → New Project → Deploy from GitHub repo. Select your repository. Railway detects Node.js automatically.
  2. Add PostgreSQL: in the project dashboard → + New → Database → PostgreSQL. Railway provisions a managed database and sets DATABASE_URL in your service's environment automatically.
  3. Set environment variables: Service → Variables tab. Add all variables from your .env.example: JWT_SECRET, NODE_ENV=production, CLIENT_ORIGIN (your Railway domain — set this after the first deploy).
  4. Set build + start commands: Settings → Build Command: cd client && npm install && npm run build. Start Command: node server/index.js (or npm start).
  5. Deploy: push to your main branch — Railway builds and deploys automatically. Watch the build logs for errors.
  6. Run schema.sql: after the first deploy, connect to the Railway PostgreSQL instance and run your schema. See the next slide for how.
  7. Set CLIENT_ORIGIN: copy your Railway domain (e.g. https://myapp.up.railway.app) and add it as CLIENT_ORIGIN in Variables. Redeploy.

Running Your Schema on Railway PostgreSQL

Railway's managed database doesn't have your tables yet. Run schema.sql once after the first deploy using either the Railway shell or a local connection via the Railway CLI.

Run once — not on every deploy. schema.sql typically contains CREATE TABLE statements. Running it twice on a database with data will fail or drop data if you used DROP TABLE IF EXISTS. For subsequent changes, use ALTER TABLE migrations.

Use IF NOT EXISTS: write CREATE TABLE IF NOT EXISTS in your schema so re-running is safe in development. Railway's DB is fresh on first deploy so this is mostly a safety net for local resets.

DATABASE_URL format: Railway provides a full PostgreSQL connection string. Your pg Pool picks it up automatically: new Pool({ connectionString: process.env.DATABASE_URL }). No other DB config needed.

After running the schema, test the health endpoint: curl https://your-app.up.railway.app/api/health. If it returns { "ok": true }, the server is up and connected to the database.

Environment Variables in Production

Every secret that lives in your local .env must be set in Railway's dashboard. Never commit secrets to Git.

VariableValue in RailwayNotes
DATABASE_URLSet automatically by Railway PostgreSQL pluginDo not set manually — Railway manages this
JWT_SECRETA long random string (32+ chars)Generate with node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
NODE_ENVproductionSome packages behave differently in production (logging, error detail)
CLIENT_ORIGINhttps://myapp.up.railway.appSet after first deploy when you know the domain
PORTDo not set — Railway provides itYour code reads process.env.PORT || 3001

JWT_SECRET in production must be different from development. If the same secret is used in both environments, a token signed in development is valid in production — a security hole.

After setting variables, redeploy. Railway does not restart your service when env vars change — you must trigger a redeploy manually or push a new commit.

Testing the Live Deployment

Test in layers — API first, then auth, then the full frontend flow. Diagnose from the bottom up.

Test with curl before the browser. curl removes browser-layer issues (CORS, caching, React Router) — if curl works, the API is correct and any remaining issues are frontend.

If the health check fails: check Railway build logs. The most common causes are a missing start script, a hardcoded port, or a missing dependency that was accidentally in devDependencies.

If login returns 500: JWT_SECRET is probably not set in Railway. Verify in Variables → confirm the key is spelled exactly as process.env.JWT_SECRET reads it in your code.

If the React app loads but API calls fail: open DevTools → Network → look at a failing API request. Check the URL it is calling — if it still says localhost:3001, VITE_API_URL is set in Railway and overriding the empty default.

Prompt Reflection

Deployment surfaces assumptions you made during development. Reflect on what the process revealed.

The environment gap: Development uses .env files; production uses platform env vars. Which variables caused you the most trouble to transfer? What would make this process less error-prone — in your project structure or your prompts?

Build-time vs runtime config: VITE_API_URL is baked in at build time. PORT is read at runtime. If you needed to change the API URL after deploying without rebuilding, would that be possible? What would you need to change in your architecture?

The first curl test: What was the first error you encountered when testing the live API with curl? Walk through how you diagnosed it — what did you check first, what did the error message tell you, and what was the actual cause?

AI and deployment: Deployment configuration is infrastructure, not application code. Did you use AI to help with the Railway setup or the build script? How useful was AI for this part of the project compared to the application code itself?
