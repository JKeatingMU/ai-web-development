Forms & Validation

Forms are where your UI meets your API. React's controlled-input model is different from plain HTML — the AI will generate it correctly most of the time, but you need to understand exactly why it works the way it does so you can fix it when it doesn't.

Controlled vs Uncontrolled Inputs

HTML forms manage their own state by default. React lets you take control — or leave it to the DOM.

Uncontrolled — DOM owns the value

Simpler for one-off reads, but React can't react to changes — no live validation, no conditional UI.

Controlled — React owns the value

React re-renders on every keystroke. The displayed value and the state value are always the same. This is the standard pattern.

Multiple Fields — One State Object

Managing one useState per field gets repetitive fast. AI typically generates a single state object with a generic onChange handler — understand this pattern before accepting it.

The spread trick: { ...prev, [name]: value } copies all existing fields and overwrites just the one that changed. This prevents clearing the other fields on every keystroke.

name= must match the key: if the input's name attribute doesn't match the state key, the wrong field updates. This is the most common AI-generated bug in this pattern.

TypeScript check: the interface enforces that name is always a valid key. Without it, a typo silently adds a new field to state.

Form Submission

Submitting a form calls your API. Three things must happen: prevent the page reload, track loading state, and catch errors. AI generates all three — check that it does.

Always use a <form> element. Putting onClick on a button instead of onSubmit on the form means Enter key submission doesn't work — a common AI shortcut that breaks accessibility.

finally is non-negotiable. If you put setLoading(false) only in the try block, a network error will leave the button permanently disabled.

Reset form on success: call setForm(initialState) inside the try block after a successful API call so the fields clear for the next entry.

Client-Side Validation

Validation runs in the browser before the API call. It improves the experience — but it is not a security measure. Your API must always validate on the server side too.

Client validation ≠ server validation. Anyone can disable JavaScript or call your API directly with curl. Always validate on both sides.

Validate only what the UI knows about: format, length, required. Don't try to check uniqueness or business rules client-side — those belong on the server where you have the database.

The errors object pattern is what AI typically generates. Each key is a field name, each value is an error message string. An empty object means valid.

Note .trim(): a field containing only spaces would pass a simple !form.title check. Always trim before checking required fields.

When to Show Errors

Showing errors at the wrong moment is more frustrating than not showing them at all. Two common strategies — both have trade-offs.

StrategyWhen errors appearProsCons
On submitAfter first submit attemptNo premature errors while typing. Simple to implement.User must submit before knowing about any error. Can be jarring with many errors at once.
On blurWhen field loses focus (onBlur)Feedback per field as user moves through form. Feels responsive.More state to manage (which fields have been touched). Error on first visit to a field can feel aggressive.
HybridOn submit first; on change after first submitBest of both: no premature errors, live feedback once user is aware of the form.Requires a submitted flag in state. AI may not generate this correctly.

The hybrid pattern is the industry default for most forms — submit to reveal errors, then live feedback as the user corrects them. Ask AI for this explicitly: "validate on submit, then update errors on change."

Never validate on onChange alone. Showing "Title is required" the moment a user clicks an empty field — before they've typed anything — is an anti-pattern that erodes trust in the form.

Displaying Errors Accessibly

Error messages need to be visible and machine-readable. Screen readers need to know which message belongs to which field.

aria-describedby connects the input to its error paragraph by ID. A screen reader announces the error message when the field receives focus.

aria-invalid="true" signals to assistive technology that the field has a validation error — browsers may also add visual styling.

role="alert" on the error paragraph causes screen readers to announce it immediately when it appears in the DOM, without waiting for the user to focus the paragraph.

Check AI-generated forms for htmlFor / id pairs. AI often omits the label htmlFor linkage — a label that is not programmatically linked to its input is invisible to screen readers.

TypeScript Form Event Types

React's TypeScript generics for form events are verbose. AI handles them correctly most of the time — recognise the pattern so you can fix it when it doesn't.

The generic tells TypeScript what kind of element fired the event. Without it you get EventTarget — which has no value property, causing a type error.

Checkbox gotcha: checkboxes use e.target.checked (a boolean), not e.target.value. This is the most common checkbox bug in AI-generated forms.

AI shortcut you'll see: e: any on event handlers. This silences TypeScript but loses all safety. Push back: ask AI to provide the correct generic type for each handler.

You rarely need to import React explicitly in modern React (17+). The JSX transform handles it. But event types like FormEvent still need a named import from 'react'.

Part 2 — Prompting: Prompting for Forms

What to ask for · What to read · What AI typically gets wrong

Scaffold Prompt — Add Book Form

A good scaffold prompt specifies fields, validation rules, state shape, submission behaviour, and accessibility. Vague prompts produce forms that work but are hard to maintain.

Scaffold prompt — paste into your AI assistant

Create a React TypeScript component called AddBookForm that submits a new book to my Reading List API. Fields:

  • title — text input, required, max 200 characters
  • author — text input, required
  • status — select with options: want-to-read, reading, finished

Requirements:

  • Use a single state object with a generic onChange handler (name attribute pattern)
  • Validate on submit first; then update errors on change after first submit attempt
  • Show per-field error messages linked with aria-describedby and aria-invalid
  • Show a loading state on the submit button while the request is in flight
  • Show a general error message if the API call fails
  • Call an onSuccess prop (no arguments) when the book is added successfully
  • Use the api.post function from ../api/api.ts for the request
  • Reset all fields to their initial values after a successful submit
  • Use correct TypeScript types for all event handlers — no any
  • Every input must have a label linked with htmlFor and matching id

Reading the AI-Generated Form

Before using the component, verify these five things. AI gets most of them right — but each is a source of real bugs when it doesn't.

  1. Label linkage: every <label htmlFor="x"> must have a matching <input id="x">. If these don't match, the label is decorative only — not accessible.
  2. State key = name attribute: if the generic handleChange uses e.target.name, every input's name attribute must exactly match the key in the state object. A mismatch creates a silent new key.
  3. finally block: setLoading(false) must be in finally, not just in try. Check this first — it's the most common omission.
  4. Reset on success: check that setForm(initialState) is called after a successful API call. If not, the form retains the last submission's values.
  5. Error type narrowing: catch (err) gives you unknown in TypeScript. Check that AI narrows it — err instanceof Error ? err.message : 'Something went wrong' — rather than casting with as Error.

Real-Time Validation — and When to Debounce

Running validation on every keystroke is fine for simple rules. For anything async (checking username availability) you need to debounce — delay the call until the user pauses typing.

Without debounce: a username field fires a network request on every single character typed — potentially 20+ requests for a short username. This is expensive and confusing.

The cleanup function cancels the previous timer on every render. Only the final timer (400ms after the last keystroke) fires. This is the same useEffect cleanup pattern as AbortController.

400–500ms is the conventional debounce delay for search and validation inputs. Lower feels jittery; higher feels sluggish.

For simple sync validation (required, max length), debouncing adds complexity without benefit. Only reach for it when the validation involves a network call.

Using the Form in a Page Component

The form component is controlled entirely by its parent. The parent passes onSuccess and reacts to it — typically by refreshing the book list or showing a confirmation.

The refresh counter trick: changing the key prop on BookList unmounts and remounts it, which triggers its useEffect to re-fetch. Simpler than lifting the list state up or using a shared store.

Toggle pattern: v => !v as the setter argument ensures you're always toggling the current value — not a stale closure over the initial render's value.

Conditional mount: {showForm && <AddBookForm />} unmounts the form when hidden. This resets all form state automatically — no need to manually clear fields on cancel.
