Validation & Error Handling

Reject bad input before it enters your database, and return useful error messages when things go wrong

What Happens Without Validation

Bad data enters the database

  • Books with no title — queries break downstream
  • Status values outside your allowed set
  • Numbers stored as strings, causing sort failures
  • Empty strings that pass NOT NULL checks

Errors reach users raw

  • Cannot read properties of undefined
  • PostgreSQL constraint error text leaked to client
  • 500 responses with no body when an await fails
  • No consistent error shape for the frontend to handle

What good validation gives you

  • Reject bad requests at the boundary — never touch the DB
  • A 400 response with a clear error field the client can display
  • Consistent error shape everywhere in the API
  • Easier debugging — the error appears where the data was wrong

What this deck covers

  • Manual validation in route handlers
  • Centralised error middleware + AppError
  • asyncHandler to remove try/catch boilerplate
  • Schema validation with Zod

Where Validation Lives

Validation is not a single place — it is a layered defence. Each layer catches what the one above it missed.

Layer 1 — Client (browser / app)
  HTML required, type="number", React form libraries
  ✓ Fast feedback   ✗ Bypassable — anyone can use curl

Layer 2 — Route handler (our focus today)
  Check required fields, types, lengths before hitting DB
  ✓ Always runs     ✓ Full control over error shape

Layer 3 — Database constraints
  NOT NULL, CHECK, UNIQUE, FK constraints in PostgreSQL
  ✓ Last line of defence   ✗ Raw DB errors need translation

Layer 4 — Business logic
  Is this user allowed to edit this book?
  Does the status transition make sense?

Rule of thumb Validate at the boundary where data enters your system. The route handler is that boundary for HTTP requests — after this layer, you should be able to trust your data.

DB constraints are not a replacement A PostgreSQL NOT NULL violation returns a raw pg error. If you don't catch it, Express sends a 500. Validate first in the route handler, so the DB is a safety net, not the first reporter.

Checking Required Fields

The simplest approach: check the fields you care about before touching the database. Return 400 early if anything is wrong.

Three checks to always make

  • Required: is it present at all?
  • Type + length: is it the right shape?
  • Allowed values: is it in the permitted set?

!title catches more than you think This is truthy-falsy shorthand. It catches undefined, null, "", and 0. For strings, follow up with .trim().length === 0 to also catch " ".

The Validate Helper Pattern

When you have the same checks in multiple routes, extract them into a reusable function.

Why a separate file The same validation rules apply to POST (all required) and PATCH (all optional). One function with a requireAll flag keeps the logic in one place — change the rules once, both routes update.

Return null for success Returning a string on error and null on success is a simple convention. The route checks if (err) — null is falsy, so it only blocks when there is a real error.

Part 02: Centralised Error Handling

Express has a built-in mechanism for catching errors from any route and sending a consistent response. Stop writing the same catch block everywhere.

The Four-Argument Error Handler

Express recognises error-handling middleware by its four parameters. Register it after all routes — it only runs when a route calls next(err) or throws (with asyncHandler).

How errors reach this handler

  • Synchronous: next(new Error(...)) in a route
  • With asyncHandler: any throw or rejected promise
  • Without asyncHandler: you must wrap every await in try/catch and call next(err)

Don't log everything A 400 (bad input) is the client's fault — logging it as an error creates noise. Only log 500s, which indicate a bug in your code.

AppError — Carrying a Status Code

Error objects don't have a status property by default. A small subclass adds one so your error middleware can use it directly.

Why extends Error? Inheriting from Error gives you a .message, a .stack, and correct instanceof checks. You are just adding a .status field on top — minimal footprint.

Default to 500 The default status of 500 means that if you throw an AppError without specifying a code (or if an unexpected error reaches the handler), the client gets "Internal server error" and you get a log entry to investigate.

asyncHandler — No More Try/Catch

Express does not catch rejected promises from async route handlers automatically. asyncHandler wraps your handler and forwards any error to next() for you.

How it works The wrapper calls your async function, which returns a Promise. If that Promise rejects, .catch(next) passes the error to Express's error pipeline — same as calling next(err) yourself.

Already in express-async-errors If you npm install express-async-errors and import it once, Express patches itself to catch async errors automatically — no wrapper needed. Either approach works; the manual version teaches what's happening.

Designing Good Error Responses

Avoid these patterns

  • A bare status code with no body — client can't display anything
  • Raw PostgreSQL error text leaked to the client
  • Different shapes per route: {message} here, {err} there
  • Exposing a stack trace in production

Consistent error shape Always { error: "human-readable message" }. Optionally add code for machine-readable codes the frontend can switch on.

HTTP Status Codes for APIs

Use the most specific code that fits. Clients (and developers with curl) read these to understand what went wrong.

CodeMeaningWhen to use
200OKSuccessful GET, PATCH, DELETE
201CreatedSuccessful POST (return new resource)
204No ContentSuccess with no response body (rare in REST APIs)
400Bad RequestInvalid input, missing fields, wrong types
401UnauthorizedMissing or invalid JWT
403ForbiddenAuthenticated, but not allowed to do this
404Not FoundResource does not exist (or you don't want to reveal it)
409ConflictDuplicate (UNIQUE constraint violation)
422UnprocessableSemantically invalid (structurally correct but fails business logic)
500Server ErrorUnhandled exception — always a bug to fix

401 vs 403 401 means "I don't know who you are" — the client should log in. 403 means "I know who you are, and you are not allowed" — logging in again won't help.

404 for ownership checks If a user requests /api/books/42 and book 42 belongs to someone else, return 404 rather than 403. This avoids confirming that the resource exists at all.

Part 03: Schema Validation with Zod

Manual checks work, but they don't scale. Zod lets you define the shape of valid data once, then parse any input against it — with automatic error messages and TypeScript type inference.

Defining a Schema

Install once: npm install zod. Then describe the shape of your data with z.object() and a chain of validators.

Schema = documentation + validation A Zod schema is both the validation logic and the documentation for what your route accepts. Anyone reading CreateBookSchema immediately knows the contract.

TypeScript bonus If you are using TypeScript, z.infer<typeof CreateBookSchema> gives you a type for free. You never write a separate interface that can drift out of sync with your validation.

.refine() for business rules .refine() runs custom logic that goes beyond type checking — like "at least one field must be present" for a PATCH route.

Using safeParse in a Route

safeParse returns an object with a .success flag instead of throwing. This keeps your validation clean without a surrounding try/catch.

result.data is trusted After a successful safeParse, result.data has been coerced and validated. If a field had .default('want_to_read'), it is already filled in. You do not need to re-check anything before using it.

Multiple errors at once Zod collects all validation failures in result.error.issues. Joining them into a single message string gives the client all the problems in one response — better than returning one error at a time.

Prompting for Validation & Error Handling

Prompt

Prompt — Add Zod validation

I have an Express route: POST /api/books with body fields title (required), author (required), genre (optional string), status (optional, must be one of: want_to_read, reading, read). Add Zod schema validation using safeParse. Return 400 with joined error messages if validation fails. Use my existing AppError class and asyncHandler. Show only the schema file and the updated route — do not rewrite the whole server.

Prompt

Prompt — Centralised error middleware

Add Express error-handling middleware to my server.js. It should use err.status (defaulting to 500) and err.message. Log the full error only for 500s. Return JSON with a single "error" field. Show where in the file it should be registered relative to the routes.

Give the AI your existing code Paste your current route handler into the prompt. Ask for validation to be added to it — not a new version that might use different patterns. "Add to this route" is better than "write me a route".

Ask for targeted changes AI tends to rewrite the whole file. Specify: "Show only the schema definition and the changed route — leave the rest of server.js unchanged." You can then apply the diff yourself.

Read every line Generated validation code often uses slightly different field names or misses your allowed-values list. Check that the schema matches your actual DB column constraints before running it.

The core shift Validation is about drawing a line: everything inside the line is data you trust; everything outside is data you checked. Error handling is about communicating clearly when the line is crossed. Both are habits, not afterthoughts.

Practical work

Add manual validation to POST /api/books (practical)
Add checks for required fields (title, author), type and length, and allowed status values. Return 400 with a descriptive error message if anything fails. Test with curl using missing fields, empty strings, and invalid status values.
  • POST with missing title returns 400 with a clear error message
  • POST with status="finished" returns 400 (not in allowed set)
  • POST with title of only spaces returns 400 (trim check)
  • Valid POST still returns 201 with the created book
Add AppError + asyncHandler + error middleware (practical)
Create AppError.js and asyncHandler.js. Register error-handling middleware at the bottom of server.js. Refactor at least two routes to use asyncHandler and throw AppError instead of inline try/catch. Verify the 404 case on GET /api/books/:id.
  • AppError class exists with message and status properties
  • asyncHandler wraps at least two route handlers
  • Error middleware registered after all routes in server.js
  • GET /api/books/9999 returns 404 JSON, not a 500 or empty body
Replace manual validation with Zod (practical)
Install Zod. Create a CreateBookSchema and UpdateBookSchema. Replace the manual validation in POST /api/books and PATCH /api/books/:id with safeParse calls. The UpdateBookSchema should reject requests with no fields at all using .refine().
  • npm install zod and schema file created
  • POST uses CreateBookSchema.safeParse — manual checks removed
  • PATCH uses UpdateBookSchema — .refine() rejects empty body
  • Error messages from Zod issues are joined and returned as a 400 response
