Document Databases & MongoDB

A different philosophy — built on JSON, designed for flexibility

You just finished A4 — you can model data in tables, write SQL queries, and think in joins. This module asks: what if you didn't need to? MongoDB stores data as JSON documents. Everything changes — and some things get simpler.

Two Philosophies

Relational (PostgreSQL)

  • › Organises data into tables, rows, columns
  • › Fixed schema — change it with ALTER TABLE
  • › Relations via foreign keys and JOINs
  • › Strong consistency and ACID by default

Document (MongoDB)

  • › Organises data into collections of documents (JSON objects)
  • › Flexible schema — documents in the same collection can differ
  • › Relations via embedding or references
  • › Horizontally scalable, schema evolves with your app

Neither is universally better — they solve different problems. This module is about understanding when each fits. The best developers know both.

In MongoDB, the data you store is the shape of your API response. No column-by-column assembly, no JOIN — return the document directly.

JSON → BSON → JSON

MongoDB stores data as BSON (Binary JSON) — a binary-encoded superset of JSON. The driver handles the conversion invisibly.

Your JS Object
      →
driver
      BSON (binary)
      →
MongoDB stores
      BSON (binary)
      →
driver reads
      Your JS Object

What BSON adds over plain JSON:

  • ISODate — Typed dates — ISODate("2026-03-01") not a string. Stored and compared as actual timestamps.
  • ObjectId — Compact 12-byte unique ID — encodes a timestamp + process ID + counter. Fast to generate and index.
  • Int32/Int64 — Explicit integer sizes — no ambiguity between integers and floats.
  • Binary — Raw bytes — store files, hashes, or encrypted fields natively.

You never write BSON — the MongoDB Node.js driver converts automatically. You work with plain JS objects throughout. new Date() stays a Date; no ISO string parsing needed.

Mongoose: Adding Schema to Flexibility

MongoDB is schema-flexible, but your app usually isn't. Mongoose adds validation, type coercion, and middleware on top of the raw driver.

Key concept

{ timestamps: true } automatically adds createdAt and updatedAt fields — you don't need to manage them manually.

Mongoose generates _id (ObjectId) automatically. The model name 'Book' maps to the collection books (lowercased + pluralised).

CRUD: Create & Read

Book.find() returns plain JS objects — you can pass them directly to res.json(). No row-to-object mapping needed.

Compare to PostgreSQL from A4: const {'{ rows }'} = await pool.query('SELECT * FROM books WHERE status=$1', ['reading']) — notice you had to unwrap rows. With Mongoose, the result IS your array.

CRUD: Update & Delete

{ new: true } returns the updated document — equivalent to RETURNING * in PostgreSQL.

Gotcha

Always use $set in updates. Without it, MongoDB replaces the entire document with your update object — you'd lose all other fields.

Gotcha

runValidators: true runs your Mongoose schema validators on update — they don't run by default on findByIdAndUpdate.

Embed vs Reference

This is the key design decision in MongoDB. Unlike PostgreSQL — where relationships always live in separate tables — you choose.

Embed (reviews inside book)

{
  "title": "Pragmatic Programmer",
  "reviews": [{
    "rating": 5, "note": "Great"
  }]
}
  • ✓ One database read gets everything
  • ✓ Atomic updates
  • ✗ Document grows over time
  • ✗ Can't query reviews independently

Reference (sessions as separate collection)

// books collection
{ "_id": "abc123", "title": "Pragmatic..." }
// readingsessions collection
{ "bookId": "abc123", "startedAt": "2026-01" }
  • ✓ Sessions grow independently
  • ✓ Query sessions without loading books
  • ✗ Needs $lookup (JOIN equivalent)
Tip

Rule of thumb: Embed when data is always read together, bounded size (< ~100 items), one-to-few relationship. Reference when data grows unboundedly, queried independently, or many-to-many. $lookup: Joining Collections

When you use references, $lookup is MongoDB's JOIN equivalent — it runs inside an aggregation pipeline.

Gotcha

If you find yourself writing $lookup for most of your queries, that's a signal your data might be better modelled in a relational database.

Tip

Compare to A4: PostgreSQL's LEFT JOIN reading_sessions rs ON rs.book_id = b.id is the same idea — match a foreign key to a local field.

Indexes in MongoDB

Same concept as PostgreSQL — a pre-sorted structure for fast lookups. Without an index, MongoDB scans every document in the collection.

  • 1 — Ascending index
  • -1 — Descending index
  • 'text' — Full-text search index — supports $text: { $search: "..." }
Key concept

Always index foreign reference fields (e.g. bookId in readingsessions) and fields you filter or sort on frequently.

.explain('executionStats') shows whether your index is being used — equivalent to EXPLAIN ANALYSE in PostgreSQL.

PostgreSQL also has JSONB columns — a powerful middle ground. You get relational structure for most fields, with schema-free flexibility for a specific field.

Many production systems use both. User accounts + billing in PostgreSQL; product catalog + content in MongoDB.

Schema Design with AI

What to check in AI-generated Mongoose schemas:

  • required — required: true on every mandatory field?
  • enum — enum used for status/type fields?
  • timestamps — { timestamps: true } set on the schema options?
  • indexes — Indexes defined for userId and other filtered fields?
  • embed/ref — Embed vs reference decision matches the stated access patterns?

MongoDB and AI: a Natural Partnership

JSON all the way down

Your API receives JSON. MongoDB stores JSON. AI thinks in JSON. Schema design prompts feel natural — paste a sample document and ask "write a Mongoose schema for this". The language of your stack and the language of your AI tool are the same.

Aggregation pipelines

The most powerful — and most complex — feature of MongoDB. AI generates correct pipelines quickly. Your job: read each $stage, understand what it does to the data, and ask "what would happen if I removed this stage?" Active engagement beats passive acceptance.

Embed vs reference is a design conversation

This isn't a syntax question — it's a judgement about access patterns and growth. Describe your app's query patterns to AI and ask it to reason through the trade-offs. Push back: "What if the number of sessions per book grows to thousands?"

Every AI-generated schema encodes assumptions about your data. Find those assumptions. If they're wrong, the schema is wrong — even if it looks correct.
