Part 01: Pagination

Every list endpoint that can grow should be paginated. We'll add offset-based pagination to GET /api/books.

Why It Matters

Without pagination

  • 10 books: fine
  • 10,000 books: DB fetches everything, sends 4 MB of JSON
  • Client renders a 10,000-row list — UI freezes
  • One request can take down a small server

With pagination

  • DB fetches 20 rows — fast regardless of total size
  • Client gets predictable, bounded responses
  • UI can show "Page 3 of 250" or an infinite scroll trigger
Key concept

The rule If an endpoint returns a list that could ever grow beyond a few dozen rows, paginate it from the start. Retrofitting pagination later breaks every existing client.

Two parameters

  • page — which page (1-indexed)
  • limit — how many per page (cap at 100)

Two Patterns — Which Should You Use?

FeatureOffset / PageCursor / Keyset
SQLLIMIT 20 OFFSET 40WHERE id > 123 LIMIT 20
URL?page=3&limit=20?after=abc123&limit=20
Random access✓ "Jump to page 7"✗ Forward-only
Stable on insert✗ New rows shift pages✓ Consistent
Performance at scaleSlow at high offsets (full scan)Fast at any depth (index seek)
ComplexityLow — easy to implementMedium — cursor encoding needed
Use whenAdmin tables, < 100k rows, page numbers neededFeeds, chat, millions of rows

We'll use offset pagination — it's the right fit for a reading list. If your dataset grows past ~500k rows, revisit cursor pagination.

Giving the AI Enough Context

Prompt

Prompt to AI

I have a Reading List API (Node.js, Express, PostgreSQL). The GET /api/books route currently returns all books as an array. Add offset pagination using query parameters ?page and ?limit. Requirements: - Default: page=1, limit=20 - Validate: page must be >= 1; limit between 1 and 100 - Return a JSON envelope: { data, total, page, limit, pages } - Use a single SQL query with a window function to get the total count without a second round-trip - Keep the existing authenticate middleware in place

Why this prompt works

  • Names the stack (no guessing)
  • Describes the current state
  • Specifies validation rules explicitly
  • Defines the exact response shape
  • Mentions the window function — otherwise AI often suggests two queries
  • Reminds it not to break auth

Window function? COUNT(*) OVER() runs alongside the SELECT and returns the total row count in every row — so one query gives you both the page of data and the total.

The Updated GET /api/books Route

Math.max / Math.min Clamps the input to valid range. page=0 becomes 1. limit=9999 becomes 100. No error thrown — silent correction.

Key concept

COUNT(*) OVER() A window function — runs across all matching rows before LIMIT is applied. Each row gets the total count. One round-trip to the DB instead of two.

Destructuring strip ({ total_count, ...book }) removes the internal total_count column before sending — clients never see it.

The Response Envelope Pattern

Plain array — avoid this

Envelope — the right shape

Key concept

The envelope adds metadata without changing the shape of individual book objects. Clients can render "Showing 1–20 of 47" or build page-number controls with no extra requests.

Testing Pagination with curl

What to verify

  • total matches your actual row count
  • pages = ⌈total / limit⌉
  • data.length ≤ limit always
  • Last page: data.length may be less than limit
  • Beyond last page: data: [], not an error
Gotcha

Credentials in scripts Never hardcode email/password. Export variables from your .env file: export $(grep -v '^#' .env | xargs) Then use $EMAIL and $PASS in your curl commands.

Common Pitfalls to Check

IssueWhat happensFix
No input validationpage=-5 or page=abc causes a SQL error or NaN offsetMath.max(1, parseInt(...) || 1)
No limit cap?limit=1000000 fetches the whole table — denial of serviceMath.min(100, limit)
No total countClient cannot compute number of pagesInclude total in envelope; use window function or second query
OFFSET at scaleOFFSET 50000 forces PostgreSQL to scan and discard 50,000 rows firstAcceptable for <100k rows; switch to cursor pagination beyond that
Sorting inconsistencyWithout ORDER BY, page contents are non-deterministicAlways add ORDER BY — e.g., ORDER BY created_at DESC

Always ask the AI "What happens if page is 0, negative, or non-numeric?" — the answer reveals whether validation was included.

Part 02: A Second Table

Real apps have multiple related tables. We'll add reading_sessions — a one-to-many relationship with books — and learn to JOIN, migrate safely, and build nested routes.

Three Relationship Types

Many-to-manyBooks ↔ tagsJunction table with two FKs

We're building one-to-many One book can have many reading sessions. Each session belongs to exactly one book.

Prompting for Schema Design

Prompt

Prompt to AI

I'm extending my Reading List API (PostgreSQL). The existing books table has: id SERIAL PK, title, author, genre, status, rating, notes, created_at. Add a reading_sessions table so users can record when they read a book. Requirements: - id SERIAL PRIMARY KEY - book_id INTEGER, FK → books(id), delete sessions when book is deleted - started_at DATE, NOT NULL, default today - finished_at DATE, nullable - pages_read INTEGER, must be positive - notes TEXT, optional - created_at TIMESTAMPTZ default now - CHECK: finished_at must be on or after started_at (or null) - Add an index on book_id Write only the SQL. Do NOT modify the books table.

Key phrases in the prompt

  • "delete sessions when book is deleted" → AI adds ON DELETE CASCADE
  • "must be positive" → AI adds CHECK (pages_read > 0)
  • "or null" → AI keeps finished_at nullable in the CHECK
  • "Do NOT modify the books table" → prevents accidental ALTER statements

Describe intent, not SQL "delete sessions when book is deleted" is clearer than asking for ON DELETE CASCADE by name. Let the AI translate intent to SQL — then verify it did so correctly.

The reading_sessions Table

Key concept

ON DELETE CASCADE When a book is deleted, PostgreSQL automatically deletes all its sessions. Without this, deleting a book would fail with a FK violation (orphaned sessions).

Two CHECK constraints

  • pages_read > 0 — no zero or negative page counts
  • finished_at >= started_at — can't finish before starting
  • Both enforced at the DB level — can't be bypassed by application code

Index on book_id Queries like "give me all sessions for book #42" scan only that book's sessions. Without it, PostgreSQL reads the whole table.

Adding Tables Safely in Production

Gotcha

Never do this in production

Prompt

Safer prompt

I need to add a reading_sessions table to my production database that already has data. Write ONLY a CREATE TABLE IF NOT EXISTS statement. Do NOT drop, modify, or recreate any existing table.

Safe migration — only add

Tip

Three safe primitives

  • CREATE TABLE IF NOT EXISTS — new table, idempotent
  • ALTER TABLE ... ADD COLUMN IF NOT EXISTS — new column
  • CREATE INDEX IF NOT EXISTS — new index

Nested Routes for Sub-Resources

Nested route pattern /api/books/:id/sessions makes the relationship explicit in the URL. The book ID comes from req.params.id and is passed as $1 in the SQL — never from the request body where it could be spoofed.

RETURNING * Returns the newly created session (with its generated id and created_at ) in the same query — no need for a second SELECT.

Route ordering matters These two routes must come after GET /api/books/stats and before no other routes that would conflict with :id.

Combining Tables with JOIN

LEFT JOIN vs INNER JOIN LEFT JOIN returns every book, even those with no sessions yet (session_count = 0 ). INNER JOIN would silently drop books with no sessions.

GROUP BY b.id Required when mixing aggregate functions (COUNT, MAX, SUM ) with non-aggregate columns. PostgreSQL needs to know how to group the session rows per book.

Gotcha

Avoid the N+1 pattern Don't fetch books, then loop and fetch sessions per book. That's N+1 queries. One JOIN does it in a single round-trip.

Testing Sessions with curl

Hands-on

Test the constraints Don't just test the happy path. Verify:

  • Finish before start → rejected
  • Negative pages → rejected
  • Session for non-existent book → FK error
  • Delete book → sessions gone

Test #5 is important Confirms ON DELETE CASCADE is working. Without it, step 5 would either error on the DELETE or leave orphaned session rows.

Many-to-Many: Tags

Why a junction table? A book can have many tags ("fiction", "classic", "CS"). A tag can belong to many books. You can't store that in either table directly — you need a third table that holds pairs.

ARRAY_AGG PostgreSQL-specific aggregate that collects values into an array. Returns ["fiction","classic"] as a JSON array — no post-processing needed.

Composite primary key PRIMARY KEY (book_id, tag_id) ensures each book-tag pair appears only once. No separate id column needed.

Hands-on

Extend this yourself Try prompting: "Add a tags system so each book can have multiple tags. Include routes to add and remove tags, and return tags in the book listing."

What AI Gets Wrong & Key Takeaways

What AI commonly gets wrong

  • No input validation on page / limit
  • Omitting ORDER BY (non-deterministic pages)
  • Missing ON DELETE CASCADE → FK violations on delete
  • Suggesting DROP TABLE for migrations
  • N+1 queries (JS loop + per-row SELECT) instead of JOIN
  • No index on FK columns
  • INNER JOIN instead of LEFT JOIN (silently drops rows)

Key takeaways

  • Paginate every list endpoint from the start
  • Validate and cap page and limit inputs
  • Always include ORDER BY with LIMIT
  • Foreign keys enforce data integrity at the DB layer
  • Think carefully about CASCADE: right for sessions, maybe not for billing records
  • Index every FK column
  • JOIN at the DB layer — never loop in JavaScript
  • Migrate with CREATE IF NOT EXISTS — never DROP
  • Test constraints deliberately, not just the happy path

Add pagination (practical)

Add a reviews table (book_id FK, rating 1-5, body text, created_at). Write a route that returns a book with its reviews joined. Handle the case where a book has no reviews.
  • The reviews table has a FK constraint referencing books with appropriate CASCADE rules
  • The JOIN route handles books with no reviews (empty array, not null or an error)
  • You tested with curl: create a book, add reviews, fetch the joined result
