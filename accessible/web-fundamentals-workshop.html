Client and Server

Every web interaction is essentially a conversation between two computers. You have a client, which is anything that sends requests—like a browser or a mobile app—and a server, which is a program that listens for those requests and sends back responses. HTTP is the protocol, or the language, they both speak. You don’t write raw HTTP; frameworks like Express handle that for you. Next, we'll explore HTTP, the language of the web, to understand how these conversations are structured.

Every web interaction is a conversation between two computers: a client that asks for something and a server that responds.

Client — anything that sends requests. A browser, curl on the terminal, a mobile app, another server.

Server — a program that listens for requests and sends responses. Express is our server framework.

Protocol — HTTP is the agreed language both sides speak. You never write raw HTTP — Express and the browser handle it.

HTTP — The Language of the Web

HTTP, or HyperText Transfer Protocol, is like a rulebook for how clients and servers communicate. It defines the format of requests and responses, what different methods mean, and what status codes to use. A key concept is that HTTP is stateless, meaning each request is independent. This is why we use JWTs for authentication. While HTTP/2 and HTTP/3 are faster, they maintain the same semantics as HTTP/1.1. Let's look at a simplified raw HTTP request to see this in action.

HTTP (HyperText Transfer Protocol) is the rulebook that defines how clients and servers communicate. It specifies the format of requests and responses, what methods mean, and what status codes to use.

Key concept

HTTP is stateless — each request is completely independent. The server has no memory of previous requests. This is why JWTs exist: each request must carry its own proof of identity.

HTTP/1.1 (text-based) is what you see in curl output. HTTP/2 and HTTP/3 are faster binary versions, but the semantics — methods, headers, status codes — are identical.

HTTP Methods — What You're Asking For

HTTP methods tell the server what action to perform. There are four main methods that cover most web APIs. PUT replaces the entire resource, which is rarely used; PATCH is preferred for partial updates. Safe methods like GET shouldn’t change data, while idempotent methods like PUT and DELETE yield the same result even if called multiple times. POST, however, is neither safe nor idempotent. Let's look at a table to see these methods and their characteristics.

The method tells the server what operation to perform. These four cover 95% of web APIs.

MethodMeaningHas Request Body?Typical Success Code
GETRead data — fetch a resource or listNo200 OK
POSTCreate — add a new resourceYes (JSON)201 Created
PATCHUpdate — modify part of a resourceYes (JSON)200 OK
DELETERemove — delete a resourceNo200 OK or 204 No Content
Gotcha

PUT replaces the entire resource (rarely used in practice). PATCH is preferred for partial updates — only send the fields you want to change. The AI-generated API in this course uses PATCH with COALESCE.

Key concept

Safe methods (GET) should never change data. Idempotent methods (GET, PUT, DELETE) can be called multiple times with the same result. POST is neither — sending it twice creates two records.

HTTP Status Codes — The Server's Reply

Every HTTP response includes a status code that tells you what happened. A 2xx code means success, like 200 for a successful read or update. A 4xx code indicates a client error, meaning you need to fix your request. A 5xx code is a server error, suggesting the server crashed. Check your logs for a stack trace if this happens. The table here lists common status codes and what they mean. Next, we'll break down the anatomy of a URL.

Every HTTP response includes a 3-digit status code. The first digit tells you the category.

2xx — Success. The request worked. 200 for reads/updates, 201 for creates.

4xx — Client error. You sent something wrong. Fix the request, not the server.

Gotcha

5xx — Server error. The server crashed. Check your terminal logs — there will be a stack trace.

Anatomy of a URL

A URL is more than just a web address; it’s a structured way to locate resources. The protocol, like https, ensures secure data transfer. The host is the server's address, while the path specifies the route on the server. Query strings add optional parameters to requests. Understanding these parts helps you navigate and construct URLs effectively. Next, we'll see what a request looks like in action.

https://api.example.com:3001/api/books?status=reading&limit=10

Protocol (https ) — http or https. Always use https in production. Encrypts data in transit.

Host (api.example.com ) — the server's address. In development: localhost:3001. After Railway deploy: your Railway domain.

Path (/api/books ) — the route on the server. Express matches this to a route handler: app.get('/api/books', ...).

Tip

Query string (?status=reading&limit=10 ) — optional key-value pairs after ?, separated by &. Read in Express with req.query.status.

What a Request Looks Like

A typical HTTP request includes several components. The method specifies the action, while the URL identifies the resource. Headers provide additional information, like authorization tokens and content type. The body contains the actual data being sent, which Express reads as req.body. This is how a POST request to add a book might look. Next, we’ll see what a response looks like from the server.

  • Method — POST — what operation to perform
  • URL — /api/books — which resource
  • Header: Authorization — Bearer token — proves who you are
  • Header: Content-Type — application/json — tells server the body is JSON
  • Body — the JSON data being sent — Express reads this as req.body

What a Response Looks Like

When a server responds, it sends back a status code and headers, informing the client how to handle the data. A 201 status code indicates a resource was successfully created. The content type tells the client how to parse the body, which contains the JSON payload. This JSON data is immediately available for further processing. Now, let’s look at JSON, the language of APIs.

  • 201 Created — The status code — success, resource created
  • Content-Type — application/json — tells the client to parse the body as JSON
  • Body — the JSON payload — the created book, returned immediately via RETURNING *

JSON — The Language of APIs

JSON, or JavaScript Object Notation, is a text format that looks like JavaScript object syntax. It’s used to structure data for APIs. Strings are always in double quotes, numbers are unquoted, and booleans are lowercase. JSON doesn’t allow comments or trailing commas. Understanding these rules ensures your data is correctly parsed. Let's check out a JSON object and array to see these principles in action.

  • Strings — always double quotes — "title" not 'title'
  • Numbers — no quotes — 5 not "5"
  • Booleans — lowercase — true, false
  • Null — lowercase null — means "no value"
  • No trailing commas — {"a":1,"b":2} not {"a":1,"b":2,}
  • No comments — JSON cannot contain // or /* */
Key concept

JSON is not JavaScript — it's a text format that looks like JS object syntax. JSON.parse(text) converts text → JS object. JSON.stringify(obj) converts JS object → text. Express calls these automatically.

REST — A Style, Not a Protocol

REST, or Representational State Transfer, is a set of conventions for structuring APIs. An API that follows these conventions is called RESTful. This matters because AI-generated APIs often follow REST principles. Understanding REST helps you identify when an API deviates from these norms. Not every API is RESTful; alternatives like GraphQL and WebSockets exist. Next, we’ll look at RESTful routes and their predictable patterns.

REST (REpresentational State Transfer) is a set of conventions for how to structure HTTP APIs. An API that follows them is called RESTful.

  • Resources are nouns — URLs identify things, not actions. /books not /getBooks or /fetchAllBooks.
  • Methods have meaning — GET reads, POST creates, PATCH updates, DELETE removes. Use the right method.
  • Stateless — Each request contains everything the server needs. No sessions stored on the server — hence JWT.
  • Standard responses — JSON data + appropriate status codes. 201 for creates, 404 when missing.
Key concept

Why this matters: When AI generates an API, it follows REST conventions. Understanding REST lets you spot when the AI broke them — e.g., a DELETE route that also creates a record, or a GET route that modifies data.

Gotcha

Not every API is RESTful. GraphQL, gRPC, and WebSockets are different styles. REST is by far the most common and the default that AI generates.

RESTful Routes — The Pattern

RESTful APIs follow a predictable URL structure, making it easy to guess a route once you know the pattern. Route parameters like :id are used to specify resources, and the /api/ prefix distinguishes API routes from HTML routes. Nested resources follow the same pattern, allowing you to build complex API structures. Let’s look at a table to see how different HTTP methods fit into this pattern.

REST APIs follow a predictable URL structure. Once you know the pattern, you can guess any API's routes.

MethodURLActionExpress handler
GET/api/booksList all books (with optional filter)app.get('/api/books', ...)
GET/api/books/:idGet one book by idapp.get('/api/books/:id', ...)
POST/api/booksCreate a new bookapp.post('/api/books', ...)
PATCH/api/books/:idUpdate fields of one bookapp.patch('/api/books/:id', ...)
DELETE/api/books/:idDelete one bookapp.delete('/api/books/:id', ...)
Tip

/api/books/:id — the :id is a route parameter. Express puts it in req.params.id. The /api/ prefix is a convention that distinguishes API routes from HTML page routes.

Nested resources follow the same pattern: GET /api/books/:id/sessions lists sessions for one book. POST /api/books/:id/sessions creates a new session for that book.

DNS — Domain Names to IP Addresses

Domain Name System, or DNS, translates domain names to IP addresses. When you use localhost, it resolves to your own machine without a DNS lookup. Railway, the platform we use, assigns a domain for your app, automatically handling DNS configuration. This simplifies deployment, allowing you to focus on building your application. Next, we’ll see how Express fits into this web ecosystem.

Key concept

localhost always resolves to 127.0.0.1 — your own machine. No DNS lookup needed. This is why http://localhost:3001 works without internet.

Railway assigns a domain like your-app.railway.app. DNS resolves this to Railway's servers, which forward requests to your Express process.

You don't need to configure DNS for this course. Railway handles it automatically when you deploy.

How Express Fits In

Express is a minimal web server framework that makes handling HTTP requests straightforward. When you run your server, Express listens for incoming requests. Middleware functions process these requests, parsing JSON, authenticating users, and more. Route handlers match the URL to execute your code, which might query a database or apply business logic. Finally, Express sends a response back to the client. Let's see how understanding these steps helps you build robust web applications.

  1. Browser or curl sends an HTTP request — method, URL, headers, optional body
  2. Express receives it — the app.listen(PORT) call opens a socket waiting for connections
  3. Middleware runs — express.json() parses the body, authenticate checks the JWT, etc.
  4. Route handler matches — Express finds the first app.get/post/patch/delete whose path matches the URL
  5. Your code runs — query the database, apply business logic
  6. res.json(data) sends the response — Express formats it as HTTP with the right headers and status code
  7. Client receives the response — browser renders it, curl prints it, your code processes it
Hands-on

Try it: run node server.js in your project folder, then open a new terminal and run curl http://localhost:3001/api/health. You should see a JSON response. Express Hello World guide

What AI Assumes You Know

AI assumes you understand key web concepts when generating a REST API. It makes decisions on HTTP methods, status codes, JSON structure, and more. Knowing these concepts lets you verify those decisions and spot errors early. Ask yourself if AI-generated routes and JSON meet standards, like returning 404 for missing resources or consistent error responses. This proactive approach helps you catch bugs before they hit production. Next, we'll summarize key terms.

When you give an AI a prompt like "Build me a REST API for a reading list", it immediately makes decisions based on this deck's content: which HTTP methods to use for which routes, which status codes to return, how to structure JSON, how to name URLs using REST conventions, and what headers to include. Understanding these concepts lets you verify those decisions — not just accept them.

Tip

Questions to ask about AI-generated routes: Does GET /books/:id return 404 when the id doesn't exist? Does POST return 201, not 200? Does PATCH only update the fields I sent? Does DELETE return a meaningful response?

Tip

Questions to ask about AI-generated JSON: Are error responses consistent — always { "error": "..." } ? Do list endpoints return arrays, not objects? Are field names consistent across routes — id everywhere, not sometimes bookId ?

A developer who understands HTTP can spot a bug in AI-generated code before testing it. A developer who just copies and pastes will only find out when something breaks in production.

Key Terms

This slide will summarize the key terms we've covered throughout the course. Understanding these terms is crucial for navigating web development and working effectively with APIs, whether you're writing them or interacting with them.

HTTP The protocol defining how clients and servers communicate

Client Anything that sends requests (browser, curl, mobile app)

Server A program that listens for and responds to HTTP requests

Request A message from client to server: method + URL + headers + body

Response A message from server to client: status code + headers + body

Method GET / POST / PATCH / DELETE — the operation being performed

Status Code 3-digit number indicating success (2xx), client error (4xx), server error (5xx)

URL Protocol + host + port + path + query string

Route A path pattern that Express matches: /api/books/:id

JSON Text format for structured data. All API bodies in this course are JSON.

REST Convention: resources as nouns, HTTP methods have meaning, stateless, JSON

DNS Translates domain names to IP addresses. localhost = 127.0.0.1.
