Client and server

Every web interaction is a conversation between two computers: a client that asks for something and a server that responds. The client is anything that sends requests — a browser, curl on the terminal, a mobile app, or another server. The server is a program that listens for those requests and sends back responses.

HTTP is the protocol — the agreed language both sides speak. You never write raw HTTP yourself; frameworks like Express and the browser handle that for you.

A single exchange looks like this: the client sends an HTTP request such as GET /api/books, and the server sends back an HTTP response such as 200 OK together with some JSON data.

HTTP — the language of the web

HTTP (HyperText Transfer Protocol) is the rulebook that defines how clients and servers communicate. It specifies the format of requests and responses, what the methods mean, and which status codes to use.

A key property: HTTP is stateless. Each request is completely independent and the server has no memory of previous requests. This is why JSON Web Tokens (JWTs) exist — each request must carry its own proof of identity.

HTTP/1.1 is text-based and is what you see in curl output. HTTP/2 and HTTP/3 are faster binary versions, but the semantics — methods, headers, status codes — are identical.

A raw HTTP request, simplified

GET /api/books HTTP/1.1
Host: localhost:3001
Authorization: Bearer eyJhbG...
Content-Type: application/json

HTTP methods

The method tells the server what operation to perform. Four methods cover about 95% of web APIs.

Common HTTP methods
MethodMeaningHas request body?Typical success code
GETRead data — fetch a resource or listNo200 OK
POSTCreate — add a new resourceYes (JSON)201 Created
PATCHUpdate — modify part of a resourceYes (JSON)200 OK
DELETERemove — delete a resourceNo200 OK or 204 No Content

PUT replaces the entire resource and is rarely used in practice. PATCH is preferred for partial updates — only send the fields you want to change.

Safe methods (GET) should never change data. Idempotent methods (GET, PUT, DELETE) can be called multiple times with the same result. POST is neither — sending it twice creates two records.

HTTP status codes

Every HTTP response includes a three-digit status code. The first digit tells you the category:

  • 2xx — Success. The request worked. 200 for reads and updates, 201 for creates.
  • 4xx — Client error. You sent something wrong. Fix the request, not the server.
  • 5xx — Server error. The server crashed. Check your terminal logs — there will be a stack trace.

Anatomy of a URL

A URL is a structured way to locate a resource. Take this example:

https://api.example.com:3001/api/books?status=reading&limit=10
  • Protocol (https) — http or https. Always use https in production; it encrypts data in transit.
  • Host (api.example.com) — the server's address. In development this is localhost:3001; after a Railway deploy it is your Railway domain.
  • Port (:3001) — which process on the host to talk to. Often omitted when it is the default for the protocol.
  • Path (/api/books) — the route on the server. Express matches this to a route handler, for example app.get('/api/books', ...).
  • Query string (?status=reading&limit=10) — optional key–value pairs after ?, separated by &. Read in Express with req.query.status.

What a request looks like

A typical HTTP request has a method, a URL, headers, and often a body. Here is a POST request that adds a book, sent with curl:

curl -s -X POST http://localhost:3001/api/books \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"title":"Clean Code","author":"Martin"}'
  • Method — POST: what operation to perform.
  • URL — /api/books: which resource.
  • Header, Authorization — a Bearer token that proves who you are.
  • Header, Content-Type — application/json: tells the server the body is JSON.
  • Body — the JSON data being sent. Express reads this as req.body.

What a response looks like

When the server responds, it sends back a status code, headers, and a body:

HTTP/1.1 201 Created
Content-Type: application/json

{
  "id": 7,
  "title": "Clean Code",
  "author": "Martin",
  "status": "want-to-read",
  "created_at": "2026-03-08T10:23:41Z"
}
  • 201 Created — the status code: success, resource created.
  • Content-Type: application/json — tells the client to parse the body as JSON.
  • Body — the JSON payload: the created book, returned immediately (in this course, via SQL RETURNING *).

JSON — the language of APIs

JSON (JavaScript Object Notation) is a text format that looks like JavaScript object syntax and is used to structure data for APIs.

// JSON object
{
  "id": 1,
  "title": "Clean Code",
  "rating": 5,
  "done": true,
  "tags": ["cs", "refactoring"],
  "notes": null
}

// JSON array
[
  { "id": 1, "title": "Clean Code" },
  { "id": 2, "title": "The Pragmatic Programmer" }
]
  • Strings — always double quotes: "title", not 'title'.
  • Numbers — no quotes: 5, not "5".
  • Booleans — lowercase true / false.
  • Null — lowercase null, meaning “no value”.
  • No trailing commas — {"a":1,"b":2}, not {"a":1,"b":2,}.
  • No comments — JSON cannot contain // or /* */. (The comments above are only for explanation.)

JSON is not JavaScript — it is a text format that resembles JS object syntax. JSON.parse(text) converts text into a JS object; JSON.stringify(obj) converts a JS object into text. Express calls these automatically.

REST — a style, not a protocol

REST (Representational State Transfer) is a set of conventions for structuring HTTP APIs. An API that follows them is called RESTful.

  • Resources are nouns. URLs identify things, not actions: /books, not /getBooks or /fetchAllBooks.
  • Methods have meaning. GET reads, POST creates, PATCH updates, DELETE removes.
  • Stateless. Each request contains everything the server needs. No sessions are stored on the server — hence JWT.
  • Standard responses. JSON data plus an appropriate status code: 201 for creates, 404 when missing.

Why this matters: when an AI generates an API it follows REST conventions, so understanding REST lets you spot when the AI broke them — for example a DELETE route that also creates a record, or a GET route that modifies data.

Not every API is RESTful. GraphQL, gRPC, and WebSockets are different styles. REST is the most common and the default that AI generates.

RESTful routes — the pattern

REST APIs follow a predictable URL structure. Once you know the pattern, you can guess any API's routes.

The standard five routes for a resource
MethodURLActionExpress handler
GET/api/booksList all books (with optional filter)app.get('/api/books', ...)
GET/api/books/:idGet one book by idapp.get('/api/books/:id', ...)
POST/api/booksCreate a new bookapp.post('/api/books', ...)
PATCH/api/books/:idUpdate fields of one bookapp.patch('/api/books/:id', ...)
DELETE/api/books/:idDelete one bookapp.delete('/api/books/:id', ...)

:id is a route parameter; Express puts it in req.params.id. The /api/ prefix is a convention that distinguishes API routes from HTML page routes.

Nested resources follow the same pattern: GET /api/books/:id/sessions lists sessions for one book, and POST /api/books/:id/sessions creates a new session for that book.

DNS — domain names to IP addresses

The Domain Name System (DNS) translates domain names into IP addresses — the numbers that identify a specific machine. When a client wants api.example.com, it asks a DNS server, which replies with an address such as 203.0.113.4; the client then sends its request there.

  • localhost always resolves to 127.0.0.1 — your own machine. No DNS lookup is needed, which is why http://localhost:3001 works without internet.
  • Railway (the platform used in this course) assigns a domain like your-app.railway.app and resolves it to its own servers, which forward requests to your Express process.
  • You do not need to configure DNS for this course. Railway handles it automatically when you deploy.

How Express fits in

Express is a minimal web-server framework that makes handling HTTP requests straightforward. A request travels through it in order:

  1. Browser or curl sends an HTTP request — method, URL, headers, optional body.
  2. Express receives it — the app.listen(PORT) call opens a socket waiting for connections.
  3. Middleware runs — express.json() parses the body, an authenticate function checks the JWT, and so on.
  4. Route handler matches — Express finds the first app.get / post / patch / delete whose path matches the URL.
  5. Your code runs — query the database, apply business logic.
  6. res.json(data) sends the response — Express formats it as HTTP with the right headers and status code.
  7. Client receives the response — the browser renders it, curl prints it, your code processes it.

Try it: run node server.js in your project folder, then in another terminal run curl http://localhost:3001/api/health. You should see a JSON response. See the Express “Hello World” guide.

What AI assumes you know

When you give an AI a prompt like “Build me a REST API for a reading list”, it immediately makes decisions based on everything above: which HTTP methods to use for which routes, which status codes to return, how to structure JSON, how to name URLs using REST conventions, and which headers to include. Understanding these concepts lets you verify those decisions rather than just accept them.

Questions to ask about AI-generated routes

  • Does GET /books/:id return 404 when the id does not exist?
  • Does POST return 201, not 200?
  • Does PATCH only update the fields you sent?
  • Does DELETE return a meaningful response?

Questions to ask about AI-generated JSON

  • Are error responses consistent — always { "error": "..." }?
  • Do list endpoints return arrays, not objects?
  • Are field names consistent across routes — id everywhere, not sometimes bookId?

A developer who understands HTTP can spot a bug in AI-generated code before testing it. A developer who just copies and pastes only finds out when something breaks in production.

Key terms

HTTP
The protocol defining how clients and servers communicate.
Client
Anything that sends requests — a browser, curl, a mobile app.
Server
A program that listens for and responds to HTTP requests.
Request
A message from client to server: method + URL + headers + body.
Response
A message from server to client: status code + headers + body.
Method
GET, POST, PATCH, or DELETE — the operation being performed.
Status code
Three-digit number indicating success (2xx), client error (4xx), or server error (5xx).
URL
Protocol + host + port + path + query string.
Route
A path pattern that Express matches, for example /api/books/:id.
JSON
Text format for structured data. Every API body in this course is JSON.
REST
Convention: resources as nouns, HTTP methods have meaning, stateless, JSON.
DNS
Translates domain names to IP addresses. localhost = 127.0.0.1.
