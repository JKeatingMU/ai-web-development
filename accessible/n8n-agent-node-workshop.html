What the AI Agent Node Does Internally

The AI Agent node implements the ReAct loop from E1 — without you writing the loop. When n8n executes the agent node, it runs this cycle until the LLM produces a final answer or the iteration limit is reached.

n8n passes to LLM:
  system_prompt  ← your system prompt field
  user_message   ← input item's text (or prompt template)
  tool_definitions ← one per child tool node (name + description + schema)
  messages_history ← conversation so far (from memory node, if connected)

LLM responds with tool_use → n8n executes the child tool node → result appended
LLM responds with text → done, output item contains the final answer

The tool definitions are generated automatically from the child nodes you connect below the agent. Each tool node's name and description become the tool schema. Write descriptive names and descriptions — the LLM reads them to decide which tool to call.

n8n's default max iterations is 10. The agent stops at 10 even if the task is incomplete. For complex tasks, increase this — but always set a limit.

The Chat Trigger: Interactive Agents

For agents that respond to user messages (rather than a schedule or webhook), use the Chat Trigger. It opens a chat interface in n8n's built-in chat panel — no frontend needed for testing.

Chat Trigger vs other triggers

TriggerUse when
Chat TriggerUser types a message to the agent (interactive assistant)
WebhookAnother system (your app, Slack) sends the prompt programmatically
ScheduleAgent runs automatically, no user input
ManualTesting — run once with fixed input from the workflow editor

Chat Trigger + Memory = persistent assistant

Without a memory node, every message starts a fresh context — the agent does not remember the previous turn. Connect a Window Buffer Memory node to give the agent in-context conversation history. Each chat session maintains its own history.

The Chat Trigger also provides a public chat URL you can share. With n8n Cloud or self-hosted with authentication, this becomes a deployable chatbot endpoint.

Connecting Tool Nodes to the Agent

Tool nodes connect to the bottom of the AI Agent node (not the right side). The agent uses them based on their name and description — the LLM reads both.

HTTP Request as a tool

FieldValue
Node typeHTTP Request (connected to bottom of agent)
Namelist_books
Description"List books in the reading list. Use when the user asks about their books, wants to see what they are reading, or asks about reading status."
Method / URL / AuthSame as E3 — GET /api/books + bearer token

Why description quality matters

The LLM sees the description when deciding whether to call this tool. A vague description like "gets books" leads to incorrect routing. A precise description — including example user queries — guides the LLM reliably.

Tool names use underscores, not spaces. The LLM writes list_books in its tool_use response — n8n matches this to the node name. Spaces in tool names cause matching failures.

Reading List Assistant: The Tool Set

A useful reading assistant needs tools that cover the core operations. Each tool is an HTTP Request node connected below the agent.

Tool nameHTTP method + endpointDescription (what to put in the field)
list_booksGET /api/books"List all books in the reading list. Supports ?status= filter for unread, reading, or read."
get_bookGET /api/books/:id"Get a single book by its ID. Use when the user asks about a specific book and you know the ID."
add_bookPOST /api/books"Add a new book to the reading list. Use when the user wants to add a book they mention by title and author."
update_statusPATCH /api/books/:id"Update a book's reading status to unread, reading, or read. Use when the user says they started or finished a book."
get_statsGET /api/books/stats"Get statistics about the reading list: total count, average year, counts by status."

Start with list_books and get_stats only. Add write tools (add_book, update_status ) after testing read-only behaviour — this limits risk during development.

Writing the System Prompt

The system prompt defines the agent's role, constraints, and output format. It is the most important configuration field in the agent node.

System prompt — Reading List Assistant

You are a reading list assistant. You help the user manage and understand their reading list via the Reading List API. Your tools: list_books (list all books, filter by status), get_book (look up one book by ID), add_book (add a new book), update_status (change a book's status to unread/reading/read), get_stats (summary statistics). Constraints: – For add_book, always confirm title and author before calling the tool. – For update_status, always call list_books first to find the book ID — never guess an ID. – If the user asks to delete a book, explain that deletion is not available through this assistant. – Respond concisely. Do not repeat the full book list unless the user asks for it. Return plain text responses, not JSON, unless the user explicitly asks for JSON.

Notice the constraints section. Without "always call list_books first to find the ID", the agent will hallucinate IDs. Explicit tool-use rules in the system prompt prevent the most common agent errors.

Giving Your Agent a Memory

In-context window buffer vs persistent Postgres memory — when to use each.

Window Buffer Memory

Window Buffer Memory keeps the last N conversation turns in the context window. The agent can refer to earlier messages in the same session — but memory is lost when the session ends.

How to connect it

  • 1 — Add a Window Buffer Memory node to the canvas (search in node panel)
  • 2 — Connect it to the memory input of the AI Agent node (separate connection point from tools)
  • 3 — Set Context Window Length to 10–20 (number of message pairs to retain)
  • 4 — The agent automatically reads and writes history — no configuration needed beyond the connection

Limits

  • → — Memory is in-process only — a workflow restart clears it
  • → — If two users chat simultaneously, they share the same buffer (single-user assumption)
  • → — Large windows consume tokens on every turn — cost grows with window size

Right for: single-user testing, short-session chatbots, demos. Not for: production multi-user agents.

Postgres Chat Memory

Postgres Chat Memory stores conversation history in a PostgreSQL table. It persists across restarts and supports multiple simultaneous users via a session ID.

Setup

  • 1 — Add a Postgres Chat Memory node
  • 2 — Connect your PostgreSQL credential (same DB as your Reading List API, or a separate one)
  • 3 — n8n creates the n8n_chat_histories table automatically on first use
  • 4 — Set Session ID to a unique identifier per user: {{ $json.userId }} or {{ $('Chat Trigger').item.json.sessionId }}

Why session ID matters

Without a session ID, all users share one history — each new user sees previous users' conversations. The session ID namespaces the history. For the Chat Trigger, n8n provides a sessionId automatically per browser session.

Right for: production chatbots, multi-user agents, any scenario where conversation continuity across sessions is required.

Testing Your Agent Systematically

Test in three layers: tools in isolation, agent routing, then end-to-end conversation.

LayerWhat to testHow
1 — Tool isolationEach HTTP Request tool node works correctly with the APIRun each tool node manually before connecting to the agent. Verify output JSON shape.
2 — RoutingThe agent picks the right tool for different user inputsTry: "What am I reading?" → expect list_books. "How many books?" → expect get_stats. "Mark DDIA as read" → expect list_books then update_status.
3 — Edge casesAgent behaviour when tools fail or input is ambiguous"Add a book" without title → does the agent ask? Unknown book ID → does it handle the 404 gracefully? Malformed query → does it ask for clarification?

Use the execution log. n8n records every tool call the agent made and the result it received. If the agent gives a wrong answer, the log shows exactly which tools it called and what they returned — no guessing needed.

Reading the Agent Execution Log

After running the agent, click the agent node → Output tab. You will see the full reasoning trace: every tool call, every result, and the final answer.

What to look for

  • → — Tool calls in order: did the agent call tools in a sensible sequence?
  • → — Tool results: did each tool return what you expected? A 401 here means the auth setup in the tool node is wrong.
  • → — Iteration count: if the agent hit max iterations, the task was too complex for its tool set or the system prompt was too vague.
  • → — Final answer quality: did it answer the question, or did it report a tool error to the user?

Common fixes from the log

What you seeFix
Wrong tool calledImprove the tool description to distinguish it from the one that was called
Tool called with wrong argumentsAdd schema constraints to the tool's input schema, or clarify in the system prompt
Tool result not usedThe system prompt may be overriding the tool result — check for conflicting instructions
Hallucinated IDAdd to system prompt: "always call list_books to find the ID before calling update_status"

What You Built With vs What You Learned

If you used an AI assistant to generate your system prompt or tool descriptions, work through these before moving to E5.

Questions to answer without re-reading the AI's output
  • Name every tool connected to your agent. For each: what does the description say? Why would the LLM call this one vs another?
  • What constraint in the system prompt prevents the agent from hallucinating a book ID? Copy the exact sentence.
  • Which memory node did you use? What is the session ID expression? What happens if two users chat simultaneously without a session ID?
  • Run the agent with: "How many unread books do I have?" — look at the execution log. How many tool calls did it make? Were they the ones you expected?
  • What would you change in the system prompt if the agent keeps calling list_books when the user only says hello?

Practical work

Build the Reading List assistant (practical)
Build the full Reading List assistant: Chat Trigger → AI Agent Node (Claude) with 5 tool nodes (list_books, get_book, add_book, update_status, get_stats) + Window Buffer Memory. Write the system prompt with at least two explicit constraints. Test with 5 different user queries.
  • All 5 tool nodes have descriptive names (underscores, no spaces) and accurate descriptions
  • The system prompt includes an explicit constraint preventing ID hallucination
  • The agent correctly routes at least 4 of 5 test queries to the right tool
Upgrade to Postgres memory (practical)
Replace Window Buffer Memory with Postgres Chat Memory. Use your existing Reading List database (or a separate one). Configure a session ID so different users maintain separate histories. Verify: start a conversation, note the context, restart n8n or clear the buffer, start a new chat — history should persist in Postgres.
  • Postgres Chat Memory is connected with a valid PostgreSQL credential
  • Session ID is set to an expression (not a static string) that uniquely identifies the chat session
  • Conversation history persists across a workflow restart
Analyse your system prompt (reflect)
Review your system prompt critically. Find one ambiguity that could cause the agent to make a mistake. Rewrite that part to remove the ambiguity. Test the before and after with a query that would have triggered the problem.
  • You identified a specific ambiguity (not just "it could be clearer")
  • Your rewrite addresses the specific failure mode you identified
  • You tested with a query that distinguishes old vs new behaviour
