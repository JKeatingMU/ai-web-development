Chatbot vs Agent

Both use an LLM. The difference is structure: a chatbot answers one question and stops. An agent pursues a goal across multiple steps, taking actions and observing their effects.

Chatbot User sends message → LLM responds → done. Single turn. No memory of actions. No tools. No loop.

Agent Goal defined → [reason → act → observe] → [reason → act → observe] → goal reached. Multi-step loop. Persistent context. Tool calls. Exit condition.

The word agentic describes any system with this loop — the LLM decides what to do next based on what it observes.

Concrete example: "Find me the three best-reviewed books on machine learning" — a chatbot guesses from training data; an agent searches, fetches review scores, ranks them, and returns a justified answer.

Four Components of Every Agent

Every agent system — from a simple research helper to a complex orchestration pipeline — is built from the same four parts.

ComponentWhat it doesExample
LLMThe reasoning engine — reads the goal, decides what to do next, interprets tool resultsClaude, GPT-4o, Gemini
ToolsFunctions the LLM can call — search the web, read a file, query a database, call an API, send an emailget_book_status, web_search
MemoryThe conversation history passed to the LLM each turn (in-context) plus optional external storage (database, vector store)messages array, PostgreSQL
ObjectiveThe goal the agent is trying to reach — usually the user's original request, plus any system instructions"Summarise all unread books and email the list"

Remove any one of these and the system stops being agentic. No tools = chatbot. No loop = one-shot generation. No objective = random wandering.

The ReAct Loop: Reason → Act → Observe

ReAct (Yao et al., 2022) describes the pattern at the heart of most production agents: the LLM reasons, acts, then incorporates what it observes before reasoning again.

Goal: "Which books on my reading list are unread?"
─────────────────────────────────────────────────────
Thought:  I need to query the reading list API for unread books.
Action:   get_books({ status: "unread" })
Observe:  [{ title: "DDIA", author: "Kleppmann" }, { title: "SICP", ... }]
─────────────────────────────────────────────────────
Thought:  I have the list. I can now answer the user directly.
Action:   respond({ answer: "You have 2 unread books: DDIA and SICP." })
─────────────────────────────────────────────────────
Done.

Each iteration adds to the messages array. The LLM always sees the full history — goal, all actions taken so far, all observations received. This is how it "knows what it has already tried."

What Are "Tools"?

Tools are typed function definitions you provide to the LLM. The LLM decides which tool to call and with what arguments — you execute the function and return the result. The LLM never runs code directly.

You define (JSON Schema)

{
  name: "get_book_status",
  description: "Look up a book
    in the reading list by title",
  input_schema: {
    type: "object",
    properties: {
      title: {
        type: "string",
        description: "Book title"
      }
    },
    required: ["title"]
  }
}

LLM returns (tool_use block)

{
  type: "tool_use",
  id: "toolu_01...",
  name: "get_book_status",
  input: {
    title: "Designing Data-
      Intensive Applications"
  }
}

// Your code: run the DB query,
// return the result, continue loop

The Agent Loop in Node.js

This is the essential structure — every production agent is a variation of this pattern.

async function runAgent(userGoal) {
  const messages = [{ role: 'user', content: userGoal }];

  for (let i = 0; i < 5; i++) {           // ← max 5 iterations (exit condition)
    const response = await claude.messages.create({
      model: 'claude-haiku-4-5-20251001', tools, messages
    });

    if (response.stop_reason === 'end_turn') break; // ← LLM is done

    const toolResults = [];
    for (const block of response.content) {
      if (block.type === 'tool_use') {             // ← Act
        const result = await executeTool(block.name, block.input);
        toolResults.push({ type: 'tool_result', tool_use_id: block.id, content: result });
      }
    }
    messages.push({ role: 'assistant', content: response.content }); // ← history
    messages.push({ role: 'user', content: toolResults });           // ← Observe
  }
  return messages;
}

Three things to find in any agent code: (1) the loop with a max_iterations limit, (2) the tool execution block, (3) where results are appended to messages.

Agent Patterns: How Agents Are Structured

Single-agent, multi-agent, human-in-the-loop — three patterns for three different kinds of problem.

Single Agent

One LLM, a set of tools, one goal. The simplest agentic architecture — and the right choice for most tasks.

Good for

  • Research tasks: "Find all unread books tagged 'CS theory'"
  • Document processing: "Summarise this article and extract key claims"
  • Anything that fits in one context window with its tools
  • Tasks where the full reasoning chain is auditable in one place

Limits

  • Context window fills up on long tasks
  • One model handles all reasoning — no specialisation
  • Cannot parallelise independent subtasks
  • Slow on complex multi-step workflows

Start here. Build the simplest agent that could work. Add complexity only when you have hit a concrete limit.

Multi-Agent Systems

An orchestrator agent breaks the goal into subtasks and delegates them to specialist agents. Each specialist has a limited, focused tool set.

Orchestrator
    ├── Research Agent  ── tools: web_search, fetch_url
    ├── Writer Agent    ── tools: draft_text, check_facts
    └── Reviewer Agent  ── tools: compare_versions, flag_issues

When to use Task too long for one context window. Independent subtasks that can run in parallel. Need specialist reasoning at each step (e.g. research vs writing vs reviewing are genuinely different).

Warning

Added complexity Orchestrator can misroute. Specialists can disagree. Errors propagate across agents. Debugging requires tracing the full chain. Start single-agent.

Human-in-the-Loop

The agent proposes an action; a human approves or rejects it before execution. Required for any irreversible or high-stakes action.

Warning

Actions that must have a human gate

  • Sending emails or Slack messages
  • Deleting or modifying production records
  • Deploying to a live environment
  • Spending real money (API calls with cost, purchases)

Three levels of autonomy

  • Full autonomy — agent acts immediately (safe for low-stakes reads)
  • Approval gate — agent proposes, human clicks approve (n8n "Wait" node)
  • Human reviewer — agent drafts, human edits before anything is sent

n8n (E2–E4) makes human-in-the-loop straightforward: pause a workflow, send a notification, resume when a human responds.

Four Agent Failure Modes

Agents fail in characteristic ways. Knowing these before you build saves debugging hours.

FailureCauseMitigation
Infinite loopNo exit condition — tool calls keep triggering new tool callsmax_iterations limit + hard timeout
Hallucinated argumentsLLM invents parameter values not present in context (a book ID that doesn't exist)Validate inputs before executing the tool; return a clear error if invalid
Context overflowHistory grows until early context is truncated — agent "forgets" the original goalSummarise history periodically; use external memory for long tasks
Confident wrong answerAgent completes its loop and reports success — but achieved the wrong goalOutput schemas; structured assertions on result; human review gates

The most dangerous failure is the last one — the agent is confident. Add structured output validation to catch wrong-but-plausible results before they propagate.

How to Read Agentic Code

When you encounter an agent codebase — whether AI-generated or human-written — work through these five questions before trusting the system.

  • 1 — Where is the loop? Find the for or while that drives the agent. What is the exit condition? What enforces the maximum iteration count?
  • 2 — What are the tools? List every tool definition. For each: what can it read? What can it modify? Is any tool destructive or irreversible?
  • 3 — Where is memory stored? Is the messages array the only memory, or is there a database? What happens to context when the array grows large?
  • 4 — What happens on tool failure? Find the error handling inside executeTool. Does a failed tool call stop the agent or return an error observation?
  • 5 — Is there a human gate? Before any irreversible action, is there an approval step? If not — should there be?

Agent, or Something Simpler?

Agents add real complexity. Use the simplest tool that solves the problem.

SituationRight toolWhy
Fixed sequence of API calls, same every timeJust write the codeNo reasoning needed — deterministic sequence is simpler and faster
Different paths depending on a condition you can enumerateif/else or switchExplicit logic is more auditable and reliable than LLM decision-making
One external API call with a known schemafetch() + a promptNo loop needed — one-shot generation with the API result in context
Need to decide which of several tools to use based on ambiguous inputAgentLLM reasoning is the right tool for genuine ambiguity about what to do next
Multi-step workflow connecting APIs + AI nodes visuallyn8nVisual orchestration with human-in-the-loop nodes built in — see E2

The pattern: reach for the agent when the path is unknown at the time you write the code — not just when the data is unknown.

What You Built With vs What You Learned

If you used an AI assistant to generate an agent scaffold, work through these before moving to E2.

Questions to answer without looking at the AI's explanation
  • Where is the loop in the generated code? Copy the line that limits iterations.
  • List every tool in the tools array. For each: what does it read or write?
  • Trace one complete iteration: find the Thought, the Action, and the Observe.
  • Find the stop_reason check. What happens if the LLM never returns end_turn?
  • Is there any irreversible action in the tool list? If so, is there a human gate?

The goal is not to memorise syntax. It is to be able to answer "what does this agent do, how does it stop, and what could go wrong?" for any agent code you are asked to trust.

Practical work

Map an agent loop (practical)
Find or generate a simple agent implementation (Node.js or Python). Draw a diagram showing: the loop, every tool call in one iteration, where the observation goes, and what stops the loop. Annotate the code with these labels.
  • You identified the loop and its exit condition in the actual code
  • You named every tool and described what it reads or writes
  • You traced at least one full Reason → Act → Observe iteration in the messages array
Agent or something simpler? (reflect)
Take a feature you have built or plan to build in this course. Decide: should it be an agent, a fixed sequence of API calls, or an if/else branch? Write a short justification for your decision using the criteria from slide 13.
  • You named the specific decision criterion that determined your choice
  • If you chose "agent": you identified which part of the task is genuinely ambiguous at code-write time
  • If you chose something simpler: you explained why deterministic logic is sufficient here
Identify the failure modes (practical)
Review an agent you have built or found online. For each of the four failure modes (infinite loop, hallucinated arguments, context overflow, confident wrong answer): assess whether the agent is protected. Note any gap.
  • You checked for a max_iterations or equivalent limit
  • You checked whether tool inputs are validated before execution
  • You identified whether any tool is irreversible and whether there is a human gate
