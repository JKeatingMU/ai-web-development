Why Version Control?

Without git, projects look like this:

project folder without git
project/ server.js server_old.js server_backup.js server_WORKING.js server_REAL_v2.js server_REAL_v3_FIXED.js server_v3_FINAL.js server_v3_FINAL_actually.js server_DO_NOT_DELETE.js
  • HistoryEvery saved state is accessible forever. No more backup copies — git is the backup.
  • RollbackBreak something? Revert to any previous commit in seconds.
  • CollaborationMultiple people work on the same codebase without overwriting each other.
  • Blamegit log shows who changed what and when — invaluable for debugging.
Git tracks changes, not files — every commit is a snapshot of your whole project.

Git's Mental Model — Three Zones

Working Tree
Where you edit files. Changes here are untracked until you git add them.
Staging Area
A holding area. You choose exactly which changes go into the next commit — file by file if needed.
Commit History
The permanent record. Each commit has a unique hash, a message, and a pointer to its parent.

Install & First-Time Setup

install git
# Check if already installed $ git --version git version 2.44.0 # macOS (Homebrew) $ brew install git # Windows (winget) $ winget install Git.Git # Ubuntu / Debian $ sudo apt install git
one-time global config
$ git config --global user.name "Your Name" $ git config --global user.email "you@example.com" $ git config --global init.defaultBranch main
  • --versionIf this prints a version number, git is installed. macOS ships with a basic version via Xcode CLI tools.
  • user.name / emailAttached to every commit you make. Use the same email as your GitHub account so commits link to your profile.
  • defaultBranchSets new repos to use main instead of the legacy master default.
  • ~/.gitconfigAll --global settings are stored here. One file, applies to every repo on the machine.
These go in ~/.gitconfig — only do this once per machine. Check with git config --global --list.

Starting a Project

new project from scratch
# Start a brand-new repo $ mkdir my-project && cd my-project $ git init Initialized empty Git repository in .git/ $ echo "# My Project" > README.md $ git add README.md $ git commit -m "Initial commit" [main (root-commit) a1b2c3d] Initial commit 1 file changed, 1 insertion(+) # Copy an existing repo instead $ git clone https://github.com/you/my-project.git
  • git initCreates a hidden .git/ directory — this is the entire repository. Delete .git/ to un-git a project.
  • git addMoves changes from the working tree to the staging area. Required before every commit.
  • git commit -mTakes a snapshot of staged changes. The -m flag sets the message inline.
  • git cloneDownloads an existing repo and sets up origin automatically. The alternative to git init.

The Daily Commit Workflow

everyday git commands
# What has changed since last commit? $ git status On branch main Changes not staged for commit: modified: server.js # See exactly what changed line by line $ git diff # Stage a specific file $ git add server.js # Stage everything changed $ git add . # Commit with a message $ git commit -m "Add pagination to GET /api/books"
  • git statusThe command to run first, always. Shows modified, staged, and untracked files at a glance.
  • git diffShows exact line-by-line changes in unstaged files. git diff --staged shows staged changes.
  • git add .Stages everything in the current directory. Convenient but check git status first.
Good commit messages: present-tense imperative. "Add pagination" — not "Added pagination" or "pagination stuff".

Reading History

git log and show
# Compact one-line log $ git log --oneline a1b2c3d Add DELETE /api/books/:id route 9f8e7d6 Add pagination to GET /api/books 3c2b1a0 Initial commit # Visualise branches $ git log --oneline --graph --all * a1b2c3d Add DELETE route * 9f8e7d6 Add pagination | * f4e5d6c feature/add-auth: Add JWT |/ * 3c2b1a0 Initial commit # Inspect a specific commit $ git show 9f8e7d6 # What changed since the last commit? $ git diff HEAD~1
  • --onelineCompact view: short hash + message. Fits many commits on screen. Good for a quick audit.
  • --graph --allASCII art branch diagram. Shows where branches diverge and merge across the whole repo.
  • git showFull details of one commit: author, date, message, and the diff. Uses the short hash.
  • HEAD~1HEAD means the current commit. HEAD~1 is one commit back, HEAD~2 is two, and so on.

Undoing Things Safely

safe undo commands
# Discard unstaged changes in a file $ git restore server.js # Unstage a file (undo git add) $ git restore --staged server.js # Undo a commit safely — adds a new "undo" commit # Does NOT rewrite history — safe on shared branches $ git revert a1b2c3d [main b4c5d6e] Revert "Add DELETE /api/books/:id route" # DANGER — discards all uncommitted changes permanently # git reset --hard HEAD
  • git restoreDiscard changes in the working tree. The file goes back to how it was at the last commit. Irreversible for those edits.
  • --stagedMoves a file back out of the staging area without touching the file contents. Safe — your edits are preserved.
  • git revertThe safe undo. Creates a new commit that reverses the named one. History is preserved — teammates see the revert.
Avoid git reset --hard until you understand it — it discards uncommitted work permanently.

Branches

branch commands
# Create a new branch and switch to it $ git checkout -b feature/add-auth Switched to a new branch 'feature/add-auth' # List all local branches $ git branch * feature/add-auth main # Switch back to main $ git checkout main # Delete a branch (after it's merged) $ git branch -d feature/add-auth
  • BranchJust a pointer to a commit — creating one is instant and costs almost nothing. Git is built for branching.
  • checkout -bCreate + switch in one step. The modern equivalent is git switch -c — both work.
  • git branchLists branches. * marks the current one. -a includes remote branches.
  • -dDelete a branch that has been merged. Use -D to force-delete an unmerged branch.
Convention — main for stable, always-deployable code. Feature branches for everything else. Never commit untested code directly to main.

Merging & Conflicts

merge and conflict resolution
# Merge feature branch into main $ git checkout main $ git merge feature/add-auth Auto-merging server.js CONFLICT (content): Merge conflict in server.js Automatic merge failed; fix conflicts and commit. # Inside server.js — conflict markers: <<<<<<< HEAD app.use(express.json()); ======= app.use(express.json({ limit: '10mb' })); >>>>>>> feature/add-auth # After editing — remove markers, save, then: $ git add server.js $ git commit -m "Merge feature/add-auth into main"
  • git mergeIntegrates changes from one branch into another. Run it while on the destination branch.
  • ConflictHappens when both branches changed the same lines. Git cannot decide which version to keep — you must.
  • <<< / === / >>>HEAD = your current branch. Below ======= = the incoming branch. Delete the markers and keep what you want.

GitHub — Remotes & Pushing

connecting to GitHub
# After creating a repo on GitHub: $ git remote add origin https://github.com/you/my-project.git # First push — -u sets the upstream tracking $ git push -u origin main Branch 'main' set up to track remote branch 'main' from 'origin'. # Subsequent pushes (no flags needed) $ git push # Download + merge remote changes $ git pull # List remotes $ git remote -v origin https://github.com/you/my-project.git (fetch) origin https://github.com/you/my-project.git (push)
  • remoteA named URL. origin is the conventional name for the primary remote — set it once, use forever.
  • git push -uThe -u flag links your local branch to the remote branch so future git push/git pull need no arguments.
  • git pullShorthand for git fetch + git merge. Downloads remote commits and merges them into your local branch.
  • HTTPS vs SSHHTTPS works anywhere. SSH is more convenient if you set up a key. GitHub's docs cover both.
Clone = remote + copy in one step. git clone <url> sets up origin automatically.

GitHub Pages — Free Static Hosting

publish from docs/ folder
# 1. Push your repo to GitHub as usual $ git push # 2. In GitHub: Settings → Pages # Source: branch = main # Folder = /docs # Click Save # 3. After ~1 minute, your site is live: https://username.github.io/repo-name/ # 4. Every push to main auto-deploys $ git push # → site updates within seconds
  • GitHub PagesServes static files (HTML, CSS, JS) directly from a branch and folder. No server needed.
  • docs/ folderThe /docs option lets you keep source code in root and publishable content in docs/ — ideal for course material.
  • Auto-deployEvery push to the configured branch triggers a redeploy. No CI setup required for static sites.
  • Custom domainAdd a CNAME file to docs/ and configure your DNS to point to GitHub Pages.
All the decks in this course are plain HTML — no build step. GitHub Pages works out of the box.

Pull Requests

PR workflow
# 1. Create a feature branch and do your work $ git checkout -b feature/pagination # ... edit files, commit ... # 2. Push the branch to GitHub $ git push -u origin feature/pagination # 3. Open a Pull Request on GitHub # Compare: feature/pagination → main # Add title, description, reviewers # 4. After review + CI pass → Merge # 5. Delete the branch $ git branch -d feature/pagination
  • Pull RequestA proposal to merge one branch into another. Named "PR" on GitHub, "MR" (Merge Request) on GitLab — same concept.
  • Code reviewTeammates comment on specific lines. Discussion happens in the PR thread before anything merges to main.
  • CI checksGitHub Actions (or other CI) can run tests automatically on every PR. Green checks required before merge.
  • Fork workflowFor open source: fork the repo, work on your fork, open a PR from fork → upstream. Git handles the cross-repo diff.

.gitignore — What Git Should Never Track

.gitignore for a Node.js project
# .gitignore node_modules/ .env dist/ .DS_Store *.log # If you accidentally staged .env already: $ git rm --cached .env rm '.env' # Then add to .gitignore and commit: $ git add .gitignore $ git commit -m "Remove .env from tracking"
  • node_modules/Hundreds of megabytes of installed packages. Never commit — regenerate with npm install.
  • .envContains database URLs, API keys, JWT secrets. One leaked secret can compromise an entire system.
  • dist/Build output — generated from source. Commit the source, not the output.
  • *.logGlob pattern. The * wildcard matches any filename ending in .log.
  • git rm --cachedStops tracking a file without deleting it from disk. Use this if you accidentally staged a secret.
Never commit .env — it contains secrets. Add it to .gitignore before your first commit. If a secret reaches a public repo, assume it is compromised — rotate it immediately.
