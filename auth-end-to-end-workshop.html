Authentication spans both layers — the backend issues and verifies tokens, the frontend stores and sends them. This deck traces the complete flow from registration through logout and covers the most common wiring mistakes that appear when both sides are generated by AI.

The Complete Auth Flow

Four operations. Each one has a distinct frontend action, a backend operation, and a specific outcome. Understanding all four prevents half of all auth bugs.

OperationFrontend actionBackend operationOutcome
Register Submit email + password form → POST /auth/register Hash password with bcrypt, insert user row 201 Created — frontend redirects to /login (does not store token)
Login Submit credentials → POST /auth/login Find user, compare bcrypt hash, sign JWT 200 + { token } — frontend stores token, navigates to /
Protected request Component mounts → reads token → sends Authorization: Bearer <token> Middleware verifies JWT signature and expiry, attaches req.user 200 + data — OR 401 if token missing / invalid / expired
Logout localStorage.removeItem('token') → navigate to /login replace No server call needed (JWTs are stateless) Token removed from browser — ProtectedRoute redirects on next visit
Common mistake: storing the token after registration (not just login). Registration confirms the account was created — the user still needs to prove their identity by logging in.

Registration — Frontend to Backend

Registration is the simpler of the two forms — no token storage, no redirect to a protected page. The only success action is navigating to the login page.

RegisterPage.tsx
const navigate = useNavigate(); const [form, setForm] = useState({ email: '', password: '', confirm: '', }); const [error, setError] = useState(''); const [loading, setLoading] = useState(false); async function handleSubmit(e: FormEvent) { e.preventDefault(); // Client-side guard — passwords match if (form.password !== form.confirm) { setError('Passwords do not match'); return; } setLoading(true); try { await api.post('/auth/register', { email: form.email, password: form.password, }); // Success — go to login, do NOT store a token navigate('/login'); } catch (err) { setError(err instanceof Error ? err.message : 'Registration failed'); } finally { setLoading(false); } }
No token storage on register. Your backend returns 201 with no body (or just { message: "Created" }). There is no token to store. AI sometimes generates localStorage.setItem('token', data.token) here — check for it.
Password confirmation is client-only. The backend receives only email and password — it does not receive confirm. The match check is a UX guard, not a security measure.
Uniform error messages on the backend: whether the email is invalid, already taken, or the password too short — return the same generic message ("Registration failed") rather than "Email already taken". This prevents email enumeration — an attack where an adversary probes your API to discover which email addresses are registered by reading different error messages for different failure modes.
After registration, navigate to /login without replace — pressing Back to review the registration form is acceptable behaviour, unlike the post-login case.

Login — Storing the Token

Login is the critical path. The token must be stored before navigating — in the right key, with the right navigate options, and with the NavBar updated to reflect the new auth state.

LoginPage.tsx
async function handleSubmit(e: FormEvent) { e.preventDefault(); setLoading(true); setError(''); try { const { token } = await api.post<{ token: string }>( '/auth/login', { email: form.email, password: form.password } ); // Store before navigating localStorage.setItem('token', token); // replace: true — Back won't return to /login navigate('/', { replace: true }); } catch (err) { // Uniform message — don't reveal which field is wrong setError('Invalid email or password'); } finally { setLoading(false); } } // ───────────────────────────────────────────── // Backend returns // POST /auth/login → 200 { token: "eyJ..." } // POST /auth/login → 401 { error: "Invalid credentials" }
Store before navigate. navigate causes React to unmount LoginPage and mount the next page. If you navigate first, the store call on the now-unmounted component may not execute.
Uniform error message: "Invalid email or password" — never "Email not found" or "Wrong password". Distinguishing them tells attackers which half of the credentials is correct.
The token key must be consistent. localStorage.setItem('token', ...) in LoginPage must exactly match localStorage.getItem('token') in ProtectedRoute, NavBar, and api.ts. AI sometimes uses different key names across files.
Check the token is a string. Some AI-generated backends wrap the token: { data: { token: "..." } }. If you destructure { token } from that response, you get undefined. curl the endpoint to check the exact shape.

Making Authenticated Requests

Every request to a protected endpoint must carry the token in the Authorization header. Your api.ts handles this automatically — but only if the token key is consistent and the backend middleware reads the same header.

Frontend — api.ts sends the token

api.ts
function getHeaders(): HeadersInit { const token = localStorage.getItem('token'); return { 'Content-Type': 'application/json', ...(token ? { 'Authorization': `Bearer ${token}` } : {}), }; }

Backend — middleware verifies it

middleware/authenticate.js
export function authenticate(req, res, next) { const header = req.headers['authorization']; if (!header?.startsWith('Bearer ')) { return res.status(401).json({ error: 'No token provided', }); } const token = header.slice(7); try { req.user = jwt.verify(token, process.env.JWT_SECRET); next(); } catch { res.status(401).json({ error: 'Invalid token' }); } }
The Bearer prefix must match exactly. Frontend sends Bearer <token>. Backend slices 7 characters off ("Bearer " is 7 chars). If the prefix is wrong, the token extracted from the header is corrupted.
Header names are case-insensitive in HTTP but Express normalises them to lowercase. Access with req.headers['authorization'] (lowercase) — not req.headers['Authorization'].
jwt.verify throws on expiry. The catch block returns 401, which triggers api.ts's global 401 handler, which removes the token and redirects to login. The user flow is automatic.
After middleware: req.user contains the JWT payload ({ id, email, iat, exp }). Route handlers access the current user's ID via req.user.id — no need to pass it in the request body.

Token Lifecycle and Expiry

JWTs expire. When a token expires mid-session, the user's next API call returns 401. Your app needs to handle this gracefully — not crash with an unhandled error.

api.ts — global 401 handler
// When any API call returns 401: // 1. Remove the expired token // 2. Redirect to /login // 3. Throw so the calling code's catch fires if (res.status === 401) { localStorage.removeItem('token'); window.location.href = '/login'; throw new Error('Session expired'); } // ───────────────────────────────────────────── // Backend — signing with expiry const token = jwt.sign( { id: user.id, email: user.email }, process.env.JWT_SECRET, { expiresIn: '24h' } // or '7d', '1h' ); // ───────────────────────────────────────────── // Reading expiry in the browser (without a library) function tokenExpiresAt(token: string): Date { const payload = JSON.parse( atob(token.split('.')[1]) ); return new Date(payload.exp * 1000); }
24h is a reasonable starting expiry. Shorter is more secure but more disruptive. Longer is convenient but a stolen token stays valid longer. For a learning project, 24h is fine.
window.location.href vs navigate: the 401 handler in api.ts runs outside React, so it can't use the Router's navigate hook. A full page redirect via window.location.href is the pragmatic solution.
Decoding the JWT client-side doesn't verify the signature — it just reads the payload. This is fine for reading expiry or the user's name for display. Never trust client-side decoded data for access control.
Refresh tokens are the production solution to expiry — a long-lived token that exchanges for a new short-lived JWT. For a learning project, sending the user back to login on expiry is perfectly acceptable.

NavBar Auth State

The NavBar needs to show different content to logged-in and logged-out users. Since the token lives in localStorage — not React state — you need a small state bridge.

NavBar.tsx
import { NavLink, useNavigate } from 'react-router-dom'; function NavBar() { // Re-read token on every render — it may change const isLoggedIn = !!localStorage.getItem('token'); const navigate = useNavigate(); function handleLogout() { localStorage.removeItem('token'); navigate('/login', { replace: true }); } return ( <nav> <NavLink to="/" end>Home</NavLink> {isLoggedIn ? ( <> <NavLink to="/books">My Books</NavLink> <button onClick={handleLogout}>Log out</button> </> ) : ( <> <NavLink to="/login">Log in</NavLink> <NavLink to="/register">Register</NavLink> </> )} </nav> ); }
The NavBar re-reads localStorage on every render. When the user logs in, React re-renders the Layout (which contains NavBar), and the new render picks up the token. No extra state management needed for this simple case.
If the NavBar doesn't update after login: the Layout may not be re-rendering. The navigate call in LoginPage causes a route change, which unmounts LoginPage and mounts the new page — Layout stays mounted but doesn't re-render unless its state or props change. Use a useAuth hook (next slide) to fix this properly.
Logout uses replace: true: pressing Back after logging out should not return to a protected page (the ProtectedRoute would redirect back to login anyway, but replace prevents the confusing back-redirect loop).

The useAuth Hook — Centralising Auth State

Reading localStorage directly in every component that needs auth state creates scattered, unsynchronised logic. A useAuth hook centralises it and ensures all components update together.

hooks/useAuth.ts
import { useState, useCallback } from 'react'; import { useNavigate } from 'react-router-dom'; export function useAuth() { // Initialise from localStorage — survives page refresh const [token, setToken] = useState<string | null>( () => localStorage.getItem('token') ); const navigate = useNavigate(); const login = useCallback((newToken: string) => { localStorage.setItem('token', newToken); setToken(newToken); // triggers NavBar re-render navigate('/', { replace: true }); }, [navigate]); const logout = useCallback(() => { localStorage.removeItem('token'); setToken(null); navigate('/login', { replace: true }); }, [navigate]); return { token, isLoggedIn: !!token, login, logout, }; } // Usage in LoginPage const { login } = useAuth(); // on success: login(token); // stores + navigates atomically
State + localStorage together: the hook updates both simultaneously. React state causes component re-renders; localStorage persists across page refreshes. You need both.
Lazy initialiser: useState(() => localStorage.getItem('token')) runs the function once on mount — avoids reading localStorage on every render while still catching a token from a previous session.
For shared state across many components, lift useAuth to a Context provider so all components share the same token state without prop drilling. For small apps the hook alone is sufficient.
This hook is what AI should generate when you ask for "a complete auth integration". If it gives you scattered localStorage reads instead, ask it to refactor into a useAuth hook.

Scaffold Prompt — Full Auth Integration

✎ Scaffold prompt — paste into your AI assistant
Add complete auth integration to my Reading List app. The backend already has POST /auth/register and POST /auth/login endpoints and a JWT authenticate middleware. The frontend uses api.ts with a generic request<T> function and a global 401 handler that removes the token and redirects to /login. Generate:
  • A useAuth hook (hooks/useAuth.ts) with login(token), logout(), and isLoggedIn. It must: initialise from localStorage.getItem('token') on mount, update both localStorage and React state atomically on login and logout, use useNavigate with replace: true for both redirects

Prompt Reflection

Auth bugs are often invisible until a specific sequence of actions triggers them. Reflect on the integration you built.

The token key problem:
The localStorage key must be consistent across at least four files: api.ts, LoginPage.tsx, ProtectedRoute.tsx, and useAuth.ts. Did the AI generate a consistent key? What would you add to your scaffold prompt to enforce this?
State vs storage:
The useAuth hook stores the token in both React state and localStorage. What happens if you only use localStorage (no React state)? What happens if you only use React state (no localStorage)? When would each approach break?
Security check:
Open DevTools → Application → localStorage. You can see your JWT. Open a JWT decoder and paste the token. What is in the payload? What would happen if you modified a field in the payload and sent the modified token to the API?
Sequence matters:
The login flow is: validate → call API → store token → navigate. If you swap the last two steps (navigate then store), what breaks? Have you tested this by temporarily swapping the order in your code?
