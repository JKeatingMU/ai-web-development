The Framework

Four Types of Infrastructure Prompt

Every interaction with an AI coding assistant falls into one of four categories. Recognising which type you need makes your prompts sharper.

TypeIntentTrigger phraseExample
Scaffold Generate something from scratch "Generate / Create / Give me..." "Generate a PostgreSQL schema for a reading list with these fields..."
Explain Understand what was generated "Explain / Why does / What does..." "Why use COALESCE here instead of just passing the value?"
Debug Fix something that isn't working "I'm getting an error / This isn't working..." "I'm getting 'could not determine data type of parameter $8' — here is my query..."
Extend Add a feature to working code "Add / Now also / Update this to..." "Add rate limiting to the login route — max 5 attempts per IP per 15 minutes."
The workflow: Scaffold → Explain → (run it) → Debug if needed → Extend. Never ask for everything at once. Complete each step before moving to the next.
Part 1

Database Schema Design

Prompting for SQL — and understanding every constraint, type, and index the AI gives you.

Prompt Type: Scaffold

Prompting for a Database Schema

✦ Prompt — schema scaffold
Write a PostgreSQL CREATE TABLE statement for a reading list app. A book has:
  • title (text, required) and author (text, required)
  • status: one of 'want-to-read', 'reading', 'done' — enforced by the database
  • rating: integer 1–5, optional — enforced by the database
  • notes: free text, optional
  • created_at: set automatically by the database
Use IF NOT EXISTS. Add a CHECK constraint for status and rating. Add an index on status. Explain each constraint in a comment.
What makes this prompt work:
  • Lists every field with type and constraints
  • Specifies which constraints live in the DB (not just the app)
  • Asks for IF NOT EXISTS — safe to run repeatedly
  • Asks for an index — the AI won't add one unless prompted
  • Asks for explanatory comments — forces explanation
Rule: Always specify which constraints should be database-level. Left to defaults, an AI will often only validate in application code — which means constraints are bypassed if you ever use a migration tool, import script, or admin query directly.
Prompt Type: Explain

Understanding What Was Generated — Follow-up Prompts

✦ Explain: SERIAL vs INTEGER
Why use SERIAL for the id column? What's the difference between SERIAL, INTEGER, and BIGSERIAL? When would I need BIGSERIAL?
◎ AI response (summary)
SERIAL = auto-incrementing integer (1, 2, 3…). Shorthand for creating a sequence + default.
INTEGER = plain integer — you'd supply the id yourself.
BIGSERIAL = 64-bit — use when you might exceed ~2 billion rows. For most apps, SERIAL (32-bit, ~2B rows) is fine.
✦ Explain: indexes
When should I add an index to a column? What's the cost? Why did you add one on status but not title?
◎ AI response (summary)
Add an index on columns you filter or sort by frequently.
Cost: extra disk space + slower writes (index must update on INSERT/UPDATE).
status — likely used in WHERE clauses (?status=reading).
title — full-text search needs a different index type (GIN); a B-tree index on title rarely helps.
Always ask "why" for every generated constraint, type, and index. This is not just good practice — it is how you learn database design. An AI that cannot explain its own output is a warning sign.
Part 2

Environment Configuration

Prompting for .env files, package.json, .gitignore — the scaffolding that surrounds every project.

Prompt Type: Scaffold

Prompting for Project Configuration Files

✦ Prompt — project config
For a Node.js + Express + PostgreSQL API project using ES modules, generate:
  • package.json with scripts: start (node server.js) and dev (node --watch server.js)
  • Dependencies: express, pg, dotenv, bcrypt, jsonwebtoken
  • .env.example with DATABASE_URL, PORT, and JWT_SECRET — with a comment explaining each
  • .gitignore that ignores node_modules, .env, and any OS junk files
Explain why .env must never be committed but .env.example should be.
The .env / .env.example split is critical:
  • .env — real secrets, never committed
  • .env.example — template, always committed
  • One accidental git add .env exposes your database to the world
The "explain why" instruction:
Adding "explain why" to a scaffold prompt forces the AI to justify its choices. If it cannot explain why .env should be gitignored, it should not be generating your security configuration.
Generate a strong JWT_SECRET:
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
Ask the AI to include this command in its output.
Part 3

JWT Authentication Setup

Prompting for auth step-by-step — registration, login, middleware. Getting the security details right.

Prompt Type: Scaffold — in stages

Prompting for JWT Auth — Don't Ask for Everything at Once

✦ Prompt 1 — Schema
Add a users table to my PostgreSQL schema.

Fields: id (serial), email (unique, not null), password_hash (not null), created_at (auto).

Explain why we store password_hash and not password.
✦ Prompt 2 — Routes
Add POST /auth/register and POST /auth/login routes to my Express app.

Use bcrypt (12 salt rounds) to hash passwords. On login, sign a JWT with {sub, email}, expiring in 24h.

Handle duplicate email with 409. Use the same error message for wrong email and wrong password.
✦ Prompt 3 — Middleware
Create an authenticate middleware function that:

Reads Authorization: Bearer <token> from the request header.
Calls jwt.verify() and attaches the decoded payload to req.user.
Returns 401 if missing or invalid.

Show me how to add it to a route.
Why three prompts, not one? Each step builds on a working foundation. Testing after each prompt means if something breaks, you know exactly which step caused it. One giant prompt often produces subtly wrong code that is hard to diagnose.
Prompt Type: Explain — security details

Prompting to Verify the Security Details

AI-generated auth code is usually correct at the surface. These follow-up prompts verify the details that matter most.

✦ Verify: same error message
In the login route, why should "user not found" and "wrong password" return the same error message? What attack does this prevent?
✦ Verify: jwt.verify vs jwt.decode
What is the difference between jwt.verify() and jwt.decode()? Why would using jwt.decode() for authentication be a critical security mistake?
✦ Verify: bcrypt salt rounds
Why does bcrypt take a salt rounds parameter? What are the tradeoffs between 10, 12, and 14 rounds?
User enumeration attack:
If "email not found" returns a different message to "wrong password", an attacker can confirm which emails are registered — before even trying to crack passwords.
jwt.decode() skips signature verification.
It simply base64-decodes the payload. Passing it a forged token would succeed. jwt.verify() checks the HMAC signature — a token signed with a different secret throws immediately.
Salt rounds tradeoff:
Higher rounds = slower hashing = harder brute-force.
12 rounds ≈ 250ms per hash. 14 rounds ≈ 1 second.
For login, 250ms is acceptable. For a script trying millions of passwords, it is not.
Part 4

Debugging with AI Assistance

The error message is your prompt. Paste it in full. Add context. Ask for a diagnosis before a fix.

Prompt Type: Debug

How to Write a Good Debug Prompt

Weak debug prompt:
"My login isn't working."

The AI has no information to work with. It will ask clarifying questions or guess. You get generic advice that may not apply to your code.
✦ Strong debug prompt
My POST /auth/login route is returning 401 even when I provide the correct password. Here is the error from the server console:

error: could not determine data type of parameter $8

Here is the relevant SQL query: [paste query]

What is causing this and how do I fix it?
A good debug prompt contains:
  • The exact error message — copy it verbatim
  • Which route/function is failing
  • The relevant code section
  • What you expected vs what happened
  • What you have already tried
Ask for diagnosis before fix:
"What is causing this?" before "How do I fix it?" forces the AI to reason through the problem rather than jumping to a solution. Understanding the cause means you will recognise the same error next time.
Debug — Real Examples

Common Infrastructure Errors and How to Prompt Around Them

ErrorCausePrompt pattern
could not determine data type of parameter $8 PostgreSQL cannot infer the type of a NULL parameter in a CASE expression "I have a CASE WHEN $8 IS NOT NULL... in my INSERT. PostgreSQL throws this error. Explain why and how to fix it without a CASE."
ECONNREFUSED 127.0.0.1:5432 PostgreSQL server not running, or wrong host/port in DATABASE_URL "My Node app can't connect to PostgreSQL locally. Here is my DATABASE_URL format. What should I check first?"
JsonWebTokenError: invalid signature Token was signed with a different JWT_SECRET than what is used to verify "jwt.verify() throws 'invalid signature' even on a freshly issued token. What are the possible causes?"

Cannot find module './auth.js' Missing file extension in ES module import — Node requires .js "Node ES modules require explicit .js extensions. Here is my import — what am I missing?"
Part 5

Prompting for Deployment

From working locally to live on Railway — what to ask, what to check, what AI commonly misses.

Prompt Type: Scaffold + Explain

Useful Prompts for Railway Deployment

✦ What to run first
I have a Node.js + Express + PostgreSQL app ready to deploy to Railway. Give me a step-by-step checklist of everything I need to do — from pushing to GitHub through to testing the live URL.
✦ Database migration
I have a schema.sql file with my table definitions. What is the command to run it against my Railway PostgreSQL database? The DATABASE_URL is in my environment.
✦ Environment variables
What environment variables does my app need in Railway? I use DATABASE_URL, PORT, and JWT_SECRET. Does Railway inject DATABASE_URL automatically for a PostgreSQL plugin?
What Railway injects automatically:
  • DATABASE_URL — PostgreSQL plugin connection string
  • PORT — the port your app must listen on
You must set JWT_SECRET yourself in Railway's Variables panel.
Common deployment failure:
App listens on hardcoded port 3001 instead of process.env.PORT. Railway assigns a dynamic port — the hardcoded one is never bound. Always: const PORT = process.env.PORT || 3001
What AI commonly misses:
Symlinks — if your project uses a symlink (e.g., to a shared library), Railway can't resolve it. Ask: "Are there any symlinks in my project that would prevent Railway deployment?"
The Bigger Picture

The Prompt → Test → Iterate Loop

You write a scaffold prompt (stack, fields, constraints, files, what to exclude) ↓ AI generates code ↓ You read every line Ask "explain" for anything you don't understand ↓ You run it npm install → psql schema.sql → npm run dev → curl /api/health ↓ ┌────┴─────────────┐ ↓ ↓ It works Error message ↓ ↓ Ask an extend prompt Paste the error into a debug prompt "Now add..." "I'm getting X — what's causing it?" ↓ ↓ Repeat Fix → test again
The loop is the method. The AI generates faster than you can type. Your value is the reading, the running, the testing, and the judgement about whether what came back is actually correct.
Critical Awareness

Where AI Infrastructure Code Needs Extra Scrutiny

  • ! Security defaults are often too permissive. An AI may generate CORS with origin: '*', no rate limiting on auth routes, no input length limits, and overly broad JWT payloads. Always ask: "What security hardening should I add to this?"
  • ! Error handling is often shallow. Generated code frequently propagates unhandled promise rejections or exposes raw error messages (err.message) to clients. Ask: "Does this code expose any internal errors to the client?"
  • ! SQL injection via string interpolation. AI sometimes generates template literal queries (`WHERE id = ${id}`) alongside parameterised ones. Review every single query for $ placeholders.
  • ~ Outdated package versions. An AI's training data has a cutoff. Always run npm outdated after installing generated dependencies and check for breaking changes.
  • i Missing indexes on foreign keys. AI reliably adds primary key indexes but often forgets indexes on foreign key columns, status/enum columns, and columns used in ORDER BY.
Summary

Key Takeaways

  • 1 Know your prompt type. Scaffold, Explain, Debug, or Extend. Use the right one. Don't ask for a scaffold when you need a debug.
  • 2 Specify database constraints explicitly. NOT NULL, CHECK, UNIQUE, DEFAULT — tell the AI which constraints belong in the database, not just the app. The database is the last line of defence.
  • 3 Stage your auth prompts. Schema first. Routes second. Middleware third. Test each step before adding the next.
  • 4 Paste the full error message. "It doesn't work" tells the AI nothing. The exact error text, the file, and the relevant code gives it everything it needs.
  • 5 Ask "diagnose before fix." Understanding the cause means you will recognise the same error in future, with or without AI assistance.
  • 6 Audit every security boundary the AI generates. Auth, CORS, error messages, SQL queries. These are the places where a subtle mistake has outsized consequences.
