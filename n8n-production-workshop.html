Definition

What "Production" Means for n8n Workflows

A workflow that works once in the editor is not a production workflow. Production means: it runs reliably when you are not watching, it fails gracefully, it tells you when something goes wrong, and it does not cost unpredictably.

Error Workflows: What Happens When a Node Fails

By default, when a node fails, n8n marks the execution as failed and stops. Nothing else happens — no alert, no retry. For a scheduled workflow, you will not notice until you check the execution history.

What the Error Trigger Receives

The Error Trigger node passes structured error context. Use it to build a useful alert — not just "something failed".

Fields available in the error workflow

$json.execution.error.node.nameWhich node failed

Subject: n8n workflow failed

Workflow: {{ $json.workflow.name }}
Failed node: {{ $json.execution.error.node.name }}
Error: {{ $json.execution.error.message }}
Execution ID: {{ $json.execution.id }}

Check execution history in n8n for details.
One shared error workflow can serve multiple main workflows. Each main workflow points to it in settings. The alert includes the workflow name, so you always know which one failed.
Resilience

Retry Logic: Handling Transient Failures

Some failures are transient: rate limits, temporary API unavailability, network timeouts. Retrying immediately usually works. Permanent failures (wrong URL, invalid auth) should not be retried.

n8n built-in retry

In any node settings (⚙ → Retry On Fail): set Retry On Fail to on, max retries to 3, wait between retries to 5s. n8n will retry the node automatically before marking the execution as failed.

Use for: HTTP Request nodes calling external APIs, especially those with rate limits or occasional timeouts.
When not to retry
  • ✗401 Unauthorized: retrying will not fix bad credentials — alert immediately
  • ✗400 Bad Request: the input data is wrong — a retry sends the same bad data
  • ✗Write operations: retrying a POST may create duplicate records if the first attempt partially succeeded
For writes: implement idempotency at the API level (UPSERT logic) before enabling retry.

The Wait Node: Pause Until Human Approves

The Wait node pauses the workflow execution. It generates a unique resume URL. When a human clicks that URL (via an email link, Slack button, or web form), the workflow resumes from the Wait node.

Wait node config: Resume type → "On webhook call". n8n generates a URL like https://n8n.example.com/webhook/resume/abc123. Include this URL in the draft email with [Approve] and [Reject] links. The human clicks one — the workflow resumes with the response.
Timeout: Set a maximum wait time (e.g., 24h). If the human does not respond, the workflow continues on the timeout branch — send a reminder or mark as cancelled.
Monitoring

Execution History: Your Audit Trail

Every workflow execution is recorded in n8n's Executions panel. This is your primary debugging and audit tool — use it to verify that workflows ran, inspect what data flowed, and diagnose failures.

What to check in executions
  • →Status: green (success), red (failed), grey (waiting). Any red needs investigation.
  • →Duration: if a scheduled workflow usually takes 3s and today took 45s, something is slow — likely the LLM call or an API timeout.
  • →Node output: click any node in a past execution to see exactly what data it received and what it produced.
  • →Item count: if Split Out usually produces 10 items and today produced 0, the API returned no data.
Retention settings

By default n8n retains all executions. For high-frequency workflows (every minute, large payloads), this fills disk rapidly. Set execution retention in Settings → Executions to keep only the last N executions or last N days.

Recommended: keep the last 50 executions for scheduled workflows. Keep 200 for agent workflows where debugging trace is more important.
Monitoring

Alerting: Know Before Your Users Do

The error workflow (slide 3) handles per-execution failures. For broader health monitoring — "has this workflow not run in 6 hours when it should run every hour?" — you need a watchdog.

Pattern: heartbeat workflow
  • 1Add a final node to each critical workflow: HTTP Request to a monitoring service (e.g., Uptime Robot, Better Stack, or a simple webhook you control)
  • 2The monitoring service expects a ping on a schedule. If it misses two pings → alert
  • 3This catches "workflow didn't run at all" failures — not just node errors
Minimum viable monitoring for coursework
  • →Error Workflow set for every production workflow
  • →Check Executions panel manually each morning for any red entries
  • →Add a Slack or email notification at the end of each workflow: "✓ Completed: processed N books at HH:MM"
The success notification doubles as a health check: if you expected a notification and didn't get one, the workflow failed silently or didn't run.
Cost

Managing LLM Cost in Production

LLM API calls cost per token. An agentic workflow that runs 100 times a day on 50 books each time can accumulate real cost quickly if not designed carefully.

LeverHow to apply itTrade-off
Right-size the model Use Haiku for simple summarisation; use Sonnet/Opus only for complex reasoning Haiku is ~10–20× cheaper; adequate for structured extraction
Constrain output length Set max_tokens on the LLM node — one sentence summaries don't need 4096 tokens Output tokens cost more than input; cap at 256 for short structured outputs
Filter before LLM calls IF node before the LLM — only call the LLM on items that need it (slide 5's idempotency pattern) Reduces calls proportionally to how many items already have results
Cache results Store LLM output in the database. On next run, skip items already in the DB. Works for stable data; not for tasks that need fresh reasoning each time
Set usage alerts Anthropic and OpenAI both offer spend alerts — set a monthly budget alert No performance impact; early warning before costs escalate
Architecture Decision

When n8n Outgrows Itself

n8n is excellent for orchestration. It has real limits. Know when a workflow has grown beyond what n8n handles well.

Stay in n8n when
  • ✓The workflow is primarily orchestration — connecting existing services
  • ✓Business stakeholders need to read or modify the workflow logic
  • ✓Human-in-the-loop approval is central to the design
  • ✓The team does not want to deploy and maintain custom code infrastructure
Move to code when
  • →The workflow has more than 3 Code nodes — at that point you are writing a program in a visual IDE with extra friction
  • →You need unit tests — n8n workflows are not unit-testable
  • →Performance matters — n8n adds latency per node; code runs in-process
  • →The agent logic is complex enough that the execution log is insufficient for debugging — you need a proper debugger
The hybrid pattern: use n8n for orchestration (triggers, approvals, notifications) and call your own Node.js microservice for the complex agent logic. Best of both worlds.
