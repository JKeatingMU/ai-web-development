The Two-Server Problem

In development you run two servers simultaneously. They live on different ports — and the browser's same-origin policy blocks requests between different origins. You will see this reported as a CORS error; the next slide explains exactly what CORS is and why the browser enforces it.

The symptom: your fetch call fails with a CORS error in the browser console. The API is running fine — the browser is blocking the response from reaching your code.
Two solutions: configure CORS on the Express server (production approach), or use the Vite proxy (development shortcut). You need to understand both.
In production both apps often share the same origin — Express serves the built React files. CORS becomes less of an issue, but still matters for external API consumers.

CORS — The Browser's Same-Origin Policy

CORS (Cross-Origin Resource Sharing) is a browser security mechanism. It prevents a page on one origin from reading responses from a different origin — unless the server explicitly allows it.

ScenarioSame origin?
5173 → 5173✓ Yes — allowed
5173 → 3001✗ No — different port
app.com → api.app.com✗ No — different subdomain
http → https✗ No — different scheme
app.com → app.com✓ Yes — same everything
CORS is a browser rule, not a server rule. curl and Postman are not browsers — they never enforce CORS. If your API works in curl but not in React, CORS is the likely cause.
The browser sends a preflight OPTIONS request before a POST/PATCH/DELETE with custom headers. Your server must respond correctly to the preflight or the real request never happens.
CORS headers are added to the response by the server. The browser reads them and decides whether to give the response to your JavaScript.

Configuring CORS in Express

The cors npm package adds the correct response headers. AI generates this — understand every option before deploying to production.

server/index.js
import cors from 'cors'; // Development — allow Vite dev server app.use(cors({ origin: 'http://localhost:5173', credentials: true, // allow cookies / auth headers methods: ['GET', 'POST', 'PATCH', 'DELETE'], allowedHeaders: ['Content-Type', 'Authorization'], })); // Production — use environment variable const allowedOrigin = process.env.CLIENT_URL || 'http://localhost:5173'; app.use(cors({ origin: allowedOrigin, credentials: true, methods: ['GET', 'POST', 'PATCH', 'DELETE'], allowedHeaders: ['Content-Type', 'Authorization'], }));
Never use origin: '*' with credentials: true — this is a security error. Browsers reject it. Always name your origin explicitly when sending credentials.
Authorization header must be in allowedHeaders — otherwise the browser strips it from the request before it reaches your JWT middleware.
CLIENT_URL env var — set to your deployed React app's domain in production. AI generates this pattern; it is the correct approach.

Environment Variables in Vite — The VITE_ Prefix

Your React app needs to know where the API lives. In Vite, environment variables are injected at build time — and only variables prefixed with VITE_ are exposed to the browser.

.env.local (never commit this)
# .env.local — Vite reads this automatically VITE_API_URL=http://localhost:3001 # .env.production — used in production build VITE_API_URL=https://api.yourapp.railway.app
src/api.ts — reading the variable
// import.meta.env — Vite's env object const API_URL = import.meta.env.VITE_API_URL; // Usage: const res = await fetch(`${API_URL}/api/books`);
VITE_ prefix is required — Vite strips variables without it. This prevents accidentally exposing secrets (database passwords, private keys) to the browser bundle.
import.meta.env — Vite's equivalent of Node's process.env. At build time, Vite replaces these references with the actual string values.
.env.local is for secrets — add it to .gitignore. Provide a .env.example with placeholder values so other developers know what to set.
Restart required — Vite reads env files on startup. After adding or changing a .env file, stop and restart npm run dev.

The Vite Proxy — Simpler in Development

Instead of configuring CORS, you can tell Vite to forward API requests to your Express server. The browser sees only one origin — CORS never triggers.

vite.config.ts
import { defineConfig } from 'vite'; import react from '@vitejs/plugin-react'; export default defineConfig({ plugins: [react()], server: { proxy: { // Any request to /api/** is forwarded to Express '/api': { target: 'http://localhost:3001', changeOrigin: true, }, '/auth': { target: 'http://localhost:3001', changeOrigin: true, }, }, }, });
With the proxy, your React code calls fetch('/api/books') — no full URL needed. Vite intercepts the request and forwards it to Express on port 3001.
Development only — the Vite proxy is a dev-server feature. In production your app is built into static files that cannot proxy. You still need CORS configured on Express for production.
The proxy approach means you can use relative URLs in development and absolute URLs in production by reading VITE_API_URL — or use an empty string for the base URL when the proxy is active.

Centralising API Calls — The api.ts Module

Scattering fetch('/api/books', { headers: { Authorization: ... } }) across every component is fragile. AI generates a central API module — one place to set the base URL, auth header, and error handling.

src/api.ts
const BASE = import.meta.env.VITE_API_URL ?? ''; function getHeaders(): HeadersInit { const token = localStorage.getItem('token'); return { 'Content-Type': 'application/json', ...(token ? { 'Authorization': `Bearer ${token}` } : {}), }; } async function request<T>( path: string, options: RequestInit = {} ): Promise<T> { const res = await fetch(`${BASE}${path}`, { ...options, headers: { ...getHeaders(), ...options.headers }, }); if (!res.ok) { const body = await res.json().catch(() => ({})); throw new Error(body.error ?? `HTTP ${res.status}`); } return res.json() as Promise<T>; } export const api = { getBooks: () => request<Book[]>('/api/books'), addBook: (b: NewBook) => request<Book>('/api/books', { method: 'POST', body: JSON.stringify(b) }), deleteBook: (id: number) => request<void>(`/api/books/${id}`, { method: 'DELETE' }), };
One source of truth for the base URL, auth header, and error shape. Change how auth works → edit one file, not every component.
Spread operator on headers — { ...getHeaders(), ...options.headers } lets callers override headers if needed, while always including the defaults.
Error body parsing — res.json().catch(() => ({})) gracefully handles non-JSON error responses (e.g. HTML error pages from a crashed server) without throwing a second error.

Handling Authentication Errors — 401 Unauthorised

A 401 response means the token is missing, expired, or invalid. The API layer is the right place to detect this and redirect to login — not every individual component.

src/api.ts — 401 handling
async function request<T>( path: string, options: RequestInit = {} ): Promise<T> { const res = await fetch(`${BASE}${path}`, { ...options, headers: { ...getHeaders(), ...options.headers }, }); // Handle token expiry globally if (res.status === 401) { localStorage.removeItem('token'); // Redirect to login without React Router window.location.href = '/login'; throw new Error('Session expired'); } if (!res.ok) { const body = await res.json().catch(() => ({})); throw new Error(body.error ?? `HTTP ${res.status}`); } return res.json() as Promise<T>; }
Clear the token first — before redirecting, remove the expired token. Otherwise the login page loads, the user logs in, and the old token remains causing an immediate re-expiry.
window.location.href — a hard navigation, not React Router. This ensures state is fully reset. With React Router you'd use a navigate() hook, but that requires being inside the router — the API module is outside it.
Ask AI: "What should happen if the 401 occurs on the login endpoint itself?" (It should not redirect in that case — you're already on login.) This is an edge case AI sometimes misses.

Using api.ts in Components

With the API module in place, components become clean — they describe what to render, not how to talk to the server.

BookList.tsx — clean component
import { api } from '../api'; function BookList() { const [books, setBooks] = useState<Book[]>([]); const [isLoading, setIsLoading] = useState(true); const [error, setError] = useState<string|null>(null); useEffect(() => { api.getBooks() .then(setBooks) .catch(e => setError(e.message)) .finally(() => setIsLoading(false)); }, []); async function handleDelete(id: number) { await api.deleteBook(id); setBooks(prev => prev.filter(b => b.id !== id)); } if (isLoading) return <p>Loading…</p>; if (error) return <p>{error}</p>; return ( <ul> {books.map(b => <li key={b.id}> {b.title} <button onClick={() => handleDelete(b.id)}>Delete</button> </li> )} </ul> ); }
Optimistic UI — handleDelete awaits the API call, then filters the local state. A more responsive version removes from state first, then reverses on error. Ask AI to show you both approaches.
The component does not know or care about the base URL, auth headers, or error parsing. All of that lives in api.ts. This is separation of concerns in practice.
Notice api.getBooks().then(setBooks) — because getBooks returns a typed Promise, you can chain directly. No need for a wrapper async function for simple cases.

Token Storage — localStorage vs sessionStorage vs Cookies

AI will often default to localStorage for the JWT. Understand the trade-offs before accepting that choice.

StoragePersists across tabs?Persists after close?XSS riskCSRF risk
localStorageYesYesHigh — JS readableLow
sessionStorageNoNoHigh — JS readableLow
httpOnly cookieYesYesLow — not JS readableHigher
The real question to ask AI: "You stored the JWT in localStorage. What are the XSS implications, and under what threat model would you choose httpOnly cookies instead?" This single question reveals whether AI is making a considered choice or a default one. For a learning project, localStorage is fine. For production handling sensitive data, evaluate carefully.

Debugging CORS — Reading the Error

CORS errors are verbose. Knowing which part of the message to read saves significant time.

browser console — CORS error anatomy
Access to fetch at 'http://localhost:3001/api/books' from origin 'http://localhost:5173' has been blocked by CORS policy: Case 1 — no CORS header at all: No 'Access-Control-Allow-Origin' header is present on the requested resource. → cors() not installed or not before routes Case 2 — wrong origin: The 'Access-Control-Allow-Origin' header has value 'https://example.com' that is not equal to the supplied origin. → origin: in cors() config doesn't match Case 3 — preflight failed: Response to preflight request doesn't pass access control check. → Authorization missing from allowedHeaders
Check middleware order — app.use(cors(...)) must come before route definitions. If it's after, requests hit the routes before CORS headers are added.
Check the Network tab — look at the OPTIONS preflight request. What status did it return? What headers came back? This tells you whether the server responded at all or whether Express rejected the preflight route.
curl to the same endpoint works? Then it is definitely CORS — not a server bug. This rules out half the problem space immediately.

Reflect — Evaluating the API Layer AI Built

The API module is infrastructure — it touches every feature. Read it more carefully than any other generated file.

  • 01Where is the token read from? localStorage? sessionStorage? A cookie? Was this an explicit design choice in the prompt, or an AI default? Do you agree with it for your use case?
  • 02What happens on a 401? Does the code redirect, throw, or silently fail? Test it: expire or delete the token, make a request, and observe what happens. Does the user experience match your expectation?
  • 03Are all HTTP methods covered? GET and POST are easy — did AI correctly set Content-Type on POST bodies? Did it include PATCH and DELETE? Test each endpoint with a real request.
  • 04What does the TypeScript tell you? If you call api.addBook() with the wrong shape, does TypeScript catch it? Open the type hover in your editor and verify the parameter types match your API schema.
