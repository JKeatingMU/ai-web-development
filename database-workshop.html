Why Databases?

Flat files (JSON, CSV, text) seem simple — until things go wrong.

Problems with files
No concurrent access — two users writing at once corrupt the file.
No querying — to find one record you read the whole file.
No referential integrity — nothing stops you deleting a record that others depend on.
No rollback — a crash mid-write leaves partial data permanently.
ACID guarantees — what a database gives you
Atomicity — a transaction is all-or-nothing; partial writes never happen.
Consistency — constraints are always enforced; invalid data is rejected.
Isolation — concurrent transactions don't interfere with each other.
Durability — once committed, data survives crashes and restarts.
PostgreSQL is the database used throughout this course — free, open source, production-grade.

The Relational Model

Data is organised into tables (relations). Each table has named columns (fields/attributes). Each row is one record (tuple). Tables are linked by foreign keys.

Every table should have a primary key — a column (or set of columns) that uniquely identifies each row.

PostgreSQL Data Types

CategoryTypes
TextTEXT, VARCHAR(n), CHAR(n)
NumbersINTEGER, BIGINT, NUMERIC(p,s), REAL
BooleanBOOLEAN — true / false
Date / timeTIMESTAMPTZ, DATE
SpecialUUID, JSONB, ARRAY
Use TIMESTAMPTZ not TIMESTAMP — always store time with timezone. Without timezone information, timestamps become ambiguous when servers move regions or clocks change.

Use TEXT not VARCHAR — PostgreSQL handles them identically internally and TEXT is simpler. Only use VARCHAR(n) if you specifically need to enforce a length limit.

Primary Keys

Two common strategies for generating unique IDs:

primary key options
-- Auto-incrementing integer (simple) id SERIAL PRIMARY KEY -- UUID (better for distributed systems / APIs) id UUID PRIMARY KEY DEFAULT gen_random_uuid() -- Complete minimal CREATE TABLE CREATE TABLE books ( id UUID PRIMARY KEY DEFAULT gen_random_uuid(), title TEXT NOT NULL, author TEXT NOT NULL, status TEXT NOT NULL DEFAULT 'unread', created_at TIMESTAMPTZ DEFAULT NOW() );
  • SERIALInteger, auto-incremented by the DB. Simple. Leaks row count — avoid exposing directly in URLs.
  • UUIDGlobally unique. Doesn't leak row count. Safe to expose in public URLs. Best choice for APIs.

SELECT & WHERE

The most common SQL operation — reading data from a table.

SELECT examples
-- All columns, all rows SELECT * FROM books; -- Specific columns with a filter SELECT title, author FROM books WHERE status = 'reading'; -- Most recent 10 books SELECT * FROM books ORDER BY created_at DESC LIMIT 10;
= != < > <= >= LIKE ILIKE IN IS NULL
SELECT * is fine for learning but in production code name your columns explicitly — it prevents surprises when the schema changes and a new column appears unexpectedly in your JSON output.

INSERT, UPDATE, DELETE

write operations
-- INSERT a new row INSERT INTO books (title, author, status) VALUES ('The Pragmatic Programmer', 'Hunt & Thomas', 'unread') RETURNING *; -- UPDATE with COALESCE (partial update pattern) UPDATE books SET title = COALESCE($2, title), status = COALESCE($3, status) WHERE id = $1 RETURNING *; -- DELETE a row DELETE FROM books WHERE id = $1 RETURNING id;
RETURNING * gives you back the modified row without a second SELECT — use it in every INSERT and UPDATE.
  • COALESCE($2, title)Returns $2 if not null, otherwise keeps the existing title. This enables partial PATCH updates.
  • $1, $2, $3Parameterised placeholders — prevents SQL injection. Your driver fills these in safely.

Constraints

Constraints are rules enforced by the database on every write operation.

ConstraintWhat it enforces
NOT NULLColumn must have a value — never empty
UNIQUENo two rows may have the same value in this column
CHECKA boolean condition must be true: CHECK (status IN ('unread','reading','done'))
FOREIGN KEYValue must exist in the referenced table
PRIMARY KEYImplies NOT NULL + UNIQUE; identifies each row
foreign key with ON DELETE
book_id UUID NOT NULL REFERENCES books(id) ON DELETE CASCADE
  • CASCADEDelete child rows automatically when the parent is deleted
  • RESTRICTBlock the parent delete if any children exist
  • SET NULLSet the FK column to NULL when the parent is deleted
Constraints are enforced by the database — not your application code. This is your last line of defence against invalid data.

JOINs

JOINs combine rows from two tables based on a matching column — typically a foreign key.

LEFT JOIN example
-- List books with their session count SELECT b.title, COUNT(rs.id) AS session_count FROM books b LEFT JOIN reading_sessions rs ON rs.book_id = b.id GROUP BY b.id, b.title;
Use LEFT JOIN when you want all rows from the left table even if there are no matching rows in the right table.
  • INNER JOINOnly rows that match in both tables
  • LEFT JOINAll left rows + matching right rows (nulls for non-matches)

Transactions

Atomicity means all or nothing. Without a transaction, a crash between two related writes leaves the database inconsistent.

transaction syntax
BEGIN; UPDATE accounts SET balance = balance - 100 WHERE id = 1; UPDATE accounts SET balance = balance + 100 WHERE id = 2; COMMIT; -- or ROLLBACK; if something went wrong
  • BEGINStart a transaction — all subsequent statements are grouped
  • COMMITApply all grouped statements permanently
  • ROLLBACKDiscard all grouped statements — as if they never happened
In pg (the Node.js driver), use client.query('BEGIN') / client.query('COMMIT') from a checked-out pool client — not pool.query(). Pool queries run in auto-commit mode.

Indexes

An index is a pre-sorted data structure that speeds up WHERE and JOIN lookups. Without one, PostgreSQL reads the entire table (O(n)). With a B-tree index, it jumps to the match (~O(log n)).

creating indexes
CREATE INDEX ON books(status); -- frequently filtered column CREATE INDEX ON reading_sessions(book_id); -- FK column (always index FKs) CREATE UNIQUE INDEX ON users(email); -- enforce uniqueness + speed
Don't index everything — indexes slow down INSERT and UPDATE because the index must be updated too. Index FKs and columns you filter or sort on frequently.
EXPLAIN ANALYSE SELECT ... shows you what PostgreSQL is actually doing — use it to confirm your indexes are being used and to spot full table scans.

Migrations: Evolving Your Schema

A production database already has data — you cannot re-run schema.sql from scratch. Migrations apply incremental, safe changes.

safe migration pattern
-- Always use IF NOT EXISTS / IF EXISTS ALTER TABLE books ADD COLUMN IF NOT EXISTS page_count INTEGER; CREATE INDEX IF NOT EXISTS idx_books_status ON books(status);

Dangerous without a backup first:

  • DROP TABLEDeletes all data permanently
  • DROP COLUMNColumn and all its data gone
  • ALTER TYPEMay fail or silently lose data
Always take a backup before running any migration:
pg_dump $DATABASE_URL > backup-$(date +%Y%m%d).sql

Using AI to Reason About Data

Schema design

AI generates schemas quickly. Your job is to read every column and ask: why this type? why this constraint? Could this constraint cause a problem at scale?

Query writing

AI writes JOIN queries fluently. Paste the query back and ask: "explain this query to me as if I'm learning SQL" — then verify the explanation matches what the code does.

Debugging

Paste psql error messages directly into the AI. PostgreSQL error codes (like 23505 for UNIQUE violation) are well-known and AI diagnoses them accurately.

Every time you use AI to write SQL, run it, understand the result, then ask AI to explain any part that's unclear. Never merge SQL you cannot read.
